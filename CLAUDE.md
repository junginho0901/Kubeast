# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This repo is **Kubeast** — a Kubernetes operations platform combining a natural-language AI assistant with a rich multi-cluster dashboard. It is a polyglot microservice system (Go + Python + React) deployed to Kubernetes via Helm, with a kind-based local dev loop.

See [AGENTS.md](AGENTS.md) for the project-specific rules every contributor (human or AI) must follow — most importantly the **audit-log requirement** summarized below.

## Architecture

Requests enter through an NGINX **gateway** (`:8000`) that routes to backend services. Each service owns one concern and a slice of the data layer (Postgres for durable state, Redis for cache/session context).

| Service | Lang | Port | Module path / dir | Role |
| --- | --- | --- | --- | --- |
| `gateway` | NGINX | 8000 | `helm/kubeast/files/nginx.conf` | Routing, CORS, SSE/WebSocket proxy. No image build — ConfigMap only. |
| `auth-service` | Go | 8004 | `services/auth-service-go` | JWT issuance, JWKS, org/team/user hierarchy, RBAC |
| `ai-service` | Python/FastAPI | 8001 | `services/ai-service` | LLM integration, streaming chat, optimization suggestions, tool calling, the MCP server for external AI agents (`app/mcp_server.py`, `MCP_ENABLED`; `MCP_WRITE_TOOLS` adds the write tools for Write-ceiling keys). The provider SDK is imported when a model client is first made and the MCP SDK only with `MCP_ENABLED`. Chart `ai.enabled: false` leaves this service, `tool-server` and the ModelConfig controller out (`AI_ENABLED` tells k8s-service, which reports it in `/cluster/features`) |
| `k8s-service` | Go | 8002 | `services/k8s-service-go` | K8s resource CRUD, WebSocket logs/exec, topology, Helm, GPU/DRA |
| `session-service` | Go | 8003 | `services/session-service-go` | Chat session / message history |
| `tool-server` | Go | — | `services/tool-server` | Backend for AI tool calls |
| `model-config-controller-go` | Go | — | `services/model-config-controller-go` | controller-runtime operator for the `ModelConfig` CRD |
| `frontend` | React/Vite/TS | 5173 | `frontend` | UI |

**Target-cluster requirements**: Kubeast installs nothing on the clusters it manages (the node shell pod aside). Whatever a feature needs there — RBAC, metrics-server, a Prometheus Service and the metric names it queries, OpenCost, a CRD, a minimum server version, a label — is listed in [docs/cluster-requirements.md](docs/cluster-requirements.md) with how Kubeast finds it and how to check it; example values live in `deploy/examples/target-cluster/` and `scripts/render-target-rbac.sh` renders the RBAC a registered cluster needs. A change that makes a feature read something new from the target cluster updates that page in the same PR.

**AI tool-calling flow**: `ai-service` (chat orchestration, provider adapters for OpenAI/Anthropic/Gemini; Azure OpenAI is its v1 API through the OpenAI-compatible client — base URL `…/openai/v1/` required, the deployment name as the model, the key as Bearer and `api-key`, deployment URLs and `api-version` refused in `model_config_policy`, and the connection test goes through the same `ProviderAdapter` as the chat; a config's options carry its own limits — `max_tokens`, else the chat's 4,096 and an investigation step's 2,048, and `tool_result_chars`, else 6,000, past which the model reads a result's start, or the end for the log tools (`formatters._LOG_TOOLS`), where the newest lines are — read through `app/services/ai/limits.py` — a `ModelConfig` resource sets them as `spec.maxTokens` (else its `openAI`/`anthropic` section's) and `spec.toolResultChars`, which the controller writes into the same options as numbers, next to its CA as `spec.caCert`; `provider_adapter` never sends `tool_result_chars`, sends OpenAI's and Azure's answer length as `max_completion_tokens`, and when a model's 400 names a parameter it refuses (`param`, as reasoning models refuse `temperature`) leaves it out, sends again once and remembers it per provider, base URL and model; the AI Models list answers `used_for` — `model_config_service.usage`, by the rules the chat, the economy tier and the investigations pick their config — which the cards show) dispatches whitelisted tools (`app/services/tool_whitelists.py`) to `tool-server`, which calls the K8s API. A role holding `ai.tool.*` does no more through the AI than on its screens: tool-server (`screen_permissions.go`) and ai-service (`app/services/ai/screen_permissions.py`) keep the same table of what the route behind each tool's screen asks, and a tool not in it is refused to everyone. A new tool takes a line in both tables and a case in `screenPermissionCases` (`TestEveryToolIsInTheTableAndHasACase`); `TestToolScreenCasesFixture` writes `tool_screen_permission_cases.json`, which `test_tool_app_permissions.py` runs. So `k8s_execute_command` also asks `resource.pod.exec` and a rollout undo `resource.workload.rollback`, which the Write role does not hold. A write tool's audit row says what it was asked to do, credentials masked (`audit_target.write_tool_input`), and an exec is a `k8s.pod.exec` row too. A write holding what a tool's answer gives in place of a value (`<REDACTED:…>`, a Secret's `***`, the base64 of either) is refused for every caller, before the approval card (`app/services/ai/masked_writes.py`) and before kubectl (tool-server `masked_writes.go`), both held to `masked_write_cases.json`. Tool results stream back to the chat. Provider `claude-code` (a Claude subscription's setup-token, personal use, off by default, image build arg `WITH_CLAUDE_CODE`, released as the `<version>-claude-code` tag the chart runs when the provider is on) hands the model loop to Claude Code (`app/services/claude_code.py`); its tool calls come back to the same `_call_tool` in `app/services/ai/streaming.py`; the alert investigator's loop is `app/services/ai/tool_turn.py`, which has the same two branches. A chat answer keeps the order it came in: the text written before a tool call stays above that call's `<details>` block, on screen (`chatStreamManager`'s one `content`, the same in AI Chat and the floating chat) and in the saved message (`streaming.answer_markdown`, both paths); the history the next model call gets drops the tool blocks whole, arguments and results too (`ai_service.strip_tool_blocks`, and Copy `chatTextUtils.stripToolDetails`, held equal by `chatTextUtils.cases.json`: tags inside a code block do not count). `chatStreamManager` keeps where each tool block starts and where its result goes, so a result, the arguments or the answer holding a tool's name or the placeholder cannot take another call's result or 🔐 line. A tool block below a code block the model left open closes that block first, on screen (`appendToolBlock`) and saved (`answer_markdown`), through `chatTextUtils.closingFence` and `formatters.closing_fence` (held equal by `chatAnswer.cases.json`), so it does not read as code; a fence a less indented line has ended, in a list item, is left alone. An answer is complete only on `[DONE]`: a refused request (`response.ok`), a stream that closes without it and an empty 200 are errors (`streamHttp`, `streamCut`, `streamEmpty`), with the question and the letters that came left on screen in both chats. Each tool result carries `access`, the identity the call reached the cluster as (`services/pkg/auth.Access`, computed from the same `Impersonation` the request sends): tool-server returns it in its answer and k8s-service in the `X-Kubeast-Access` header (`ClusterMiddleware`); ai-service never works it out. It is the 🔐 line under the tool block's name — `frontend/src/services/toolAccess.ts` while the answer streams, `app/services/ai/access.py` in the saved answer, the same text — and `after.access` of the call's audit row. Under it, "🧾 Cluster requests" lists the Kubernetes requests the call made (`after.requests`, `services/pkg/accesstrail`): a caller that sends `X-Kubeast-Record` (ai-service's k8s-service client, tool-server's `doTraced`) gets them from k8s-service in `X-Kubeast-Requests`, set when the handler starts its answer; the cluster transport (`accesstrail/kube`) sends each with a fresh `Audit-ID` and reads it with the API server's `RequestInfoFactory`, and a hit in k8s-service's cache or overview informers is listed as `source: cache`. The kubectl tools run kubectl against a loopback proxy in tool-server (`kubeproxy.go`, TLS with a boot-time certificate because client-go sends a token only over TLS, one token per run in a temporary kubeconfig, a `/c/<cluster>` path so kubectl's discovery cache stays per cluster): it drops the identity kubectl sends and forwards with the cluster credential, the user's impersonation and an Audit-ID through the `kubectl proxy` parts (`UpgradeAwareHandler`, client-go transports), listing resource requests only; `TOOL_SERVER_KUBECTL_PROXY=false` keeps the direct `--as` path.

### Go module layout

Go services are **separate modules** (not a go.work workspace). Shared code lives in `services/pkg` (module `github.com/junginho0901/kubeast/services/pkg`) and is wired into each service via a `replace ... => ../pkg` directive in its `go.mod`. `services/pkg` provides:
- `audit/` — the shared audit-log API (see below)
- `auth/` — JWT verification (`jwt.go`)
- `dbmigrate/` — the database schema as versioned SQL migrations (goose, embedded). auth-service applies them at boot (`MIGRATIONS_MODE=startup`) or a chart hook Job does (`job`); every other service only waits for `dbmigrate.Required`. New schema changes go in a new `migrations/NNNNN_*.sql` file plus a `Required` bump (and ai-service's `REQUIRED_SCHEMA_VERSION` in `app/database.py`, which `tests/test_schema_wait.py` holds equal) — never in service start-up code. A migration that creates a table also adds it to `expectedTables` in `dbmigrate_postgres_test.go`; the `dbmigrate (postgres)` CI job compares the table list after `Up`.
- `config/`, `logger/`, `response/` — config loading, slog setup, HTTP response helpers
- `storeurl/` — the address rule for the metrics and log store URLs registered on a cluster, run when a URL is saved, before each request and when a name has resolved (`features.clusterStoreAllowedHosts`). ai-service's `model_config_policy` reads an address's IPv6 forms the same way for a model's URL. `ai-service/tests/fixtures/address_forms_cases.json` gives each address both rules' answers, `store` and `model`, each `never`, `listed` or `open`, which `TestSharedAddressCases` and `test_shared_address_cases` run
- `netpol/` — the NetworkPolicy evaluator behind the drawers' "Network Policies" section, the check window and the AI tool `network_policy_check` (k8s-service `internal/k8s/netpol_check.go` reads the objects as the user). It depends on nothing beyond `k8s.io/api`; where the documentation leaves the behaviour to the network plugin (an `ipBlock` covering a pod IP, hostNetwork pods) it answers unknown. `services/netpol-oracle` is a test-only module, in the CI go matrix and in no image, that compares it with np-guard/netpol-analyzer on generated scenarios (`NETPOL_ORACLE_SCENARIOS`, `NETPOL_ORACLE_SEED` for longer runs)

A Go service follows a `cmd/server/main.go` → `internal/routes` (route registration) → `internal/handler` (one file per resource kind, e.g. `pods.go`, `deployments.go`, `helm*.go`) → `internal/k8s` (client logic) layering. A k8s-service route with no `{namespace}` in its path is refused to a grant limited to namespaces until it has a rule in `internal/handler/namespace_scope_routes.go`; `TestNamespaceRouteTable` holds every route to its rule. The same middleware holds everyone to the two namespaces of `services/pkg/protectedns`, the one rule k8s-service and tool-server share: on the cluster Kubeast runs in (`InCluster`/`IsSelfCluster`, or a kubeconfig whose `kube-system` UID is that cluster's) its `POD_NAMESPACE` is for global admins (`*`) as far as Secrets, Helm releases, writes and terminals go, and on any cluster `NODE_SHELL_NAMESPACE` takes writes, terminals and pod logs (a node shell's log is its screen) only from holders of `resource.node.shell`. Other reads stay. A read of the log store with no namespace leaves the node shell's namespace out with a matcher in its query unless the caller holds `resource.node.shell` on that cluster (`hiddenLogNamespace`; search, LogQL, labels and patterns, `TestAReaderAcrossNamespacesGetsNoNodeShellLines`): a search says so as `hiddenNamespace` in its answer and `hidden_namespace` in its row, and LogQL shows it in `effectiveQuery`. A terminal, a followed log and a live list stay open past their token and end when the session behind them stops standing (`auth.LiveSessions`, read from the shared database by `internal/sessioncheck`, close code 4401 or the event `session-ended`). What a caller reads of a failed call to a server goes through `response.Public`, which leaves its address out. `routeAct` says what a route does there (`TestRoutesSayWhatTheyDo`); `protectedns.RoundTripper` on the cluster client (`Pinned` on `UserRESTConfigFor`, whose callers send their own contexts) and on tool-server's kubectl proxy holds each request as the API server reads it and narrows a list of every namespace's Secrets with a field selector; tool-server gets the names with the kubeconfig (`/internal/clusters/{id}/kubeconfig`) and `/cluster/can-i` answers no there without asking, so the buttons follow. Without `resource.secret.reveal` a Secret's and a Helm release's values read masked, and what a save sends back for them stands for the values. A Secret's apply leaves each mask out of its merge patch (`ApplySecretYAMLWithoutReveal`), and a create holding one is a 400 (`YAMLSecretMasks`). A Helm upgrade keeps a `<REDACTED:…>` left where it was shown and refuses one anywhere else with a 400 naming where (`UpgradeValuesWithoutReveal`, `internal/helm/masked_values.go`). `kept_masked` names where a value stayed, in the answer and the audit row. For Helm, `changed_masked` names in both where one was written over or removed, read from the text sent and never compared with the value (`TestHelmPreviewAnswersARightGuessAsAWrongOne`). `values_changed`, in the answer only, says the values sent differ from those read, which keeps `UpgradePreviewModal`'s Apply open when the diff is empty. What a screen reads the AI reads too: every GET route of k8s-service, auth-service, session-service and ai-service has a row in `services/ai-service/tests/fixtures/ai_route_coverage.json`, the tool that reads the same data or the reason none does (`TestEveryGETRouteIsReadByAToolOrExcludedWithAReason` in each Go service and `test_every_get_route_is_read_by_a_tool_or_excluded_with_a_reason` in ai-service, which fail on a new route without one); tool-server's `TestRouteCoverage_*` run each tool with its row's arguments against stand-ins and hold it to that route or kind, and `test_ai_route_coverage.py` holds the call to what the model is offered. A row whose reason starts "No tool yet" is a gap on record, not a decision. The `k8s-service` also has `internal/ws` (WebSocket logs/exec), `internal/helm`, `internal/cache`, and `internal/netflows` — the Hubble Relay client behind the drawers' "Recent Flows" and the AI tool `network_flows` (`features.networkFlows`): `observer.Observer/GetFlows` as gRPC over HTTP/2 written by hand with `protowire` (no Cilium or grpc module), sent through the API server's service proxy as the user (`proxy`, needs Relay TLS) or to a TLS address; `wire_test.go` decodes bytes recorded from a real Relay (`testdata/`), and `dropreasons.go` copies the drop reason names of Cilium's `flow.proto`. `internal/netdrops` is the drawers' "Network Drops" and the AI tool `network_drops`: it reads the label names of the Hubble metric `hubble_drop_total` in the cluster's Prometheus (separate `source_*`/`destination_*` labels, or one `source`/`destination` label of `<namespace>/<pod>`), builds fixed PromQL with the names only as matcher values (its tests parse every query with Prometheus's parser), and sums the answer by reason and peer; `internal/k8s/netdrops_target.go` names a target's workload as the agent does and lists its pods as the user. `internal/nettraffic` is the Resource Graph's traffic lines (`GET /api/v1/networktraffic`): one Relay read for all the graph's namespaces folded into workload-to-workload lines (a forwarded connection counts where it arrived — seen at the destination's ingress, answered, or going outside the pods — since Hubble's verdict is per observation point), or the Hubble metrics `hubble_tcp_flags_total{flag="SYN"}` (counted at the arriving side with `traffic_direction`) and `hubble_drop_total`; `hubble_flows_processed_total` is not used because it counts replies with no label to tell them. The frontend (`pages/resource-graph/traffic.ts`, `RoutedEdge.tsx`) lays the lines out with ELK (`ORTHOGONAL` routes, `elk.json.edgeCoords: ROOT`, edge labels placed by ELK) so they run between the boxes, and in the Traffic view splits each line by port into rows of the receiving box with ELK ports fixed at each row. Microsoft Retina's Hubble control plane serves the same Relay, but its flows name pods without their workload and, where the client sends, a Service's cluster IP: `netflows.Lookup` (`internal/k8s/netflows_lookup.go`, as the user) names the pods' workloads as Cilium's `GetWorkloadMetaFromPod` does and marks those ends `service_address`, which the lines count where they arrive; a workload read also asks the Relay for its current pods by name, and metrics with pod labels but empty workload labels (Retina's) are read by pod and named the same way; such a metric names one side of a drop only (Retina without remote context labels the pod on the node that saw it), so the other side is `unnamed` — a box "Peer the metric did not name", note `drop_peer_unnamed` — not outside the pods, a metric seen on one side only still counts as one (`DetectShape`), and the drops naming no pod at either end are counted cluster-wide (`UnplacedDropsQuery`, `unplaced_drops` on the status line). A `calico` entry reads Calico's Whisker backend instead (`internal/netflows/whisker.go`, `GET …/services/https:whisker:8443/proxy/whisker-backend/flows` as the user, verb `get`): one list per side, items Goldmane aggregated per pod set (`<generateName>*`, looked up like a pod) turned into flows that count packets, each side reporting its half (the drawer's groups leave out what only the sender saw forwarded when the receiver dropped it, as the lines count it where it arrived); the target cluster needs one Calico policy letting the API server reach Whisker (`deploy/kind/calico-whisker-apiserver.yaml`) and the Role of `templates/impersonation-viewer-whisker.yaml`, which renders only with `features.networkFlows.whisker` set so Kubeast's own install does not make it. `internal/nfm` is the drawers' "Top Talkers" and the AI tool `network_top_flows` (`features.networkFlowMonitor`, `GET /api/v1/namespaces/{ns}/networktopflows`): the top contributors of an EKS cluster's Amazon CloudWatch Network Flow Monitor monitor through the AWS SDK for Go v2 (`service/networkflowmonitor`, Kubeast's own AWS identity — IRSA or `existingSecret` keys), one query per category of the console's views (start, poll the status, read the pages, stop on timeout, kept for the minute); NFM takes no namespace or pod, so Kubeast keeps the rows with the target at either end, names the pods' workloads with `netflows.Lookup`, requires the user's `list` on pods (SelfSubjectAccessReview) and hides peers in namespaces the user cannot list; `nfm/nfmtest` serves the API's paths and JSON for tests.

The Pods list is paged by k8s-service (`GET /api/v1/pods/page`, `internal/k8s/pods_page.go`): the overview informers keep a `podRow` per pod instead of the Pod (`pod_index.go`, about 0.4 KB with its store entry, held under 600 bytes by `TestPodRowMemory`), the caller's own identity is asked whether it may list those pods (SelfSubjectAccessReview, 60 s), and the server searches, sorts, counts the summary cards and cuts the page; the page polls with the revision it has and gets `unchanged` while no row it may see changed. Until the informers have synced, or while `kubeast:cache` may not watch pods, the rows are listed as the caller 500 at a time. A pod's Status, READY and RESTARTS — in the row, in `formatPodDetail` and wherever else a pod's status is shown (`podListView`) — are kubectl's v1.37 `printPod` (`internal/podrow`; `TestPodListView_AsKubectlPrintsIt` holds them to a copy of `printPod` over random pods), so a pod being deleted reads Terminating. A pod's live update is the same row (`podrow.Info`) over `podrow.FromObject`, which reads an event's fields by hand because the reflective converter costs ten times the row for each of a namespace's pods (`BenchmarkPodFrame`); `TestFromObjectReadsWhatInfoReads` holds it to the converter over random pods, and no environment value reaches a row. A drawer's pod table reads that Status before the phase (`podTableStatus`) and the Pod drawer's Status tile is that Status (`podDrawerStatus`); its Reason and Message rows are `status_reason` and `status_message`, its Last State row each container's `last_state` (`podLastStates`). The Namespace drawer's pod table reads `/namespaces/{namespace}/owned-pods`, whose rows take Status, READY and RESTARTS from `podListView` with `phase` beside them (`TestNamespaceOwnedPods_SayWhatThePodsListSays`). The Dashboard's Pods window is chosen by phase, and its rows and the Namespace drawer's say that Status in the Pods list's colour with the phase on hover (`podWindowBadge`). What the Namespace, Node and workload windows tell the floating chat of their pods goes through `utils/aiContext/podCounts`, which reads that Status before the phase, and `notRunningFirst` keeps the pods that need a look in a list cut for it. A pod is in one state card, so they add up to the total: Error (the phase Failed or a status naming an error), Terminating (that Status), Pending and Completed by the phase, Ready (Running with every container ready) and Not Ready what is left; Restarted is what a pod went through and counts apart (`podStats`, `TestPodStats_EachPodInOneCard`, `number-check-pods-terminating.spec.ts`, which keeps pods Terminating with a command that ignores SIGTERM and finished ones with a finalizer). GPU Pods' cards count a pod once as well: Failed for the phase Failed or a status naming an error, the rest by phase (`gpuPodCounts`, and `pod_counts` of the AI tool `gpu`), so a Succeeded or Unknown pod is in the total and in no card. The overview informers report synced only once the pod handler has had the first list, so the first page's revision does not move after it. The node list (`GET /api/v1/nodes`, also the issues' nodes) comes from the same informers for a caller the cluster lets list nodes (`cachedNodes`, SelfSubjectAccessReview through `mayList`, 60 s; a refusal, a namespace-scoped grant or informers not yet synced list as the caller): the store keeps the fields `formatNodeSummary` reads (`stripNode`, without images, annotations and condition times, so a heartbeat is no change — `sameNodeView`), and the list and its JSON are built once per change and second (`nodeSummaries`, `nodeList.JSON`) and shared by every caller — 100 people opening it each listed 1 001 nodes before, 6 MiB a request. The dashboard's counts (`GET /api/v1/cluster/overview`, the same informers) are each given only to a caller whose identity may list that kind, across the cluster or in a scoped grant's namespaces (`keepListable`, SelfSubjectAccessReview through `mayListGroup`, 60 s); the others are null and named in `refused`, a card showing "—" with the reason (`number-check-dashboard.spec.ts`). A node's usage (`/metrics/nodes`, the dashboard's top nodes) is printed as `kubectl top nodes` prints it (`nodeUsage`: CPU rounded up to a millicore, memory in Mi rounded down, percents of the allocatable cut to a whole number — `TestNodeUsage_AsKubectlTopPrintsIt`, `number-check-monitoring.spec.ts`); Monitoring's Nodes tab lists the node list's nodes, one without a sample last with `-`, as kubectl prints `<unknown>`. A refresh of Monitoring's Nodes or Pods tab that fails keeps the rows, says how old they are (`MetricsRefreshFailed`) and tells the floating chat as `refresh_failed` (`monitoring.spec.ts`). The Node drawer's Allocated Resources are kubectl describe node's (`node_allocated.go`, `allocated_resources`): the pods on the node not Succeeded or Failed listed as the caller, a grant limited to namespaces only those (`allocated_scope`), the reason without rows when they could not be read (`allocated_error`). The callers that hold every pod row (the page, the node map, the pod metrics' limits, the flows' workload lookup) take one of `GOMAXPROCS` places (`podRowSlots`) after the access check and give it back with `podRowSet.done`, so a crowd waits instead of copying the rows hundreds of times at once (400 people on the Pods page took 482 MiB). k8s-service gives the Go GC 90 % of its cgroup memory limit unless `GOMEMLIMIT` is set (`cmd/server/memlimit.go`), live watches are capped at `multicluster.wsMaxSubscriptions` (2 000, 50 per tab) and the gateway runs 2 nginx workers of 8 192 connections each (a connection counts on both sides); `docs/architecture.md` "Many users" has what one k8s-service measured. Cluster View reads the same rows: `GET /api/v1/pods/nodes` (`pods_nodes.go`) counts each node's pods by the card colour, which the row keeps (`podHealth`, Go port of `pages/cluster-view/podHealth.tsx` `getPodHealth` — `TestPodHealthFixture` writes `podHealth.cases.json`, which `podHealth.cases.test.ts` runs the page's function over), for the node map (`ClusterNodeMap.tsx`, Canvas 2D, a dot per pod) polled with the revision every 2 s; a node box on screen fetches `GET /api/v1/pods/on-node?node=` as the caller and watches that node (`fieldSelector=spec.nodeName`), so the page holds the pods on screen, not the cluster's; `number-check-cluster-view.spec.ts` holds the legend, the cells, the box badges, the Unscheduled box, the search counts, a namespace-limited grant's map and the floating chat's numbers (a node ready as `utils/nodeStatus` reads it) to kubectl. The Resource Graph lists pods 500 at a time into `rgPod` and, with `group_pods` (the page and the AI tool `resource_graph` send it, the tool through `/namespaces/{namespace}/resource-graph`, which reads the same options, and answers the summary first, the nodes, then the edges (`marshalOrdered`), so a model's cut keeps the objects; the API default does not group), folds the healthy pods (`podHealth`) of an owner with more than `podGroupMin` (10) pods that have the same edges into one node of the members' kind with `group`, `count` and `members` (`resource_graph_groups.go`): its edges stand for every member and carry a `count`, the page's node or instance grouping (`group_by`) is part of the group, a StatefulSet's per-pod PVCs (`<template>-<pod>`) and their PVs are grouped with its pods, and `expand` lists groups drawn pod by pod. A group box opens `PodGroupList` — the owner's pods from `/pods/page?owner=<kind>/<name>` (`health` filter and counts, `sort=health` puts problems first). ## Audit logging — mandatory (read before touching any Go handler)

> Authoritative rules: [AGENTS.md](AGENTS.md) and [docs/audit-log-plan.md](docs/audit-log-plan.md). PRs that add/modify a write-class HTTP handler **without** an audit call are rejected.

Every **write-class HTTP handler** (create/update/delete/rollback/restart/…) and every **sensitive read** (Secret reveal, Node shell, Pod logs sensitive access, container log files, Cronjob trigger, session recording read, audit-log read itself) MUST record an audit entry via `services/pkg/audit`.

Code that runs commands in a container through `pods/exec` must use short commands that end on their own: a process started through exec keeps running in the container after the client disconnects (TTY or not). Pass an argv array, never a shell — see AGENTS.md "컨테이너 exec". Plain list/get reads and health/public endpoints are excluded.

- **Action names are strict**: `<domain>.<object>.<verb>` (e.g. `k8s.pod.delete`, `helm.release.rollback`, `ai.tool.execute`, `admin.audit.read`). New actions must be added to the catalog in `docs/audit-log-plan.md §5-2` **first** (update the plan doc before the code).
- **Record both success and failure** — on failure set `rec.Result = audit.ResultFailure` and fill `rec.Error`.
- The **database row is a precondition for sensitive actions; only the stdout mirror is best-effort.** While the audit store cannot take a row, writes and sensitive reads are refused with 503 `audit unavailable` (`AUDIT_FAIL_CLOSED`, default true; chart `audit.failClosed`) — mutation routes through the `audit.RequireWritable` middleware, conditionally-audited GET handlers via `h.auditReady(r)` before the action plus the `recordAudit*` return value (`h.refuseUnaudited`). A write that fails after a mutation already ran is counted and logged by `audit.Guarded`; the response stands, and from then on readiness probes a write (inserted and rolled back) until the audit table takes rows again — a ping alone misses a database that answers while that table refuses rows. auth-service refuses admin writes only (sign-in, sign-out, token refresh and one's own password change go on); the AI chat's tools and alert investigations check before they read the cluster. A read tool whose row could not be stored gives no answer, in the chat, over MCP and in an investigation (`audit_unavailable`, `test_audit_after_read.py`); a write that ran keeps its own. The model connection test and the provider model list, which spend the server's key, answer 503 before they start (`model_config_audit.ready_or_503`). Services wait for the database at boot (`AUDIT_DB_WAIT_SEC`, 90 s) and exit if it does not come — there is no log-only fallback.
- Mask sensitive fields (password/secret/token/apikey) with `audit.MaskSensitive(...)` before storing in `Before`/`After`. It does not read inside a string, so YAML or JSON text stays out of the row: record its length or a summary (`yaml_len`, `helmValuesAudit`).
- Every new `docs/*-plan.md` must include a `## N. 감사 로그` section (record-target actions + permission/audit-action mapping table).

The handler pattern is documented in [AGENTS.md](AGENTS.md); use `audit.FromHTTPRequest(r)` to seed a record, then set `Service` (`audit.ServiceK8s` / `ServiceHelm` / `ServiceAI` / `ServiceAuth` / `ServiceAdmin`), `Action`, actor, target, and write via the handler's `auditStore`.

## Build & deploy

**Always build/deploy through `scripts/rebuild-kind.sh`** — do not run raw `docker build` / `kubectl` for deploys (per AGENTS.md). It builds the image, loads it into the kind cluster, and rollout-restarts the deployment. The dev cluster itself is installed from the Helm chart by `scripts/kind-deploy.sh` (values in `deploy/kind/values.yaml`, personal extras in the git-ignored `deploy/kind/values.local.yaml`); `scripts/reset-and-deploy.sh` recreates it or resets just the database.

```bash
scripts/rebuild-kind.sh ai-service frontend     # rebuild specific services
scripts/rebuild-kind.sh --all                   # rebuild everything
scripts/rebuild-kind.sh --list                  # list buildable services
scripts/rebuild-kind.sh --tag dev k8s-service   # custom image tag
scripts/rebuild-kind.sh gateway                 # nginx.conf only: helm upgrade with the release's values, no image
```

Chart-managed objects are changed through the chart (`helm upgrade`), never with `kubectl apply`: Helm 4 applies server-side, so a field kubectl took over makes the next upgrade stop on a conflict.

The script resolves KUBECONFIG in priority order: `$KUBECONFIG_PATH` → single-file `$KUBECONFIG` → repo-local `.kubeconfig-kind` → `/tmp/kubeast-kubeconfig`. Note: the auth/k8s/session Go services share build context `services/` with explicit Dockerfiles (`<svc>-go/Dockerfile`).

Install paths, all from the one chart: `helm/kubeast` (Helm; users install the released OCI chart `oci://ghcr.io/junginho0901/charts/kubeast`, whose image tags the release sets — the chart in a checkout keeps a placeholder tag), `install.sh` (one-liner for an existing cluster; installs that OCI chart at the release version `kubeast` in `deploy/dependencies.yaml`, which the release workflow requires to equal the tag), `scripts/kind-deploy.sh` (local kind), `install-docker.sh` + `docker-compose.yml` (single-host, no cluster; the release workflow starts it on the run's images and signs in before tagging — `scripts/compose-smoke.sh`, also runnable locally with a digests dir or `--build`). There is no separate copy of the manifests. `helm upgrade --reuse-values` renders the chart on the values of the release it upgrades, without the defaults later versions added: `templates/checks/upgrade-values.yaml` (rendered first, as the deepest path) stops it with the `--reset-then-reuse-values` hint, and `scripts/chart-upgrade-values.sh` (CI) renders every release's values.yaml both ways — a new values path that changes the output goes into that check. `helm/kubeast/values-minimal.yaml` is the smallest install (no AI, no Redis — k8s-service caches in memory when `REDIS_HOST` is empty — six pods, requests from measurement); the footprint table in `docs/architecture.md` comes from `scripts/kind-footprint.sh` (a kind cluster of its own, `crictl` working set and CPU once a minute) — rerun it and update the table when a change adds a pod or a background job.

## E2E tests (Playwright)

`e2e/` runs **against the live kind cluster's gateway**, not a dev server. Tests are serialized (`workers: 1`, `fullyParallel: false`) because they mutate shared single-cluster K8s state. Many specs are **visual-regression baselines** — snapshots captured on `main` must match pixel-for-pixel (within `maxDiffPixels: 100`) on feature branches.

```bash
cd e2e
npx playwright test                      # run all (set E2E_BASE_URL if not :30080)
npx playwright test ai-chat.spec.ts      # single spec
npm run baseline                         # playwright test --update-snapshots (regenerate baselines)
npm run check:assertions                 # every test asserts an outcome (also a CI job)
```

A test asserts what it is named for, not only that something is on screen: compare with what the cluster has (`kubectl`, the API) or with the value the action should produce. `check:assertions` fails on a test with no assertion or with presence matchers only (`toBeVisible`, `toBeEnabled`, a count above zero); a same-file helper that asserts counts. A change to screen text can break a spec that asserts the old words: `scripts/e2e-specs-for-strings.py [base]` lists the specs that contain a catalog value or fallback text the branch changed (and "1 <word>" for a count before a word).
