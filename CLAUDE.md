# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This repo is **Kubeast** — a Kubernetes operations platform combining a natural-language AI assistant with a rich multi-cluster dashboard. It is a polyglot microservice system (Go + Python + React) deployed to Kubernetes via Helm, with a kind-based local dev loop.

See [AGENTS.md](AGENTS.md) for the project-specific rules every contributor (human or AI) must follow — most importantly the **audit-log requirement** summarized below.

## Architecture

Requests enter through an NGINX **gateway** (`:8000`) that routes to backend services. Each service owns one concern and a slice of the data layer (Postgres for durable state, Redis for cache/session context).

| Service | Lang | Port | Module path / dir | Role |
| --- | --- | --- | --- | --- |
| `gateway` | NGINX | 8000 | `helm/kubeast/files/nginx.conf` | Routing, CORS, SSE/WebSocket proxy. No image build — ConfigMap only. |
| `auth-service` | Go | 8004 | `services/auth-service-go` | JWT issuance, JWKS, org/team/user hierarchy, RBAC |
| `ai-service` | Python/FastAPI | 8001 | `services/ai-service` | LLM integration, streaming chat, optimization suggestions, tool calling, the MCP server for external AI agents (`app/mcp_server.py`, `MCP_ENABLED`; `MCP_WRITE_TOOLS` adds the write tools for Write-ceiling keys). The provider SDK is imported when a model client is first made and the MCP SDK only with `MCP_ENABLED`. Chart `ai.enabled: false` leaves this service, `tool-server` and the ModelConfig controller out (`AI_ENABLED` tells k8s-service, which reports it in `/cluster/features`) |
| `k8s-service` | Go | 8002 | `services/k8s-service-go` | K8s resource CRUD, WebSocket logs/exec, topology, Helm, GPU/DRA |
| `session-service` | Go | 8003 | `services/session-service-go` | Chat session / message history |
| `tool-server` | Go | — | `services/tool-server` | Backend for AI tool calls |
| `model-config-controller-go` | Go | — | `services/model-config-controller-go` | controller-runtime operator for the `ModelConfig` CRD |
| `frontend` | React/Vite/TS | 5173 | `frontend` | UI |

**Target-cluster requirements**: Kubeast installs nothing on the clusters it manages (the node shell pod aside). Whatever a feature needs there — RBAC, metrics-server, a Prometheus Service and the metric names it queries, OpenCost, a CRD, a minimum server version, a label — is listed in [docs/cluster-requirements.md](docs/cluster-requirements.md) with how Kubeast finds it and how to check it; example values live in `deploy/examples/target-cluster/` and `scripts/render-target-rbac.sh` renders the RBAC a registered cluster needs. A change that makes a feature read something new from the target cluster updates that page in the same PR.

**Who a cluster request goes as**: with `auth.impersonation.enabled` on, k8s-service's cluster transport (`auth.ImpersonationRoundTripper`) sends a request as the person in its context and refuses one whose context names no one (`auth.ErrNoPerson`, nothing sent) unless it is marked `auth.AsKubeast` and is a GET of `/version`, `/api`, `/apis`, `/api/v1` or `/apis/<group>/<version>` under the path of the cluster's server URL (`kubeastOwnRead`, `ImpersonationRoundTripperAt`; anything else so marked is refused the same way) — the server version (`serverVersionInfo`, one read for everyone, at most 30 s old where a screen shows it), the discovery kept once per cluster for everyone (`apiResources`, `resolveCache`) and the health reads (`/health` reads `/version` once every 5 s for all its callers) — so a client-go call takes the caller's context (`discovery.ToDiscoveryInterfaceWithContext(…).…WithContext(ctx)`; the context-less discovery methods use `context.Background()`), a config whose callers send their own contexts pins its person (`UserRESTConfigFor`, `auth.WithPinnedPerson`), the reads made once for everyone as `kubeast:cache` go through `cacheClient`, which this transport is not on, and tool-server prepares no kubectl run without a person (`errNoPerson`); `TestEveryUserCallCarriesThePerson` holds the overview, the discovery reads, the cluster config, hygiene, a watch, a pinned config and the health reads to it, with and without a path on the server URL, and `TestKubeastOwnRequestsAreVersionAndDiscoveryReadsOnly` the paths and methods. client-go sends the cluster's credential and the person's headers again on every redirect it follows, and the API server passes on a Service's `Location` to another host unchanged, so a read of a Service through the API server proxy (Prometheus, OpenCost, the Hubble Relay, Whisker) follows a redirect only on the same API server and under that Service's proxy path (`internal/proxypath` `Follow`; in `internal/k8s` the reads go through `proxyClient` and `proxyGet`), and a flow source at an address follows none (`FollowNone`); a failed answer whose body is a Kubernetes `Status` is the API server's own (`proxypath.APIServerAnswer`) — at an address, where no API server is in between, every 401 or 403 is the flow source's own —, and a store's own 401 or 403, and the Relay's gRPC PermissionDenied or Unauthenticated, is a 502, not a sign-out or a refusal (`TestPrometheusProxyFollowsARedirectOnlyInsideItsServicePath`, `TestAStoresOwn401BehindTheProxyIsA502NotASignOut`, `TestAFlowSourcesOwn401Or403BehindTheProxyIsA502NotARefusal`, `TestEvery401Or403AtAnAddressIsTheRelaysOwn`).

Provider `claude-code` (a Claude subscription's setup-token, personal use, off by default, image build arg `WITH_CLAUDE_CODE`, released as the `<version>-claude-code` tag the chart runs when the provider is on) hands the model loop to Claude Code (`app/services/claude_code.py`); its tool calls come back to the same `_call_tool` in `app/services/ai/streaming.py`; the alert investigator's loop is `app/services/ai/tool_turn.py`, which has the same two branches. A chat answer keeps the order it came in: the text written before a tool call stays above that call's `<details>` block, on screen (`chatStreamManager`'s one `content`, the same in AI Chat and the floating chat) and in the saved message (`streaming.answer_markdown`, both paths); the history the next model call gets drops the tool blocks whole, arguments and results too (`ai_service.strip_tool_blocks`, and Copy `chatTextUtils.stripToolDetails`, held equal by `chatTextUtils.cases.json`: tags inside a code block do not count). `chatStreamManager` keeps where each tool block starts and where its result goes, so a result, the arguments or the answer holding a tool's name or the placeholder cannot take another call's result or 🔐 line. Each tool result carries `access`, the identity the call reached the cluster as (`services/pkg/auth.Access`, computed from the same `Impersonation` the request sends): tool-server returns it in its answer and k8s-service in the `X-Kubeast-Access` header (`ClusterMiddleware`); ai-service never works it out. The kubectl tools run kubectl against a loopback proxy in tool-server (`kubeproxy.go`, TLS with a boot-time certificate because client-go sends a token only over TLS, one token per run in a temporary kubeconfig whose context names `default` — as the direct path's kubeconfig does (`namespaceDefault`) — so a call naming no namespace works there and not in the pod's `POD_NAMESPACE`, a `/c/<cluster>` path so kubectl's discovery cache stays per cluster): it drops the identity kubectl sends and forwards with the cluster credential, the user's impersonation and an Audit-ID through the `kubectl proxy` parts (`UpgradeAwareHandler`, client-go transports), listing resource requests only; `TOOL_SERVER_KUBECTL_PROXY=false` keeps the direct `--as` path, and a proxy that fails to start refuses the kubectl tools with the reason (`kubectlProxyRefusal`) instead of going direct.

### Go module layout

Go services are **separate modules** (not a go.work workspace). Shared code lives in `services/pkg` (module `github.com/junginho0901/kubeast/services/pkg`) and is wired into each service via a `replace ... => ../pkg` directive in its `go.mod`. `services/pkg` provides:
- `audit/` — the shared audit-log API (see below)
- `auth/` — JWT verification (`jwt.go`)
- `dbmigrate/` — the database schema as versioned SQL migrations (goose, embedded). auth-service applies them at boot (`MIGRATIONS_MODE=startup`) or a chart hook Job does (`job`); every other service only waits for `dbmigrate.Required`. New schema changes go in a new `migrations/NNNNN_*.sql` file plus a `Required` bump (and ai-service's `REQUIRED_SCHEMA_VERSION` in `app/database.py`, which `tests/test_schema_wait.py` holds equal) — never in service start-up code. A migration that creates a table also adds it to `expectedTables` in `dbmigrate_postgres_test.go`; the `dbmigrate (postgres)` CI job compares the table list after `Up`. That job runs whole every package whose tests read `DBMIGRATE_TEST_DATABASE_URL` (`scripts/postgres-tests.sh`): a new test that needs PostgreSQL reads that variable and skips without it, and needs no CI change.
- `dbsession/` — the session limits every service SETs on its database connections once connected (`statement_timeout` 30 s, `lock_timeout` 15 s, `idle_in_transaction_session_timeout` 5 min, chart `postgresql.sessionLimits`; ai-service's `app/db_session.py` runs them in autocommit so a rollback does not undo them, `test_db_session_postgres.py`), and the migrations always set the first two to 0 whatever the values (`ApplyMigrations`, `TestPostgres_MigrationConnectionsLiftTheRolesLimits`). Each service's pool is `postgresql.pool.<svc>.maxConns`; a new service or pool, a lock-only connection too, is added to `kubeast.dbConnections`, whose sum `templates/checks/db-connections.yaml` holds under `postgresql.maxConnections` (`tests/db_connections_test.yaml`), and PgBouncer is for session pooling only.
- `config/`, `logger/`, `response/` — config loading, slog setup, HTTP response helpers; `config.SwitchOn`/`EnvSwitch` is the on/off rule of the v0.7.9 switches (true, 1, on, yes in any case), the same as ai-service's `app/services/switch.py`, both held to `ai-service/tests/fixtures/switch_cases.json`
- `probe/` — `/livez` and `/readyz` and the end of long-lived connections on SIGTERM for auth-service, k8s-service, session-service and tool-server
- `storeurl/` — the address rule for the metrics and log store URLs registered on a cluster, run when a URL is saved, before each request and when a name has resolved (`features.clusterStoreAllowedHosts`); through an environment proxy only the host as written is checked, since the proxy resolves the name. ai-service's `model_config_policy` reads an address's IPv6 forms the same way for a model's URL, and `app/services/model_http.py` holds each direct connection to a `base_url` to its rule on the addresses that connection will use (no `base_url`, the chart's `ai.baseUrl` with no stored config and a connection through an environment proxy are not held to it). `ai-service/tests/fixtures/address_forms_cases.json` gives each address both rules' answers, `store` and `model`, each `never`, `listed` or `open`, which `TestSharedAddressCases` and `test_shared_address_cases` run
- `netpol/` — the NetworkPolicy evaluator behind the drawers' "Network Policies" section, the check window and the AI tool `network_policy_check` (k8s-service `internal/k8s/netpol_check.go` reads the objects as the user). It depends on nothing beyond `k8s.io/api`; where the documentation leaves the behaviour to the network plugin (an `ipBlock` covering a pod IP, hostNetwork pods) it answers unknown. `services/netpol-oracle` is a test-only module, in the CI go matrix and in no image, that compares it with np-guard/netpol-analyzer on generated scenarios (`NETPOL_ORACLE_SCENARIOS`, `NETPOL_ORACLE_SEED` for longer runs)
- `clusternotice/` — the channel and message of k8s-service's cluster change notices on Redis, which tool-server listens to
- `redisacl/` — reads the chart's Redis users for the services' tests (below)

Each service signs in to the chart's Redis as its own user, which may run only the commands its code sends, on keys and channels under `kubeast:` (`kubeast.redisUsersAcl` in `helm/kubeast/templates/_helpers.tpl`, `redis.acl`). A service that starts to send a new Redis command adds it to its user's line there, with a case in `tests/redis_test.yaml`: otherwise an install with Redis ACL refuses it (NOPERM) and the cache reads empty without an error. Tests hold what each service sends to its line through `services/pkg/redisacl`: k8s-service's `internal/cache` runs every exported method of `Cache` once against a stand-in that records the commands (`TestTheCachesRedisCommandsAreThoseItsChartUserMayRun`, which also fails on a method it does not run), and the cluster change notices are held the same way, k8s-service's publishing and listening (`internal/clustersync`, `TestTheNoticesRedisCommandsAreThoseItsChartUserMayRun`) and tool-server's listening (`TestClusterNoticesDropTheirClusterAndSendNothingElse`); a new place that sends Redis commands gets such a test. `internal/callgraph` is the AI tool `resource_graph`'s `include=calls` (`features.callGraph`, off by default, `CALL_GRAPH_ENABLED`; `/namespaces/{namespace}/resource-graph?include=calls&range=`, or a fixed `start`/`end` read at its end — `callWindowOf`, the tool's `since_time`/`until_time`): the traces' service graph metrics (`traces_service_graph_request_total`, `_failed_total`, `_server_seconds_bucket` — Tempo's metrics-generator or a `servicegraph` connector) and the traffic lines' Hubble metrics (`trafficFromMetrics`, shared with `/networktraffic`), both from the cluster's Prometheus as the user, placed on the graph's boxes (the namespace and workload dimensions, else a workload's name, else a Service's selector), at most 100 edges; the trace source is left out for a grant limited to namespaces (`namespace_limited`, as `promClusterWide`) and the Hubble one without `resource.networkflow.read` (`permission`), each source saying why in `calls.sources`; `Suspects` puts the failing workloads that call nothing failing first (10 kept, `suspects_total`; `failing_outside` names a suspect's failing calls to ends outside the graph) and draws the cause → … → symptom paths (`no_start: cycle` when each failing workload calls another); an end placed by name where the metric names no namespace has a `matched_by` ending in `_unscoped`, the name-only path's p90 query is a `topk` of 500 like the other two (an edge whose series is outside the failed `topk` has `errors` and `error_ratio` null, never 0 — `Edge.ErrorsUnknown`, `Suspects` counting only the failed calls read — and a `topk` that comes back with 500 series above 0 marks the trace source `truncated`, and `calls` too when it is the requests one, `Traces.Cut`), and an edge carries the traffic lines' drop reasons (`drop_reasons`); tool-server keeps 40 edges with the paths and suspects first, ai-service offers `include`/`since` only where `/cluster/features` says `callGraph.enabled` (`features.PARAM_GATES`), the MCP server's read tools only with `CALL_GRAPH_ENABLED` (`tools.offer_call_graph`), and the investigation prompt adds the path rule with the same switch (`settings.call_paths`; with `rules` on only when to read the calls, the rules' Likely cause chain being the one path instruction); `anomaly_rank` reads the same graph over its own window to put a suspect's findings before its victims' (`call_order`, `anomaly.AssembleWith`), its Prometheus reads taken from the narrowing's query budget, three of it kept for them from `maxQueries` 12 up (`callOrderShare`, `budgetedSource`). `internal/nodecpu` is `GET /nodes/{name}/neighbors` (`features.nodeNeighbors`, off by default, `NODE_NEIGHBORS_ENABLED`, 404 without it), the AI tool `get_node_metrics` with `node`: what used a node's CPU in a window against the one before it, at most six reads of the metrics store and the metrics API (`nodecpu.MaxQueries`), the node and its pods read as the caller, a namespace whose pods they may not list counted and not named, an answer whose reads all succeeded kept a minute per caller in the pod (`nodeAnswers`); ai-service offers `node`, `since_time` and `until_time` only where `/cluster/features` says `nodeNeighbors.enabled` (`features.PARAM_GATES`), the MCP server's read tools only with `NODE_NEIGHBORS_ENABLED` (`tools.offer_node_neighbors`), dispatch drops them without it, and with the same switch the chat's prompt and that of the investigation of an alert without a namespace say when to read it (the token of one with a namespace is limited to it, and the tool spans the cluster).

A Go service follows a `cmd/server/main.go` → `internal/routes` (route registration) → `internal/handler` (one file per resource kind, e.g. `pods.go`, `deployments.go`, `helm*.go`) → `internal/k8s` (client logic) layering. A k8s-service route with no `{namespace}` in its path is refused to a grant limited to namespaces until it has a rule in `internal/handler/namespace_scope_routes.go`; `TestNamespaceRouteTable` holds every route to its rule. The same middleware holds everyone to the two namespaces of `services/pkg/protectedns`, the one rule k8s-service and tool-server share: on the cluster Kubeast runs in (`InCluster`/`IsSelfCluster`, or a kubeconfig whose `kube-system` UID is that cluster's; while either UID cannot be read the namespace of that name is guarded there and the read is asked again on a later use, at most every 10 s — `installRecheck`) its `POD_NAMESPACE` is for global admins (`*`) as far as Secrets, Helm releases, writes and terminals go, and on any cluster `NODE_SHELL_NAMESPACE` takes writes, terminals and pod logs (a node shell's log is its screen) only from holders of `resource.node.shell`. Other reads stay. A read of the log store with no namespace leaves the node shell's namespace out with a matcher in its query unless the caller holds `resource.node.shell` on that cluster (`hiddenLogNamespace`; search, LogQL, labels and patterns, `TestAReaderAcrossNamespacesGetsNoNodeShellLines`): a search says so as `hiddenNamespace` in its answer and `hidden_namespace` in its row, and LogQL shows it in `effectiveQuery`. A terminal, a followed log and a live list stay open past their token and end when the session behind them stops standing (`auth.LiveSessions`, read from the shared database by `internal/sessioncheck`, close code 4401 or the event `session-ended`, and close code 1013 (`auth.SessionEndCloseCode`) when the session could not be read for `StaleTTL`, which the page connects again from; each is checked when it opens and every 30 s after by one ticker that walks them all, `sweep`, not by a goroutine of its own). ## Audit logging — mandatory (read before touching any Go handler)

> Authoritative rules: [AGENTS.md](AGENTS.md) and [docs/audit-log-plan.md](docs/audit-log-plan.md). PRs that add/modify a write-class HTTP handler **without** an audit call are rejected.

Every **write-class HTTP handler** (create/update/delete/rollback/restart/…) and every **sensitive read** (Secret reveal, Node shell, Pod logs sensitive access, container log files, Cronjob trigger, session recording read, audit-log read itself) MUST record an audit entry via `services/pkg/audit`.

Code that runs commands in a container through `pods/exec` must use short commands that end on their own: a process started through exec keeps running in the container after the client disconnects (TTY or not). Pass an argv array, never a shell — see AGENTS.md "컨테이너 exec". Plain list/get reads and health/public endpoints are excluded.

- **Action names are strict**: `<domain>.<object>.<verb>` (e.g. `k8s.pod.delete`, `helm.release.rollback`, `ai.tool.execute`, `admin.audit.read`). New actions must be added to the catalog in `docs/audit-log-plan.md §5-2` **first** (update the plan doc before the code).
- **Record both success and failure** — on failure set `rec.Result = audit.ResultFailure` and fill `rec.Error`.
- **A database that can take the row is a precondition for sensitive actions; only the stdout mirror is best-effort** (fail-closed: while the store cannot take a row, an action is refused before it runs; a row whose write fails after the action ran is counted and logged, and the response stands). Writes and sensitive reads are refused with 503 `audit unavailable` (`AUDIT_FAIL_CLOSED`, default true; chart `audit.failClosed`) — mutation routes through the `audit.RequireWritable` middleware, conditionally-audited GET handlers via `h.auditReady(r)` before the action plus the `recordAudit*` return value (`h.refuseUnaudited`). `audit.Guarded` counts that failure and logs it; from then on readiness probes a write (inserted and rolled back) until the audit table takes rows again — a ping alone misses a database that answers while that table refuses rows. `audit.Guarded.Write` writes with the caller's context values and deadline but not its cancellation: once the caller has left, the write goes on at most `audit.WriteGrace` (5 s), counted from the write's start or the caller's cancellation, whichever comes last, so a browser that closes after the mutation ran (net/http then cancels the request's context) does not take the row with it, and while the caller is there the write waits as before; pass the request's context as it is. auth-service refuses admin writes only (sign-in, sign-out, token refresh and one's own password change go on); the AI chat's tools and alert investigations check before they read the cluster. A read tool whose row could not be stored gives no answer, in the chat, over MCP and in an investigation (`audit_unavailable`, `test_audit_after_read.py`); a write that ran keeps its own. The model connection test and the provider model list, which spend the server's key, answer 503 before they start (`model_config_audit.ready_or_503`). Services wait for the database at boot and exit if it does not come — there is no log-only fallback: k8s-service up to `AUDIT_DB_WAIT_SEC` (90 s) for the database and the schema, auth-service and session-service up to 60 s for the database (`audit.WaitReady`: 5 s a ping, since pgxpool gives a connect two minutes; the wait ends with its context, auth-service's on SIGTERM) and then 60 s for the schema (a hung version read ends 5 s later). The chart gives these three a 180 s startup probe (`kubeast.startupProbe`) so liveness does not cut that wait; a longer boot wait changes it too.
- Mask sensitive fields (password/secret/token/apikey) with `audit.MaskSensitive(...)` before storing in `Before`/`After`. It does not read inside a string, so YAML or JSON text stays out of the row: record its length or a summary (`yaml_len`, `helmValuesAudit`).
- Every new `docs/*-plan.md` must include a `## N. 감사 로그` section (record-target actions + permission/audit-action mapping table).

The handler pattern is documented in [AGENTS.md](AGENTS.md); use `audit.FromHTTPRequest(r)` to seed a record, then set `Service` (`audit.ServiceK8s` / `ServiceHelm` / `ServiceAI` / `ServiceAuth` / `ServiceAdmin`), `Action`, actor, target, and write via the handler's `auditStore`.

Text a cluster wrote reaches the model only as a tool result, in both loops of the chat and of the investigator, the investigator's step 0 reads included (`tool_turn.server_calls`); `ai.toolResultsJSON` makes each one JSON object (`app/services/ai/tool_results.py`), and the places that are not a tool result — an investigation's alert, its step 0 answers on a Claude subscription and the floating chat's screen, fenced, the tool results in the request of the call that closes an investigation or a chat answer on a Claude subscription (`tool_turn.tool_results_text`), and an approved write's result, an assistant message the history reads — are named in docs/ai-alerts.md "Planted instructions" and held by `tests/test_tool_results_json.py`; the MCP server hands answers to an external agent as they are. A change to the prompts, the tools or the loops runs the planted-instruction cases (`evals/ai-planted/`, scored by `scripts/ai_eval_planted.py`; the alert investigation's, `evals/ai-planted-alerts/`, by `scripts/ai_eval_planted_alerts.py`) for each model.

```bash
scripts/rebuild-kind.sh --tag dev k8s-service   # custom image tag
scripts/rebuild-kind.sh gateway                 # nginx.conf only: helm upgrade with the release's values, no image
```

Chart-managed objects are changed through the chart (`helm upgrade`), never with `kubectl apply`: Helm 4 applies server-side, so a field kubectl took over makes the next upgrade stop on a conflict.

The script resolves KUBECONFIG in priority order: `$KUBECONFIG_PATH` → single-file `$KUBECONFIG` → repo-local `.kubeconfig-kind` → `/tmp/kubeast-kubeconfig`. Note: the auth/k8s/session Go services share build context `services/` with explicit Dockerfiles (`<svc>-go/Dockerfile`).

Install paths, all from the one chart: `helm/kubeast` (Helm; users install the released OCI chart `oci://ghcr.io/junginho0901/charts/kubeast`, whose image tags the release sets — the chart in a checkout keeps a placeholder tag), `install.sh` (one-liner for an existing cluster; installs that OCI chart at the release version `kubeast` in `deploy/dependencies.yaml`, which the release workflow requires to equal the tag), `scripts/kind-deploy.sh` (local kind), `install-docker.sh` + `docker-compose.yml` (single-host, no cluster; the release workflow starts it on the run's images and signs in before tagging — `scripts/compose-smoke.sh`, also runnable locally with a digests dir or `--build`). There is no separate copy of the manifests. `helm upgrade --reuse-values` renders the chart on the values of the release it upgrades, without the defaults later versions added: `templates/checks/upgrade-values.yaml` (rendered first, as the deepest path) stops it with the `--reset-then-reuse-values` hint, and `scripts/chart-upgrade-values.sh` (CI) renders every release's values.yaml both ways — a new values path that changes the output goes into that check. A values path the last release has and this chart has not goes into `templates/checks/removed-values.yaml` with what to set instead, which stops a render that still sets it (`scripts/chart-removed-values.sh`, CI). A published chart's defaults also hold its release's image tags, which a checkout's values.yaml does not, so that render cannot see them: the release writes the chart version into the defaults as `chartVersion` (empty in a checkout), and the check stops values without it or holding another version — `--reuse-values` from an earlier release or a values file copied from one — whether or not that release added a path (`tests/upgrade_values_test.yaml`). A file copied from 0.7.6 or earlier holds no `chartVersion` and takes the new chart's, so a published chart also stops a `global.imageTag` of another release (`vX.Y.Z`, with or without its digest; a tag of an image built by hand goes on), and the script passes each release's values file, as the release wrote it, with `-f` to the chart as the release would publish it; `docs/getting-started.md` "Upgrade" says so. `helm/kubeast/values-minimal.yaml` is the smallest install (no AI, no Redis — k8s-service caches in memory when `REDIS_HOST` is empty — six pods, requests from measurement); the footprint table in `docs/architecture.md` comes from `scripts/kind-footprint.sh` (a kind cluster of its own, `crictl` working set and CPU once a minute) — rerun it and update the table when a change adds a pod or a background job.

Docs: a pull request that changes `docs/X.md` changes `docs/ko/X.md` too (`README.md` and `README.ko.md` alike), and a values path it adds to `helm/kubeast/values.yaml` is named in `docs/configuration.md` and `docs/ko/configuration.md`; CI (`scripts/check-docs-pair.sh`) fails otherwise, unless a commit of the pull request says why in a trailer, in the last paragraph of its message with `Co-Authored-By`: `Docs-Pair: en-only [<file>...] <reason>` (or `ko-only`; `values-not-in-docs [<path>...] <reason>`), which covers the files or values paths it names, or the whole pull request when it names none.

More than one replica of a service is supported ([docs/high-availability.md](docs/high-availability.md)), so work only one pod may do — a periodic job, a queue — takes turns through the database, never through process memory: a Postgres advisory lock held while the work runs (`pg_try_advisory_lock`) or for one transaction (`pg_try_advisory_xact_lock`, `internal/auditchain`), or rows taken with `FOR UPDATE SKIP LOCKED` (the access-request and dormant-account sweepers, ai-service's alert investigation queue); a pod that does not get the lock leaves that turn to the one that did. A lock held while the work runs goes on a connection of its own outside the pool, made with the pool's settings (auth-service `internal/retention`, k8s-service `internal/pglock`) and counted once per pod in `kubeast.dbConnections`; one kept on a pool connection (auth-service's audit sinks, `internal/auditsink`) takes one of the pool's for as long as it is held, so a pool of one (two beside another such lock) has none left for the work's own statements or the requests. Caps, caches and counters kept in a process are per pod, so the install's total is that times the replicas; what must hold for the whole install lives in the database or Redis. A change that adds such work or state says in docs/high-availability.md (en, ko) what a pod keeps.

## E2E tests (Playwright)

`e2e/` runs **against the live kind cluster's gateway**, not a dev server. Tests are serialized (`workers: 1`, `fullyParallel: false`) because they mutate shared single-cluster K8s state. Many specs are **visual-regression baselines** — snapshots captured on `main` must match pixel-for-pixel (within `maxDiffPixels: 100`) on feature branches. `E2E_AI_LAYERS=1 npx playwright test --project=ai-layers` (opt-in; one worker, about 30–35 minutes when every state passes and 45–90 minutes on a first run, `E2E_AI_LAYERS_ONLY=<regular expression>` runs the screens whose sidebar address it matches) opens every screen of the sidebar config (`navGroups` in `Layout.tsx`, read by `e2e/tests/ai-layer-screens.ts`, which the default run's "every menu" test in `floating-context.spec.ts` reads too; a screen that sends nothing by rule is in `e2e/tests/ai-layer-exempt.json` with a reason and a PR, and Advanced Search is opened with a search typed, `prepareScreen`) with its reads answered in the browser as the cluster's answer, a failed Refresh, 403, 500, a kind not served (only the lists k8s-service's `ListIfServed` answers so, `NOT_SERVED_LISTS`; a screen that reads none of them skips it) and an empty list, the Dashboard's Services window also in 403 and 500, and fails when a notice on the screen (the shared ones and each screen's own, `NOTICES`) has no layer of the same meaning in what the floating chat is sent (refused, failed with the reason, not served, zero items) or a layer states a count the screen does not show; Monitoring's "Metrics server not available for this cluster", which cluster `default` never shows, is held with its metrics reads answered as not served (a 404), on the Nodes tab and on the Pods tab before a namespace is chosen.

It holds that every read answers 2xx within 3 s, that each closed list socket gets a frame again within 5 s and the boxes show each pod once as kubectl lists them, that the Logs tab shows each line once as `kubectl logs` prints it, that the terminal of the leaving k8s-service ends with the server's line, close 1001 `server_shutdown` and a `k8s.session.end` row, that a fresh terminal answers after each rollout, and that each old pod is gone within its grace period (the preStop wait and the shutdown's 30 s) with no container killed, timed by a `kubectl get --watch`. A check the build lacks is skipped with the reason (no preStop wait, readiness not on `/readyz`, no `worker_shutdown_timeout` in the gateway's nginx.conf, terminals on `k8s-service-stream`). The measurements are attached as `rollout-in-use.json`. Its pod is removed after; the Deployments keep the `restartedAt` annotation `kubectl rollout restart` writes.

`e2e/actions/` is an **opt-in** action suite (94 catalogued UI actions — deletes of every kind, a Node and a VolumeAttachment made for their delete among them, YAML edits, rollbacks, Helm, nodes, admin pages including access requests — each verified with `kubectl` against a seeded second kind cluster). It is not in the default run: `E2E_ACTIONS=1 npx playwright test --project=actions` (≈ 12 min + seed). Prerequisites and the per-test contract are in [e2e/actions/README.md](e2e/actions/README.md).

`e2e/guard/` holds the opt-in safety nets, not in the default run: `E2E_GUARD=1 npx playwright test --project=guard` runs `permission-matrix.spec.ts`, where an Admin, a Write and a Read user on `self` and a Read user limited to one namespace open every sidebar screen, `/account` and a drawer of every kind, and what each is shown is compared with `kubectl auth can-i` as the identity in `X-Kubeast-Access` (the admin pages with the user's Kubeast role); each user's cells are attached as JSON. Each summary screen has a rule for the limited user (`limited` in the table: narrowed to its namespaces and naming what the cluster refuses beyond them, or closed with why; a list beyond them that the cluster does not serve, metrics.k8s.io without metrics-server, is refused to no one and every user is shown it is not available), and no other namespace's name may be on any screen. The same users then do the same on `test2` for the Gateway API's six lists and drawers and the VPA's, with objects of the run and a Role opening them in the one namespace; it skips without `test2`. With the build to compare with running beside the install (`scripts/before-stack.sh up <tag>`, `-before` Deployments with the same Secrets, ConfigMap and database and the tag's chart's probes (`check <tag>` prints them without a cluster), `hostAliases` keeping them talking to each other, the gateway on `:30081`; `up local` compares the install with itself, `down` before any other run) and `E2E_BEFORE_URL=http://localhost:30081`, the same project runs `response-diff.spec.ts`: those users and a global admin (also on `default` and `test2`) open every screen and drawer, and every GET and first live answer they caused is asked of old, new and old again. `response-compare.ts` flattens the answers into cells, rows paired by name (an event by its object, reason and message, a catalog's group with no name by its `category`, a discovery list by its `groupVersion`, a name seen twice as its first and second): old differing from old is noise, old agreeing with itself and differing from new is a real difference, which fails unless `response-diff-ignore.json` names it with a reason and a PR — the list holds what changed since v0.7.9, the last release, and is emptied of those when the next one is out (the rules naming each build's own values stay), and a rule may be for one user's answers or one cluster's (`cluster`: a GET's `cluster` parameter, a live request's cluster id); a rule whose cells take in `$status` names the status the new build answers (`newStatus`), so a server error of a route the old build lacked is never a known difference; a rule with `rowsLeftOut` takes its cells only from a new answer that is each old answer's list with some rows left out (every row it keeps the same, in the same order), one with `tailCopies` only the cells of a name's later rows that one side holds past the other's last, while all three answers hold that name's first row, and one with `addedRow` only the cells of the row of that name, which neither old answer has, and the count and the order of the list it is in while the old list is the new one without that row. Writes, AI answers, terminals and followed logs are not replayed; system roles come from one database, so a change to their seed shows in the matrix, not here. `E2E_DIFF_OUT` keeps the table and the cells in a directory. With `E2E_SCREEN_DIFF=1` as well it runs `screen-diff.spec.ts` instead: every sidebar screen, `/account` and a drawer of every kind on `self` in each colour mode, and the sidebar on `default` and `test2`, opened on both builds at once with the clock fixed and compared picture by picture (`screen-compare.ts`, in a browser page, no dependency). A few faint pixels are a redraw; old differing from itself is noise; what still differs a minute later fails unless `screen-diff-intended.json` names the screen with a reason and a PR; a rule there with `within` (a CSS selector) covers that element in both pictures and leaves the rest of the screen compared, one without it takes the whole screen. `screen-diff-masks.json` covers a value that moves by itself, with why; `E2E_SCREEN_ONLY=<regular expression>` looks at some screens again. `screen-diff-intended.json` holds the changes since the build compared with and is emptied of them when that build holds them. With `E2E_A11Y=1` the project runs `a11y.spec.ts` alone: the same screens and drawers on `self` in each colour mode at 1440×900, axe-core with the tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa` and `wcag22aa` (its `target-size` counted, not judged: it reads the element's box, not the `::after` hit area) and each control's size to press read with `elementFromPoint` (24×24 CSS px with WCAG 2.5.8's spacing and inline exceptions; Close, Back and the floating chat's controls under DESIGN.md's 40 are listed and never fail); a finding `a11y-baseline.json` does not hold fails unless `a11y-exempt.json` names it with why, `E2E_A11Y_WRITE=1` writes the baseline, `E2E_A11Y_HITS_ZERO=1` fails on any 24×24 finding not exempt, `E2E_A11Y_ONLY=<regular expression>` narrows the screens, and without a baseline it only reports. `E2E_A11Y_VIEWS=1` runs the three accessibility views instead (`a11y-views.ts`: ten main screens and two drawers in the default mode): `aria-tree.spec.ts` compares each screen's accessibility tree cut down to its landmarks, headings, controls and column headers, line by line, with `aria-tree-baseline.json` (or, with `E2E_BEFORE_URL`, with the old build at the same moment), `reduced-motion.spec.ts` fails on an animation running under `reducedMotion: 'reduce'` or a picture at rest that differs from the one without it, and `forced-colors.spec.ts` on a keyboard focus with no outline or a mark drawn by its fill alone under `forcedColors: 'active'`; each has a baseline written at the v0.7.9 tag with `E2E_A11Y_VIEWS_WRITE=1` that a later build may only shrink, `a11y-views-intended.json` names a difference a PR means with why and the PR, and `E2E_A11Y_VIEWS_OUT` keeps the tables and the pictures.

`e2e/fault/` holds the opt-in fault tests of v0.7.8 (step 4 §5), not in the default run: `E2E_FAULT=1 npx playwright test --project=fault`. Each file belongs to a pull request of W4 or W5 — `pod-shutdown` (rollouts with requests in flight), `cluster-versions` (a cluster change reaching every k8s-service replica within 10 s, also with Redis stopped), `drain-in-db` (a drain read on another server, its server killed mid-drain — also with no SIGTERM, `crictl stop --timeout 0` on the kind node, while it holds a terminal and a page's live list — PostgreSQL off 60 s and frozen 20 s and 30 s with `ctr task pause`, other seconds with `E2E_FAULT_FREEZE_SECONDS`), `claude-code-slots` (the install-wide cap across ai-service replicas, a stale slot taken at 60 s), `redis-users` (each Redis user refused what it does not send, tool-server's 10 s, Redis off 60 s) and `w4-stream-split` (the stream server or the api server killed), with `force-kill` for step 4 F-5 and F-14 (one of two k8s-service pods, the gateway with one and two pods) — and holds its pass line to kubectl, the database or the API, reaching one server through `kubectl port-forward pod/…` where it matters. They kill pods and stop Redis or PostgreSQL on the dev install, put back what they changed — registered with `atExit` as they change it (a Deployment scaled to 0, a frozen container, a cordon on test2), since an interrupted test's `finally` does not run: each file's `afterEach`, the worker's exit and SIGINT/SIGTERM/SIGHUP run the list, and for a worker killed outright a detached process scales back and puts test2 back once it is gone, or resumes a frozen container 30 s after its time — and skip with the reason when a prerequisite (two replicas, Redis users, `streams.enabled`, the kind clusters `kubeast-b` and `test2`) is missing. While a `Probe` sends, kubectl goes through `kubectlAsync` and its `…Async` helpers (`takeDown` and `stopFor` too): the synchronous `kubectl()` holds the worker's event loop, so the probe would send nothing meanwhile and time the request it had started with the whole wait; `expectProbeKeptSending` holds it to a request at least every `SEND_GAP_MS` (2 s). `scripts/kind-fault-shape.sh` switches the dev install between the shapes they run in (`s1` one pod each, `s2` two k8s-service, ai-service and tool-server pods, `s2-gateway`, `s3` streams) and `back`, with `--history-max 0`, a server render first and the values' hashes before and after, starting only when this checkout's chart renders what is installed, refusing to switch or roll back when something else upgraded the release after the start or the noted revision is gone, and to switch or run `back-values` (which puts the start's values back from a 0600 copy) when this checkout's chart files differ from the start's; prerequisites, pass lines, how each fault was checked, what a run leaves and cleanup after a cut run are in [e2e/fault/README.md](e2e/fault/README.md).

`e2e/fault/node-shell-cleanup.spec.ts` holds threat model row 1.9 (`node_shells`): the node shell pod of a server killed with no SIGTERM goes within 150 s and not before 40 s with one `server_gone` row (NS-1), the shells of the server that stays keep their pods, sockets and rows (NS-2), PostgreSQL frozen 20 s closes no shell (NS-3a), and stopped 60 s has each shell's own server close it as `heartbeat_lost` (NS-3b); it skips with the reason without `nodeShell.enabled`, `node_shells` or a PostgreSQL it may freeze or stop, and deletes only the pods it made.
