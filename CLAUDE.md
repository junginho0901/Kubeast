# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This repo is **Kubeast** — a Kubernetes operations platform combining a natural-language AI assistant with a rich multi-cluster dashboard. It is a polyglot microservice system (Go + Python + React) deployed to Kubernetes via Helm, with a kind-based local dev loop.

See [AGENTS.md](AGENTS.md) for the project-specific rules every contributor (human or AI) must follow — most importantly the **audit-log requirement** summarized below.

## Architecture

Requests enter through an NGINX **gateway** (`:8000`) that routes to backend services. Each service owns one concern and a slice of the data layer (Postgres for durable state, Redis for cache/session context).

| Service | Lang | Port | Module path / dir | Role |
| --- | --- | --- | --- | --- |
| `gateway` | NGINX | 8000 | `helm/kubeast/files/nginx.conf` | Routing, CORS, SSE/WebSocket proxy. No image build — ConfigMap only. |
| `auth-service` | Go | 8004 | `services/auth-service-go` | JWT issuance, JWKS, org/team/user hierarchy, RBAC |
| `ai-service` | Python/FastAPI | 8001 | `services/ai-service` | LLM integration, streaming chat, optimization suggestions, tool calling, the MCP server for external AI agents (`app/mcp_server.py`, `MCP_ENABLED`; `MCP_WRITE_TOOLS` adds the write tools for Write-ceiling keys). The provider SDK is imported when a model client is first made and the MCP SDK only with `MCP_ENABLED`. Chart `ai.enabled: false` leaves this service, `tool-server` and the ModelConfig controller out (`AI_ENABLED` tells k8s-service, which reports it in `/cluster/features`) |
| `k8s-service` | Go | 8002 | `services/k8s-service-go` | K8s resource CRUD, WebSocket logs/exec, topology, Helm, GPU/DRA |
| `session-service` | Go | 8003 | `services/session-service-go` | Chat session / message history |
| `tool-server` | Go | — | `services/tool-server` | Backend for AI tool calls |
| `model-config-controller-go` | Go | — | `services/model-config-controller-go` | controller-runtime operator for the `ModelConfig` CRD |
| `frontend` | React/Vite/TS | 5173 | `frontend` | UI |

**Target-cluster requirements**: Kubeast installs nothing on the clusters it manages (the node shell pod aside). Whatever a feature needs there — RBAC, metrics-server, a Prometheus Service and the metric names it queries, OpenCost, a CRD, a minimum server version, a label — is listed in [docs/cluster-requirements.md](docs/cluster-requirements.md) with how Kubeast finds it and how to check it; example values live in `deploy/examples/target-cluster/` and `scripts/render-target-rbac.sh` renders the RBAC a registered cluster needs. A change that makes a feature read something new from the target cluster updates that page in the same PR.

**AI tool-calling flow**: `ai-service` (chat orchestration, provider adapters for OpenAI/Anthropic/Gemini; Azure OpenAI is its v1 API through the OpenAI-compatible client — base URL `…/openai/v1/` required, the deployment name as the model, the key as Bearer and `api-key`, deployment URLs and `api-version` refused in `model_config_policy`, and the connection test goes through the same `ProviderAdapter` as the chat) dispatches whitelisted tools (`app/services/tool_whitelists.py`) to `tool-server`, which calls the K8s API. Tool results stream back to the chat. Provider `claude-code` (a Claude subscription's setup-token, personal use, off by default, image build arg `WITH_CLAUDE_CODE`, released as the `<version>-claude-code` tag the chart runs when the provider is on) hands the model loop to Claude Code (`app/services/claude_code.py`); its tool calls come back to the same `_call_tool` in `app/services/ai/streaming.py`; the alert investigator's loop is `app/services/ai/tool_turn.py`, which has the same two branches. A chat answer keeps the order it came in: the text written before a tool call stays above that call's `<details>` block, on screen (`chatStreamManager`'s one `content`, the same in AI Chat and the floating chat) and in the saved message (`streaming.answer_markdown`, both paths); the history the next model call gets drops the tool blocks whole, arguments and results too (`ai_service.strip_tool_blocks`). Each tool result carries `access`, the identity the call reached the cluster as (`services/pkg/auth.Access`, computed from the same `Impersonation` the request sends): tool-server returns it in its answer and k8s-service in the `X-Kubeast-Access` header (`ClusterMiddleware`); ai-service never works it out. It is the 🔐 line under the tool block's name — `frontend/src/services/toolAccess.ts` while the answer streams, `app/services/ai/access.py` in the saved answer, the same text — and `after.access` of the call's audit row. Under it, "🧾 Cluster requests" lists the Kubernetes requests the call made (`after.requests`, `services/pkg/accesstrail`): a caller that sends `X-Kubeast-Record` (ai-service's k8s-service client, tool-server's `doTraced`) gets them from k8s-service in `X-Kubeast-Requests`, set when the handler starts its answer; the cluster transport (`accesstrail/kube`) sends each with a fresh `Audit-ID` and reads it with the API server's `RequestInfoFactory`, and a hit in k8s-service's cache or overview informers is listed as `source: cache`. The kubectl tools run kubectl against a loopback proxy in tool-server (`kubeproxy.go`, TLS with a boot-time certificate because client-go sends a token only over TLS, one token per run in a temporary kubeconfig, a `/c/<cluster>` path so kubectl's discovery cache stays per cluster): it drops the identity kubectl sends and forwards with the cluster credential, the user's impersonation and an Audit-ID through the `kubectl proxy` parts (`UpgradeAwareHandler`, client-go transports), listing resource requests only; `TOOL_SERVER_KUBECTL_PROXY=false` keeps the direct `--as` path.

### Go module layout

Go services are **separate modules** (not a go.work workspace). Shared code lives in `services/pkg` (module `github.com/junginho0901/kubeast/services/pkg`) and is wired into each service via a `replace ... => ../pkg` directive in its `go.mod`. `services/pkg` provides:
- `audit/` — the shared audit-log API (see below)
- `auth/` — JWT verification (`jwt.go`)
- `dbmigrate/` — the database schema as versioned SQL migrations (goose, embedded). auth-service applies them at boot (`MIGRATIONS_MODE=startup`) or a chart hook Job does (`job`); every other service only waits for `dbmigrate.Required`. New schema changes go in a new `migrations/NNNNN_*.sql` file plus a `Required` bump (and ai-service's `REQUIRED_SCHEMA_VERSION` in `app/database.py`, which `tests/test_schema_wait.py` holds equal) — never in service start-up code. A migration that creates a table also adds it to `expectedTables` in `dbmigrate_postgres_test.go`; the `dbmigrate (postgres)` CI job compares the table list after `Up`.
- `config/`, `logger/`, `response/` — config loading, slog setup, HTTP response helpers
- `netpol/` — the NetworkPolicy evaluator behind the drawers' "Network Policies" section, the check window and the AI tool `network_policy_check` (k8s-service `internal/k8s/netpol_check.go` reads the objects as the user). It depends on nothing beyond `k8s.io/api`; where the documentation leaves the behaviour to the network plugin (an `ipBlock` covering a pod IP, hostNetwork pods) it answers unknown. `services/netpol-oracle` is a test-only module, in the CI go matrix and in no image, that compares it with np-guard/netpol-analyzer on generated scenarios (`NETPOL_ORACLE_SCENARIOS`, `NETPOL_ORACLE_SEED` for longer runs)

A Go service follows a `cmd/server/main.go` → `internal/routes` (route registration) → `internal/handler` (one file per resource kind, e.g. `pods.go`, `deployments.go`, `helm*.go`) → `internal/k8s` (client logic) layering. The `k8s-service` also has `internal/ws` (WebSocket logs/exec), `internal/helm`, `internal/cache`, and `internal/netflows` — the Hubble Relay client behind the drawers' "Recent Flows" and the AI tool `network_flows` (`features.networkFlows`): `observer.Observer/GetFlows` as gRPC over HTTP/2 written by hand with `protowire` (no Cilium or grpc module), sent through the API server's service proxy as the user (`proxy`, needs Relay TLS) or to a TLS address; `wire_test.go` decodes bytes recorded from a real Relay (`testdata/`), and `dropreasons.go` copies the drop reason names of Cilium's `flow.proto`.

## Audit logging — mandatory (read before touching any Go handler)

> Authoritative rules: [AGENTS.md](AGENTS.md) and [docs/audit-log-plan.md](docs/audit-log-plan.md). PRs that add/modify a write-class HTTP handler **without** an audit call are rejected.

Every **write-class HTTP handler** (create/update/delete/rollback/restart/…) and every **sensitive read** (Secret reveal, Node shell, Pod logs sensitive access, container log files, Cronjob trigger, session recording read, audit-log read itself) MUST record an audit entry via `services/pkg/audit`.

Code that runs commands in a container through `pods/exec` must use short commands that end on their own: a process started through exec keeps running in the container after the client disconnects (TTY or not). Pass an argv array, never a shell — see AGENTS.md "컨테이너 exec". Plain list/get reads and health/public endpoints are excluded.

- **Action names are strict**: `<domain>.<object>.<verb>` (e.g. `k8s.pod.delete`, `helm.release.rollback`, `ai.tool.execute`, `admin.audit.read`). New actions must be added to the catalog in `docs/audit-log-plan.md §5-2` **first** (update the plan doc before the code).
- **Record both success and failure** — on failure set `rec.Result = audit.ResultFailure` and fill `rec.Error`.
- The **database row is a precondition for sensitive actions; only the stdout mirror is best-effort.** While the audit store cannot take a row, writes and sensitive reads are refused with 503 `audit unavailable` (`AUDIT_FAIL_CLOSED`, default true; chart `audit.failClosed`) — mutation routes through the `audit.RequireWritable` middleware, conditionally-audited GET handlers via `h.auditReady(r)` before the action plus the `recordAudit*` return value (`h.refuseUnaudited`). A write that fails after a mutation already ran is counted and logged by `audit.Guarded`; the response stands, and from then on readiness probes a write (inserted and rolled back) until the audit table takes rows again — a ping alone misses a database that answers while that table refuses rows. auth-service refuses admin writes only (sign-in, sign-out, token refresh and one's own password change go on); the AI chat's tools and alert investigations check before they read the cluster. Services wait for the database at boot (`AUDIT_DB_WAIT_SEC`, 90 s) and exit if it does not come — there is no log-only fallback.
- Mask sensitive fields (password/secret/token/apikey) with `audit.MaskSensitive(...)` before storing in `Before`/`After`.
- Every new `docs/*-plan.md` must include a `## N. 감사 로그` section (record-target actions + permission/audit-action mapping table).

The handler pattern is documented in [AGENTS.md](AGENTS.md); use `audit.FromHTTPRequest(r)` to seed a record, then set `Service` (`audit.ServiceK8s` / `ServiceHelm` / `ServiceAI` / `ServiceAuth` / `ServiceAdmin`), `Action`, actor, target, and write via the handler's `auditStore`.

## Build & deploy

**Always build/deploy through `scripts/rebuild-kind.sh`** — do not run raw `docker build` / `kubectl` for deploys (per AGENTS.md). It builds the image, loads it into the kind cluster, and rollout-restarts the deployment. The dev cluster itself is installed from the Helm chart by `scripts/kind-deploy.sh` (values in `deploy/kind/values.yaml`, personal extras in the git-ignored `deploy/kind/values.local.yaml`); `scripts/reset-and-deploy.sh` recreates it or resets just the database.

```bash
scripts/rebuild-kind.sh ai-service frontend     # rebuild specific services
scripts/rebuild-kind.sh --all                   # rebuild everything
scripts/rebuild-kind.sh --list                  # list buildable services
scripts/rebuild-kind.sh --tag dev k8s-service   # custom image tag
scripts/rebuild-kind.sh gateway                 # nginx.conf only: helm upgrade with the release's values, no image
```

Chart-managed objects are changed through the chart (`helm upgrade`), never with `kubectl apply`: Helm 4 applies server-side, so a field kubectl took over makes the next upgrade stop on a conflict.

The script resolves KUBECONFIG in priority order: `$KUBECONFIG_PATH` → single-file `$KUBECONFIG` → repo-local `.kubeconfig-kind` → `/tmp/kubeast-kubeconfig`. Note: the auth/k8s/session Go services share build context `services/` with explicit Dockerfiles (`<svc>-go/Dockerfile`).

Install paths, all from the one chart: `helm/kubeast` (Helm; users install the released OCI chart `oci://ghcr.io/junginho0901/charts/kubeast`, whose image tags the release sets — the chart in a checkout keeps a placeholder tag), `install.sh` (one-liner for an existing cluster; installs that OCI chart at the release version `kubeast` in `deploy/dependencies.yaml`, which the release workflow requires to equal the tag), `scripts/kind-deploy.sh` (local kind), `install-docker.sh` + `docker-compose.yml` (single-host, no cluster; the release workflow starts it on the run's images and signs in before tagging — `scripts/compose-smoke.sh`, also runnable locally with a digests dir or `--build`). There is no separate copy of the manifests. `helm/kubeast/values-minimal.yaml` is the smallest install (no AI, no Redis — k8s-service caches in memory when `REDIS_HOST` is empty — six pods, requests from measurement); the footprint table in `docs/architecture.md` comes from `scripts/kind-footprint.sh` (a kind cluster of its own, `crictl` working set and CPU once a minute) — rerun it and update the table when a change adds a pod or a background job.

## Per-component dev & test

**Go services** (run inside each `services/<svc>-go` dir):
```bash
go run ./cmd/server          # run locally
go test ./...                # all tests (standard go test; *_test.go alongside source)
go test ./internal/helm/...  # single package
```

**Python ai-service** (`services/ai-service`):
```bash
pip install -r requirements.txt          # or requirements-dev.txt for tests
uvicorn main:app --reload --port 8001
pytest                                   # config in pytest.ini (asyncio_mode=auto)
pytest tests/test_tools.py               # single file
```

**Frontend** (`frontend`):
```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # tsc typecheck + vite build
npm run lint     # eslint, --max-warnings 0 (warnings fail)
npm run test     # vitest run
```

Frontend source under `frontend/src`: `pages/` (route-level, grouped by resource domain), `components/`, `hooks/`, `services/` (API clients), `i18n/` (ko/en via i18next). Kubernetes kinds (`StatefulSet`, `ConfigMap`, `Namespace`, …) and screen names (sidebar items, page titles) are English in every locale; verbs, descriptions and notices are localized. Field names, condition values, Pod phases and identifiers (audit actions, permission keys) stay as Kubernetes or the API writes them; what Kubeast itself writes is localized. An empty cell shows `-`, an empty list or section "None" (`common.none`, the drawer's `NoneText`); booleans are Yes/No text (`common.yes`/`no`), not icons or badges; workload lists show one set of summary states through `utils/workloadStatus` (the server value in the tooltip); a drawer section title looks up the `detail` entry `section:<title>` first (kubernetes.io/ko terms) so a field label with the same English word stays English; Korean sentences that describe end in "…합니다.", requests in "…하세요.". The catalog test checks keys built from a value, the agreed Korean terms and every drawer section title. Text a server writes for the screen either comes with a catalog key and values next to its English `message` (cluster hygiene findings; the Prometheus status `reason`) or follows a `lang` the page sends (`utils/uiLang`: the optimization stream, the exec and node shell sockets). Form labels share one style, `block text-xs font-semibold text-slate-400 mb-1` (the `CustomDropdown` label), and controls on one row share a height (`h-10`, or `h-8` next to a `size="sm"` dropdown). The chat inputs (AI chat, floating assistant) use `hooks/useChatTextarea` — they grow with their lines up to a cap, Enter sends and Shift+Enter adds a line, also while an input method is composing; chat answers render `<details>` through `components/MarkdownDisclosure` (the sidebar groups' height transition), and the user's own message is plain text with its line breaks, not markdown. AI-written markdown (chat answers, investigation reports, the optimization answer) renders with `utils/markdown`'s `REMARK_PLUGINS` — GFM with strikethrough only between `~~two~~` tildes, so ranges like `10~14%` stay text. Chat answer tables go through `components/MarkdownTable` (row and column lines; a tall table in the floating chat scrolls under a fixed header row). A range `prometheus_query` (or a `loki_query` metric query) the AI marks `chart=true` (with `title` and `unit`) is drawn under the answer by `components/ChatChart` — SVG, no chart library, the same in AI Chat and the floating chat, sized by the answer's box (under 520 px: lower, three legend entries), "View larger" opening it at z 1400 above the floating chat; ai-service builds the data (`app/services/ai/charts.py`, at most 10 series) and sends it as `chart` on the tool result event and in the saved `tool_calls`, and the chat pairs a tool result with its call by `call_id`, not by tool name; a chart redone under the same title replaces the earlier one. The chat lists follow new text only near the bottom through `hooks/useStickToBottom` (scrolling up stops it and shows `JumpToLatest`; a new question scrolls back smoothly); AI chat bubbles are keyed by conversation and position so the server sync after an answer keeps the same bubble, whose action row (usage, Copy) is closed while the answer comes and opens with the same grid-rows transition, its contents fading in after (no motion under `prefers-reduced-motion`). A stopped answer is saved by the page with `stopped: true`, which session-service keeps as usage `{"stopped": true}` (`turnUsageText` reads it as "Stopped · usage not available"). A dropdown entry's short note ("recommended") is `listHint`: shown in the open list only, so a narrow field shows the whole name. Create, edit and confirm windows use `ModalFrame` (size `sm`/`md`/`lg`, height from the content, footer buttons from `modalStyles.modalButton`); confirmations go through `useConfirm()`, never `window.confirm`; deletes of system objects (`systemObject()`) ask for the name. `ModalOverlay` keeps Tab inside the top-most window and closes it on Escape. The floating chat sits above every modal (z 1300; the modal stack starts at 1200) and moves left of the open detail drawer on screens at least 1348 px wide; Escape and Tab pressed in it stay in it (Escape closes only the chat, Tab stays in it while a modal or the drawer is open). It keeps one conversation per browser tab (`services/floatingChatSession`, sessionStorage): a reload continues it, the "+" left of the input starts a new one (the old one stays in the AI Chat list), signing out forgets it, and one the account cannot open (404) is replaced by a new one; a failed answer (a model refusal, the budget) keeps the question on screen with the error under it, also on a new conversation's first question. A screen tells the floating chat what it shows through `useAIContext`: the layer stays until its input is `null` or the component unmounts, a list that has loaded empty registers zero items (only `undefined` while loading registers nothing), and a path change does not clear layers. A window that shows information (the dashboard lists, the Cluster View pod, a Helm revision, test or upgrade preview, an investigation report) registers what it shows; a create or confirm window registers only its action and target, not its form; nothing goes from a private screen (`utils/aiContext/privateScreens`: the admin pages except Cluster Hygiene and Investigations, and the account page), whatever registered there. `PageContextProvider` sits in `App` above `ConfirmProvider`, so the shared confirm window registers too. List tables fit their box through `useAdaptiveTable`: secondary columns (images, selectors, ports …) carry `col-optional` and fold first, then the rest narrow by up to a fifth, and only then do `col-low` columns (Namespace, Age, IPs) fold too — a folded column keeps its slot at zero width, so an empty row's `colSpan` and the filler rows count every column; a `col-low` value stays on one line with a `title`. Times come from `utils/time`: an age reads as kubectl's AGE (`formatAge`, the apimachinery `HumanDuration` rules), an absolute time as `YYYY-MM-DD HH:mm:ss` in the viewer's zone (`formatTime`) with the UTC value on hover in table cells (`utcTitle`, `absoluteTitle` on an age cell); date fields are `DateTextInput` (typed `YYYY-MM-DD`, checked), not `type="date"`; a list footer is `ListPager` (rows per page — Fit, 25, 50, 100, one choice kept in the browser — the range and the page buttons; always shown, also with one page or no rows) and an empty list row is `TableEmptyRow` with its shared text ("No items.", or "No results found." while the search box has text). The open resource drawer is in the query (`?detail=<Kind>/<namespace>/<name>`, `ResourceDetailProvider`), so a reload or a shared link opens it again. A state that needs no attention (Idle) uses `badge-neutral`, not `badge-warning`. Kind icons come from `components/kindIcons.ts` (sidebar and drawer header), the tab title is the sidebar name, h1 is `text-3xl font-bold` (the full-screen tools Resource Graph, Change History and AI Chat keep a smaller one), page refresh and create buttons are `btn btn-primary`, list search boxes `h-12`, and a page longer than the screen adds `page-scrolls` so the floating chat button does not cover its last row. Heavy use of TanStack Query, Monaco editor, xterm.js (Node Shell), and React Flow / dagre / elkjs (Topology & Dependency graphs).

## E2E tests (Playwright)

`e2e/` runs **against the live kind cluster's gateway**, not a dev server. Tests are serialized (`workers: 1`, `fullyParallel: false`) because they mutate shared single-cluster K8s state. Many specs are **visual-regression baselines** — snapshots captured on `main` must match pixel-for-pixel (within `maxDiffPixels: 100`) on feature branches.

```bash
cd e2e
npx playwright test                      # run all (set E2E_BASE_URL if not :30080)
npx playwright test ai-chat.spec.ts      # single spec
npm run baseline                         # playwright test --update-snapshots (regenerate baselines)
npm run check:assertions                 # every test asserts an outcome (also a CI job)
```

A test asserts what it is named for, not only that something is on screen: compare with what the cluster has (`kubectl`, the API) or with the value the action should produce. `check:assertions` fails on a test with no assertion or with presence matchers only (`toBeVisible`, `toBeEnabled`, a count above zero); a same-file helper that asserts counts.

`auth.setup.ts` is a setup project that logs in once and stores state in `.auth/user.json`; all chromium tests depend on it. That sign-in lasts the dev token lifetime (`auth.tokenTTLMinutes: 60` in `deploy/kind/values.yaml`), so a run that takes longer — a laptop that sleeps — fails on the login page from that point; keep the machine awake (`caffeinate -ims npx playwright test` on macOS). Specs that check the cluster with `kubectl` (`data-display`, `deployment-rollback`, `ai-tool-approval`, and the action suite) take the kubeconfig from `kind get kubeconfig --name …`, not from the shell's `KUBECONFIG`, so the `kind` CLI must be on the PATH. The suite assumes the dev registry holds `self` (the kind cluster itself, in-cluster mode) and a second kind cluster registered as `default` that has **no** `kubeast` namespace but does run metrics-server, kube-state-metrics, node-exporter and a small Prometheus that scrapes the kubelet and cAdvisor (`scripts/add-kind-cluster.sh default --addons`, manifests in `deploy/kind/second-cluster.yaml` — that Prometheus carries `external_labels: cluster: kubeast-b` and is also exposed on NodePort 30090 plain and 30091 behind an nginx basic-auth front (kubeast / kubeast-prom), which `prometheus-external.spec.ts` registers on the first cluster as an external store — and an OpenCost in namespace `opencost` that this Prometheus scrapes, for `cost.spec.ts`, and Kyverno 1.19 with two Audit policies (`deploy/kind/kyverno-values.yaml`, `kyverno-policies.yaml`) whose PolicyReports `policy-reports.spec.ts` reads, rendered with `helm template --no-hooks` and applied server-side so the cluster keeps no Helm release, which `helm.spec.ts` relies on — plus Roles that let the Read group GET that Prometheus and OpenCost through the API server proxy, rendered from `templates/impersonation-viewer-proxy.yaml`, for `viewer-proxy.spec.ts`, and the alert investigator's read-only RBAC from `templates/impersonation-investigator.yaml` — the dev values turn `features.alertInvestigation` on — for `investigator-rbac.spec.ts`, and an Alertmanager (`deploy/kind/alertmanager.yaml`) that posts to this install's webhook for cluster `default` with the token copied from kubeast-secrets, which `alert-investigation.spec.ts` feeds with `amtool`); the multi-cluster specs find out from the API which of the two has releases, metrics or Prometheus and compare them, and `quick-actions.spec.ts` expects the optimization table of `kube-system` there to carry usage. Pages opened without `?cluster=` show `default`, so the resource-drawer specs that need an object pin `?cluster=self`, where `deploy/kind/fixtures.yaml` (applied by `kind-deploy.sh`) provides a CronJob, an Ingress with TLS, a StatefulSet, an HPA, a RuntimeClass, an Argo CD-annotated Deployment, two deliberately broken objects for the issues specs (an unschedulable Deployment and a failed Job) and `e2e-logfile-writer`, an app that logs only to files under `/var/log/app` for `logfiles.spec.ts`; `features.prometheus.enabled` and `features.logFiles` (that path pattern, namespace `default`) are on in the dev values. The AI specs need a default model registered on the dev cluster — with Ollama on the laptop, `kubectl apply -f deploy/kind/modelconfig-ollama.yaml`; for a full run without local inference, `scripts/kind-model-haiku.sh up <key-file>` makes Anthropic Claude Haiku the default for the run (the key from a file, never printed) and `down` puts the Ollama model back and removes the key; `scripts/kind-model-subscription.sh up <token-file>` / `down` does the same with a Claude subscription's setup-token on provider `claude-code` (ai-service built `WITH_CLAUDE_CODE=true`). Both upgrade with the chart of the checkout they sit in, so run them from the worktree of the branch under test. All of this is dev data: re-create it after a reset. The versions of these add-ons and of the target-cluster example charts are listed in `deploy/dependencies.yaml` with every place each one is written: CI checks that the places agree (zeitgeist), and the weekly `addon-versions` workflow keeps one issue open while upstream has something newer — bump the version there and in each listed place, then run the specs that use the add-on. A spec whose prerequisite is missing skips with the reason instead of failing. `audit-sinks.spec.ts` needs `deploy/kind/devtools.yaml` (S3 stand-in, Mailpit, webhook receiver — `kind-deploy.sh` applies it) and the dev sinks in `deploy/kind/values.yaml`; it skips without them. `session-recording.spec.ts` needs `sessionRecording.enabled` (on in the dev values, recording into the S3 stand-in's `kubeast-sessions` bucket); it skips when recording is off. `log-search.spec.ts` needs `scripts/kind-logsearch.sh up` (one Loki in the second cluster, an OpenTelemetry Collector in each, `features.logSearch` on through `deploy/kind/logsearch-values.yaml`; `down` undoes it); it skips while log search is off for `self`. `custom-ca.spec.ts` needs `scripts/kind-private-ca.sh up` after that (an HTTPS front in the second cluster signed by a throwaway CA, `customCAs` set to it through `deploy/kind/private-ca-values.yaml`); it skips without it. `trace-links.spec.ts` needs `scripts/kind-tracing.sh up` after `kind-logsearch.sh up` (a Jaeger and a Tempo in the second cluster, `features.tracing` and `features.traceStore` through `deploy/kind/tracing-values.yaml`);
