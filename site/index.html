Kubernetes®

One web console for many clusters. Browse and edit resources, follow logs, open a shell, roll back a Helm® release — and ask an assistant that answers from the cluster with your own permissions.

여러 클러스터를, 하나의 웹 콘솔에서. 리소스 확인과 수정, 실시간 로그, 셸, Helm® 롤백까지. 궁금한 건 AI에게 물어보세요. 내 권한 그대로 클러스터를 읽고 답합니다.

    Questions자주 묻는 질문

    Do I need an AI provider?AI 서비스가 꼭 필요한가요?

    No. With ai.enabled=false the AI services are not installed and the rest of the console works as is. With a local model in Ollama, nothing leaves your network.

    아니요. ai.enabled=false로 설치하면 AI 없이 나머지 기능을 모두 쓸 수 있습니다. Ollama로 로컬 모델을 쓰면 데이터가 내 네트워크 밖으로 나가지 않습니다.

    What can the AI change?AI는 무엇까지 바꿀 수 있나요?

    In the chat, only what the person asking may change, and only after they approve that exact action on its card. Alert investigations only read. MCP write tools, off by default, run without a card for keys with a Write ceiling, within the key owner's permissions. Every tool call is in the audit log.

    채팅에서는 질문한 사람이 바꿀 수 있는 것만, 그 작업을 승인 카드에서 직접 승인한 뒤에만 바꿉니다. 알림 조사는 읽기만 합니다. MCP 쓰기 도구(기본 꺼짐)는 Write 상한 키에 한해 카드 없이, 키 주인의 권한 안에서 실행됩니다. 모든 도구 호출은 감사 로그에 남습니다.

    Do passwords or keys reach the AI provider?AI에게 비밀번호나 키가 넘어가나요?

    Kubeast masks them first. What the tools read is masked before it is sent: values under names like password, token or api_key, credentials in URLs, bearer tokens, cloud and model keys, and every value of a Secret. Masking finds values by their name and shape, so a password in free text with neither can go through. Each tool call's audit row counts what was masked. Emails and phone numbers can be masked too (ai.redaction.pii).

    보내기 전에 가립니다. 도구가 읽은 내용 중 password·token·api_key 같은 이름의 값, 주소 속 계정 정보, Bearer 토큰, 클라우드·모델 키, 그리고 Secret의 모든 값이 대상입니다. 이름과 형태로 찾기 때문에, 둘 다 없는 평문 속 비밀번호는 걸러지지 않을 수 있습니다. 무엇을 가렸는지는 도구 호출마다 감사 로그에 남습니다. 이메일·전화번호도 가릴 수 있습니다(ai.redaction.pii).

    How does it reach my clusters?클러스터는 어떻게 연결하나요?

    On first sign-in, the setup page connects the cluster Kubeast runs in (In-cluster); others are added with a kubeconfig, EKS through IAM. Requests go to each cluster as the signed-in user, so the cluster's own RBAC still decides: each cluster needs the RBAC bindings the chart renders for this. Kubeast runs no agent on the clusters it manages.

    처음 로그인하면 설정 화면에서 Kubeast가 설치된 클러스터를 연결하고(In-cluster), 다른 클러스터는 kubeconfig로 추가합니다(EKS는 IAM). 모든 요청은 로그인한 사용자 이름으로 전달되므로 권한 판단은 클러스터의 RBAC가 그대로 맡습니다. 이를 위해 각 클러스터에 차트가 만들어 주는 RBAC 바인딩을 적용합니다. 관리하는 클러스터에 에이전트는 설치하지 않습니다.

    Where is the data kept?데이터는 어디에 저장되나요?

    In PostgreSQL — in the cluster or your own. Audit logs and terminal recordings can also go to S3-compatible storage.

    클러스터 안의 PostgreSQL이나 직접 운영하는 PostgreSQL에 저장합니다. 감사 로그와 터미널 녹화는 S3 호환 스토리지로 내보낼 수도 있습니다.

    How much does it need?자원은 얼마나 필요한가요?

    AI를 뺀 최소 설치라면 작은 노드 하나로 충분합니다. 설치 구성별 실측값은 아키텍처 문서에서 확인하세요.
