# site-demo — the project site's demo

`site/demo/` on the project site (https://junginho0901.github.io/Kubeast/demo/) is eight screens of the released console — Overview, Cluster View, Pods, Monitoring, Cost, Helm, Audit and AI Chat — from v0.7.9 (`b4e4ff9f9c592e6ccf909ead68f8cdf87c360786`), on sample data. `site/index.html` shows it in a frame; on a phone only AI Chat is in the frame, and the other screens show a recording or a short note. On a computer the frame is a 1280×700 window, and `site/demo-frame.css`, which `site/interactions.js` adds to the frame's page, fits each screen into it with no page scroll: Overview keeps its title, counts and status charts and leaves out the lists below them (the line naming what was deleted takes its row from the charts), Cluster View's node boxes scroll in a box of their own under the node map, a Helm release's Manifest editor is 12 px lower, and AI Chat's welcome takes less space so the message box stays in view. On a phone the same sheet keeps AI Chat to the frame's width and 640 px height with a smaller welcome and smaller table cells in the answers, so every prepared question and the message box are in view.

The console's components are imported unchanged from that commit; this folder holds only the entry and the sample layer:

| File | What it does |
| --- | --- |
| `main.tsx` | The eight routes, with `HashRouter`, so every screen opens and reloads from `demo/` on Pages; the Pod drawer reads its logs on Load and Refresh, as v0.8.0's does (`LIVE_DRAWER_LOGS` off), and Cluster View's Pod window follows its log through the sample layer's stream |
| `sample/install.ts` | Imported first: `localStorage` and `sessionStorage` in page memory; `fetch` (axios switched to its fetch adapter), `XMLHttpRequest`, `EventSource` and `WebSocket` to `/api/…` answered in the page; a followed log (`…/logs/stream`) streams its lines, and one that cannot be read says why, ends and is opened again after 3 s; the watch socket sends the nodes and a node's Pods and then each change (a restart, a Pod gone and its replacement, a cordon), and any other watch RESYNC; a terminal (exec, node shell) opens, says in its own window that the demo has no cluster to open it on, and closes; any other request refused; in the site's frame, bringing an element into view moves the frame's own boxes only |
| `sample/cluster.ts` | The sample cluster as Kubernetes objects: 11 namespaces, 8 nodes (one NotReady, one Unknown), 25 workloads and their 38 Pods, Services with their Endpoints and EndpointSlices, ConfigMaps, Secrets (masked), ServiceAccounts, 5 PVCs (one Pending) with their PVs and 2 StorageClasses, Ingresses, an HPA, a CronJob and Jobs, and events. Every list row, describe answer, YAML and JSON is made from these objects as k8s-service makes them, so a list and the window opened from it agree, and Cluster View's map, boxes and watches count and colour the Pods the Pods page lists; create from YAML, delete (a deleted Node's Pods move to the nodes left; a deleted Namespace's Pods end and it goes, or stays Terminating with a Pod of a node that is not Ready), YAML apply, cordon, drain, CronJob suspend and trigger, resize and Helm revisions change them, and every view shows the change. A changed template rolls out as Kubernetes does it: a new ReplicaSet, or the one that had it before, with Pods of its own, while the Pods before stay when the new ones do not start (no room on a node, or checkout-api without its setting), and a scale-down removes the newest first; a connection check answers from them (the sample has no NetworkPolicy) |
| `sample/logs.ts` | Each container's log, matched to its app (access lines, jobs, database checkpoints, the crash-looping start and its error), then a new line every 0.5–2 s; at most 1 000 lines a container |
| `sample/yaml.ts` | YAML as kubectl writes it, and the reader the YAML windows use |
| `sample/diff.ts` | The unified diff of two Helm revisions, as the diff windows read it |
| `sample/api.ts` | The answers: the cluster's routes, the account, cost, Helm (values, manifest, history, diffs and previews from the workloads' objects; each revision keeps its own), audit and the chat, and the writes applied to the sample data with the line "Demo — nothing really changes"; a route the screens never ask answers "Not supported in the demo" |
| `sample/chat.ts` | Nine prepared conversations and their follow-ups, streamed as the chat's own events; a question that is not prepared gets the prepared questions instead of an unrelated answer; "Restart checkout-api" shows the approval card |
| `sample/fixtures.ts` | The account (a Write role without Secret reveal), cost (OpenCost's allocation of the workloads' requests), Helm releases and audit records, over the sample cluster: invented names on `*.northstar.example`, no real cluster, account, key or address |
| `sample/notice.ts` | The demo's own notices and the prepared-question chips |
| `index.html` | The entry, with a Content-Security-Policy that allows the page's own files only |

Nothing a visitor does leaves the page or outlives it: no model, no server, no storage; a reload starts again from the sample data. The sample's clock is the page's: what happened before it opened (the checkout-api change 25 minutes earlier and the audit records, alert and graphs around it, the storefront upgrade 9 minutes before that, the node that stopped reporting 9 minutes before the page opened, the CronJob's last half-hourly run) is placed from that moment, and checkout-api starts again every 20 s from the change on, so its restarts match its age, and its events and log move while the page is open.

## Build

```sh
site-demo/build.sh
```

It extracts `frontend/` at v0.8.0 into `site-demo/.release/` (fetching that commit if the clone lacks it), runs `npm ci` there with v0.8.0's lock, and builds into `site/demo/` with base `/Kubeast/demo/`. `KUBEAST_DEMO_NODE_MODULES=<dir>` uses an installed `node_modules` instead of `npm ci`; `KUBEAST_DEMO_BASE=/some/path/` builds for another path. `site/demo/` is not committed: `.github/workflows/pages.yaml` builds it for each deploy.
