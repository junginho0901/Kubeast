# Architecture


The NGINX gateway receives every request and routes it to the microservices. PostgreSQL holds persistent state, and Redis holds cache/session context.

```
                         ┌──────────────────────────┐
                         │  Frontend (React + Vite) │
                         └────────────┬─────────────┘
                                      │
                         ┌────────────▼─────────────┐
                         │  Gateway (NGINX, :8000)  │  routing · CORS · SSE/WS proxy
                         └────────────┬─────────────┘
        ┌───────────┬─────────────────┼─────────────────┬───────────┐
        ▼           ▼                 ▼                 ▼           ▼
   ┌─────────┐ ┌─────────┐      ┌──────────┐      ┌─────────┐ ┌──────────┐
   │  Auth   │ │   AI    │      │   K8s    │      │ Session │ │   Tool   │
   │   Go    │ │ FastAPI │─────▶│   Go     │      │   Go    │ │  Server  │
   │  :8004  │ │  :8001  │      │  :8002   │      │  :8003  │ │   Go     │
   └────┬────┘ └────┬────┘      └────┬─────┘      └────┬────┘ └────┬─────┘
        │           │                │                 │           │
        │           └──────┐    ┌────┘                 │      kubectl → K8s API
        ▼                  ▼    ▼                       ▼
   ┌──────────┐        ┌──────────┐               ┌──────────┐
   │ Postgres │        │  Redis   │               │ K8s API  │ (multi-cluster)
   └──────────┘        └──────────┘               └──────────┘

   model-config-controller (controller-runtime) — watches the ModelConfig CRD
```

**AI tool-calling flow**:

1. `ai-service` orchestrates the chat and dispatches allowlisted tools to `tool-server`.
2. `tool-server` calls the K8s API of the selected cluster.
3. The results are streamed to the chat.

## Services

| Service | Language | Port | Role |
| --- | --- | --- | --- |
| `gateway` | NGINX | 8000 | API routing, CORS, SSE/WebSocket proxy (no image build, config only) |
| `auth-service` | Go | 8004 | Authentication, JWT/JWKS, organizations/teams/RBAC, cluster registry |
| `ai-service` | Python (FastAPI) | 8001 | LLM integration, streaming chatbot, optimization suggestions, Tool calling |
| `k8s-service` | Go | 8002 | K8s resource CRUD, WS logs/exec, topology, Helm, GPU/DRA, multi-cluster pool |
| `k8s-service-stream` | Go | 8002 | With `streams.enabled` only: the same image as k8s-service (`SERVER_ROLE=stream`) taking pod exec, the node shell and the followed logs |
| `session-service` | Go | 8003 | Chat sessions / message history |
| `tool-server` | Go | — | AI Tool call backend (runs kubectl) |
| `model-config-controller` | Go (controller-runtime) | — | `ModelConfig` CRD controller |
| `frontend` | React + Vite + TS | 5173 | UI (static build in prod, served by nginx) |
| `postgres` | — | 5432 | Main DB (durable state), PostgreSQL 18 |
| `redis` | — | 6379 | k8s-service cache, Valkey 9.1 (Redis protocol). k8s-service and tool-server (cluster change notices only) each sign in as their own Redis user, and only they may connect ([Redis users](configuration.md#redis-users)). With `redis.enabled: false`, k8s-service caches in memory |

k8s-service writes its cache in Redis under the key prefix `kubeast:cache:`, every entry with a time to live of at most an hour, and a change of a cluster's registration deletes only those keys (`SCAN` and `UNLINK`), so other keys in the same Redis database stay. A k8s-service whose Redis did not answer at start caches in memory and asks Redis again every 5 s; once it answers, the cache moves there. Which clusters changed is kept in PostgreSQL, not in Redis: auth-service gives a cluster a new `config_version` in the database transaction that replaces its kubeconfig or changes its Prometheus or log store, which commits only once the Secret is written. A change that fails answers an error: the Secret it wrote is put back with the cluster's row locked, so a change of the same cluster waiting for it does not see it, and the cluster then gets one more new `config_version`, so a connection made from the written Secret meanwhile is dropped too; a Secret that could not be put back is named in the answer and in the audit row. Every k8s-service reads the versions every 5 s and drops a connection built from another version or to a deleted cluster. With Redis, the k8s-service that auth-service tells also notifies the others at once (channel `kubeast:clusters:changed:<db>`).

## Resource usage

Measured with `scripts/kind-footprint.sh` on 2026-10-20, on a single kind node. Container memory (working set, the same basis as `kubectl top`) and CPU were sampled every minute.

- "Idle" is the 90th percentile over 30 minutes right after install, with nobody using it (15 minutes for the default install).
- "Busy" is the maximum while 9 list APIs of the UI were called continuously, 4 at a time, for 2 minutes.

The cleanup job that runs once a day also runs once when the server starts, so it falls within this window.

Work that always runs:

- auth-service:
  - seals audit records every 10 seconds (`audit.integrity.sealSeconds`)
  - reverts expired access requests every minute
  - cleans up records past retention every 24 hours, and once at startup
  - with `dormantAccounts` on, locks dormant accounts every 24 hours
  - when an S3 sink is set, writes the audit anchor every 24 hours
- k8s-service:
  - checks the health of each registered cluster every 60 seconds (`multicluster.healthcheckIntervalSec`): every replica probes for its own fail-fast state, and the one holding a PostgreSQL advisory lock (on a connection of its own) writes `clusters.health_status`. The probe reads `/version` as Kubeast itself through the cluster's own version client, as `/health` does, so it waits behind none of the people's requests in the client's rate limit, and waits 5 seconds once the cluster's client is ready (a credential plugin can hold it longer: client-go does not stop one at that time): the version writes `healthy`; another answer below 500 (a 401, a proxy's 404) closes the breaker and writes `disconnected`; a call that could not reach the cluster, a 5xx (kube-apiserver answers `/version` itself, so this is a proxy in front of one that is down, or the server failing), no answer within the 5 seconds once its headers went out and an error of Kubeast's own before the call (a credential plugin that fails, however long it took) fail the probe, and so does a cluster no client can be made for. A probe whose call did not go out before its 5 seconds ended (a wait of Kubeast's own, a credential plugin that succeeded after them) or whose sweep is stopping changes neither the breaker nor the status; the first logs a line. A failed probe, or `multicluster.breakerConsecutiveFails` requests that could not reach the API server with no answer of it between them, opens the cluster's breaker. Such a request had a call with no response (refused, a name that did not resolve, a TLS handshake that did not end, a connection that ended, a deadline that passed before its headers went out) and no call with one, whatever the screen answered; a response of any status (an aggregated API's 503, the API server's 504), a deadline that passed once its headers went out (a slow list) and a failure of Kubeast's own before any call (its database, the client's rate limit) count nothing. The reads Kubeast makes apart from the request's values (the version, discovery, a node's pods and an object's events read once for everyone, the Helm SDK's calls) count for the request they were made for, and a call to another cluster (a live list socket's) counts for neither. A read several requests share (`handler.Shared`) counts once, for the first that waited on it, and not at all when that one left before it ended. An API server that answers while its storage is down (500, 504) is counted neither by requests nor by the probe, whose `/version` does not read the storage: its screens wait for the API server's own time limit. Open, the cluster's requests are answered 503 for `multicluster.breakerOpenSec` (30 s), then the replica lets one request through to try the cluster. Among requests, only that one closes an open breaker (a probe the API server answers below 500 and a change to the cluster close it too), at the API server's first answer below 500 (a terminal or a followed log at once, not when it ends); its failure opens the breaker again, and so does, for a period from its end, a trial the cluster took and answered none below 500 (a 5xx, or no answer before the deadline or before the trial's caller left once its headers went out, as with a proxy in front of an API server that is down; a call Kubeast itself cancelled then, because a call beside it failed, holds the period too); a trial the cluster took no call of (answered from a cache, refused by Kubeast itself, rate limited, its caller gone before its headers went out) leaves the try to the next one. While the clusters cannot be listed (the database down) a replica keeps its last verdicts and logs that once
  - `/health` (the console's header asks it every 5 seconds from each open tab) reads the default cluster's `/version` at most once every 5 seconds for all its callers, each read ending within 1.5 seconds once the cluster's client is ready and waiting behind none of the people's requests, so its `kubernetes` follows the cluster by up to about 7 seconds and does not grow with the tabs; it answers within 1.5 seconds with the audit store's state read beside it, inside the 2 seconds auth-service waits for it
  - cleans up the informer caches of clusters not used for a long time
  - on each replica, reads every registered cluster's `config_version` from the database every 5 seconds, give or take a second, one query (`internal/clustersync`); with Redis it also follows the other replicas' cluster change notices
  - when Redis did not answer at start, asks it again every 5 seconds until it answers, then moves the cache there
  - while it runs a node drain, writes that it is alive every 5 seconds; every 10 seconds marks the drains whose server stopped as interrupted; every hour deletes drains that finished a day ago (`node_drains`)
  - with `nodeShell.enabled` on, on a server that opens terminals: while it holds a node shell, writes that it is alive every 15 seconds over one connection it keeps from its pool, and closes its node shells itself when that write has failed for 45 seconds; every 30 seconds, the first time at start, reads the node shells whose server has not written so for a minute (one query, nothing else while there are none) and deletes their pods as the person who opened each, dropping a row whose pod cannot be deleted once the shell's deadline has passed (`node_shells`). Node shell off (the default), none of this runs

The MCP, alert investigation, session recording, node shell and `features.*` rows are based on the code. They create no pods, so they were not measured separately. The MCP value was measured on 2026-10-13.

To measure again, run these steps. They create a `kubeast-fp` cluster, separate from the dev cluster.

1. `scripts/kind-footprint.sh up`
2. `measure <name> 30`

## Many users

Measured on 2026-10-30 with one k8s-service at the chart's limits (512 Mi; gateway 256 Mi), on a laptop kind cluster, against a KWOK cluster of 1 001 nodes and 50 000 pods. The requests were sent from inside the kind network; the laptop's Docker port forwarding drops connections under a crowd and was not used for these numbers.

| What | Result |
| --- | --- |
| 500 people keeping the Pods page or Cluster View open (polls every 2 s, 8 node boxes each — 2 000 live watches), pods restarted during the run | 0 errors · p95 325 ms · every socket got the changes · k8s-service at most 427 MiB, CPU 1.9 cores on average |
| 300, 400, 500 people opening the Pods page and Cluster View at the same instant (11 requests each) | 0 errors, no restart · k8s-service at most 413 MiB · gateway at most 103 MiB · the last answer after 17, 30 and 29 s |

### Many different people on a large cluster

Measured again on 2026-11-08 with the v0.7.6 code, the same way: one k8s-service at the chart's 512 Mi (the Go collector's limit is 90 % of it, 461 MiB), a laptop kind cluster, a KWOK cluster of 1 000 nodes, 50 000 pods and 100 000 events, requests from inside the kind network. This time each person signed in as an account of its own: 500 accounts, a fifth of them limited to 5 or 20 namespaces. One account's identical reads are shared (`handler.Shared`), so different accounts are the harder case. Before each run k8s-service was started fresh and the KWOK cluster warmed up.

| What | Result |
| --- | --- |
| 100, then 300 different people opening a ConfigMap drawer within 10 s in the namespace of 50 000 pods and 76 000 events, and keeping it open for 2 minutes | 0 errors, no restart · opening p95 1.4 s (100) and 1.2 s (300) · while open p95 6 ms · the API server answered none of Kubeast's requests with 429 · k8s-service at most 150 MiB |
| 100 different people following a Deployment of 500 pods, then a DaemonSet of 1 000 pods, in their drawers through a rollout (3 minutes each) | 0 errors, no restart · k8s-service at most 300 MiB · every change reached every drawer · a drawer's describe read again p95 12.0 s (Deployment) and 7.2 s (DaemonSet), a change on screen p95 22 s and 17 s |
| 500 different people keeping the Dashboard, Pods and Cluster View open for 6 minutes, then 100 of them opening those screens at the same instant | while open p95 16 ms, no restart, no 429 · k8s-service at most 440 MiB · of the 100, half got their last answer only at the load's 60 s timeout, and 263 requests failed |
| 20 people using the AI's read tools at once for 2 minutes (one account, 407 calls) | no restart · tool-server at most 162 MiB of 256 Mi · 8 calls failed, all reading events (`k8s_get_events`, `timeline`) |

Sizing:

- The chart's 512 Mi for k8s-service held every v0.7.6 run above, on 50 000 pods. Keep it unless many people use a large cluster at once.
- When many people use a large cluster at once — hundreds of accounts, tens of thousands of pods — set `resources.k8sService.limits.memory` to `1Gi` (the collector's limit follows). The crowd of 100 above came within 21 MiB of the collector's limit, and on 2026-11-07, before the changes this page describes, the same crowd took k8s-service to 611 MiB with a limit of 1 Gi.
- More memory does not make a crowd faster: the 1 Gi run of 2026-11-07 had the same 60 s answers. It keeps k8s-service from restarting when a crowd and a large namespace meet.

Known limits of v0.7.6, from these runs:

- The 100 people arriving at once above. k8s-service had answered their requests: on an earlier run the same day its sockets to the gateway held 46 MB unsent with retransmissions, and at quiet times k8s-service and auth-service retransmitted some 4 200 segments in 6 minutes too. That points at the laptop's kind network rather than Kubeast, but it has not yet been measured on a real cluster.
- A drawer that follows its object reads its describe again as the object changes, and each person's read waits on the client's rate to the cluster (`multicluster.clientQPS`). During a rollout followed by 100 different people that read takes seconds (above), where a quiet drawer answers in milliseconds.
- A drawer that follows its object, and a workload's pod table up to 300 pods, each hold one watch on the cluster as that person. They are not shared between people.
- The AI's event reads (`k8s_get_events`, `timeline`) read pages of events outside `multicluster.eventListConcurrency`.
- The whole list of a namespace's pods (`GET /api/v1/namespaces/{namespace}/pods`) is made in k8s-service before it is sent. v0.7.5's drawers read it; today's screens read it only for a namespace under their table's line or when the paged read is refused, and a script can call it. One account's reads at one moment share one answer (at most two reads, one after the other); different accounts each make their own, so many accounts reading a large namespace this way at once can take k8s-service past 512 Mi. One read of 50 000 pods holds about 80 MiB besides its 36 MiB answer (`BenchmarkTenReadersOfOneNamespacesPods`). Until a v0.7.6 change it also held every row as a map, about 300 MiB, and ten people of one account opening v0.7.5's ConfigMap drawer in that namespace took k8s-service past 512 Mi in a test.

What sets these limits:

- `multicluster.wsMaxSubscriptions` (2 000): every live watch on a screen is one watch on the cluster as the user. Past the limit, a screen loads but does not update, says so and asks again by itself, spread over half a minute and more. The same happens to a new watch while what k8s-service holds against the collector's limit — the heap the last collection found live, the goroutine stacks and the runtime's own — is past 80 % of that limit (`watchMemoryFull`), asked when the page asks for the watch and again when its turn to open comes unless a watch of that list has been on (one whose version expired opens again), and the screen says the server is short of memory: a watch decodes every object there is as it opens, and in the W2 load test 700 people reopening their screens at once after a restart took k8s-service past 512 Mi six times in a row. A first form of this check counted the live heap alone, against 75 %; at 700 people the stacks were 58–92 MiB of the 461 MiB limit, so the live heap could reach that share only as k8s-service ran out of memory, which it did four times in the second W2 night (2026-11-15). The watches already on go on. A watch of pods, nodes or deployments decodes only what its row reads (`watch_decode.go`): in `TestWSMemoryPerUser` that took what opening W2's kept screens allocates from 9.4 to 5.5 MiB per person and the most memory held while the node list of 1 000 nodes opened from 4.4–4.6 to 3.1 MiB per person; with the collector's limit of 461 MiB, 700 people opening at once held about 0.65 MiB more each either way. A drawer shares the list watch of the page behind it instead of opening its own, and most drawers follow their object on the read they already make every 10 s, which costs no watch. The Helm pages' stream counts here too, one watch or one per namespace of a grant limited to them; past the limit the same notice says so and the stream asks again after half a minute to five.
- A drawer's table of a selector's or a workload's pods (Service, PodDisruptionBudget, Deployment, DaemonSet, StatefulSet, ReplicaSet, Job) follows them by a watch of its own up to 300 pods; past that it reads the server's page with its revision every 3 s (10 s in a namespace of more than 10 000 pods) and says so above the table. On 2026-11-08, with that line at 2 000, 100 different people following a Deployment of 500 pods, then a DaemonSet of 1 000, through a rollout took k8s-service past 512 Mi and it restarted. The tables that pick from a namespace's pods (ConfigMap, Secret, ServiceAccount, RoleBinding, NetworkPolicy) keep 2 000.
- The node boxes of Cluster View are answered from the overview informers' pod rows, looked up by node (an index on the rows, as Kubernetes' own controllers look up a node's pods), and each person keeps the namespaces its own identity may list pods in (a SelfSubjectAccessReview, 60 s); a namespace that check refuses is listed as that person, so the cluster decides there. A box gets what it draws and its menu reads — name, namespace, Status, phase, restarts, creation time, labels, pod IP, node and the card's colour and reason — and the pod's window opened from it reads the pod's describe before it shows the containers, unless a live frame has already brought the pod's full row. A box of every namespace is made once per node while the node's pods stay the same, for everyone who may see every namespace. With no informers running — after a restart, or ten minutes with no screen using them — a box starts them, as the node map does, and is listed as the person until they have synced; it never waits for them. It starts none, and is listed as the person, within five minutes of the cluster refusing `kubeast:cache` a list or watch; a server that keeps no informers (the `stream` role) serves no boxes. The node map on the same screen starts them too, so this matters for the first boxes after a restart, before the map has answered, and for a caller that reads only boxes. The index costs 36 bytes a pod (569 bytes a pod with it, 533 without, `TestPodRowMemory`); one box of 50 pods takes 62 µs and 46 KB in k8s-service, 5 µs and 1.5 KB when it was made already, where the read of the node as `kubeast:cache` took 4.7 ms and 1.9 MB (`BenchmarkNodeBox`, on 50 000 pods of 1 000 nodes). On 2026-11-16, before this, 100 people opening 4 different nodes each made 400 lists of pods as `kubeast:cache`, and the slowest box's first byte came after 2.7 s, 2.4 s of it waiting for the node read places below; now they make none (`TestFourHundredPeopleOpeningFourHundredNodesListNoPods`).
- A Node drawer's pod table and Allocated Resources are read once per node for everyone asking at that moment, as `kubeast:cache`, with the same namespaces kept for each person. At most 16 nodes of one cluster are read at once and the others wait: a node of 40 pods holds about 0.7 MiB while it is read, and on 2026-11-08 k8s-service went from 316 to 492 MiB in the second a crowd opened 400 nodes, as many at once as the client's burst of 200 let through. The lists made as the person take the same places, a box's too: a namespace that check refuses, and the whole node before the informers have synced after a restart or while `kubeast:cache` is refused. The namespace list comes from what k8s-service keeps for a caller the cluster lets list namespaces, and for a grant limited to namespaces from what it keeps of each namespace the cluster lets that person read (a SelfSubjectAccessReview of that read, 60 s).
- What different people still ask as themselves is one access check per kind a screen shows, remembered for a minute: about eight for one person's Dashboard, Pods and Cluster View. A grant limited to N namespaces is asked, in each namespace, about the overview's kinds that namespace holds (pods, Services, Deployments, PVCs) and whether it may read the namespace, and once about a kind none of them holds: a namespace without any of a kind adds nothing to its count, so its answer is needed only while no other namespace allowed that kind. That is up to 5 × N on its first screens, and nothing more within the minute but its node list (counted from the code, `TestFirstScreensOfOnePersonListNoPodsAsThatPerson`, `TestTheDashboardsRequestsAsThePerson`: a Dashboard of 20 namespaces that each hold pods, a Deployment and a Service, two of them a PVC, makes 83 requests as the person and 1 when opened again, where it made 101 and 21 when every namespace was asked about every kind and read on every open). They queue on the client's rate to that cluster, `multicluster.clientQPS` (100 a second) and `clientBurst` (200). How long requests waited there is `kubeast_k8s_client_rate_wait_seconds` (`limiter="user"`, [metrics](metrics.md)): a p95 near 0 means the rate is not the wall, seconds mean it is. Raising that rate on 2026-10-30, when the node boxes were still read as each user, moved the queue to the test cluster's API Priority and Fairness and the node boxes waited longer. `multicluster.reviewQPS` and `reviewBurst` give the access checks a rate of their own and leave the reads' rate as it is; a check reads nothing from the API server's storage. For K different people opening their first screens at the same moment, a burst of about 8 × K checks lets none of them wait on the rate. Without it, a check asked for the first time goes before the checks that open screens ask again once their minute ran out; one asked again lets the others go first for at most 10 s, then takes its place by arrival. The rate and the number of checks stay the same. Played through the limiter with 100 people arriving at once while 500 screens ask again at 59 a second (`TestACrowdsFirstChecksFinishSoonerAndChecksAskedAgainWaitAtMostTheBound`, the calls counted from the code, eight side by side per person, no API server time), the last of the 100 got its last turn after 12.2 s instead of 23.7 s for 1 290 calls, and after 27.8 s instead of 39.6 s for 1 930 (nothing remembered); a check asked again waited up to 10 s instead of 3.7 to 6 s.
- `auth.impersonation.sharedReadChecks` (off; [cluster requirements](cluster-requirements.md) §1) asks those checks of the screens served from `kubeast:cache` once per group set instead of once per person: as `kubeast:group-check:<made at each start>` in the person's groups, its allow standing for everyone with those groups for the rest of the minute, a refusal asked again as the person. One wide Read person's eight then come down to its can-i. The shared checks wait on the same client rate as the person's, so the rate and the burst stay as they are and fewer requests wait there. Played through the limiter (`TestACrowdOfOneGroupSetQueuesItsAllowedChecksOnce`, the requests the code made for the first screens of 100 people at once, 80 of them wide Read and 20 Read limited to 5 or 20 namespaces, eight side by side per person, no API server time), the requests on the user rate went from 1 470 to 189 (7 shared by the wide group set, 62 by the limited one): 1 270 of them past the burst of 200 before and none after, the last of the 100 done after 12.7 s before and 0.1 s after. On the kind dev install of the release candidate (2026-11-17), with 100 people arriving at once the last of them was done after 1.4–2.0 s in three runs with it on and after 6.9–7.0 s with it off on the same build, and the API server got 100–103 access reviews instead of 828–843; a check against `kubectl auth can-i` for five accounts found no difference. Each replica asks for itself. `kubeast_k8s_access_reviews_total` counts these reviews by `asked_as` ([metrics](metrics.md)).
- The Pods page reads its page again every 3 s, and every 10 s when it counts more than 10 000 pods (the namespace chosen, or every namespace the user may see), so on a large cluster a change k8s-service has seen is on screen within 10 s. Each read sends the revision the page holds and is answered from k8s-service's rows, `unchanged` before any sort while no row the user may see has changed; it is not a request to the cluster (the table above: 500 different people with it open on 50 000 pods, p95 16 ms). While the rows are listed as the user, before the informers have synced or while `kubeast:cache` may not watch pods, it reads every 30 s.
- The Pods page, the node map and the node list are answered from what k8s-service keeps (measured up to 500 people at once). Their work on the rows runs on as many at once as there are CPUs, at most eight: the chart sets no CPU limit, so Go counts every CPU of the node, and each of these holds about 2 MB of rows on 50 000 pods. `POD_ROW_CONCURRENCY` in k8s-service's environment sets another number.
- The gateway holds proxy buffers for every request in flight, about 30–90 KB each.
- One person's identical reads at one moment are at most two reads of the cluster: the drawers, the access checks and the reads of a namespace's pods (`handler.Shared`, `internal/flight`). A read started before a request came does not answer it, and an answer never crosses to other claims.
- `multicluster.bigReadConcurrency` (2): reads of more than one page (pods, ReplicaSets, ControllerRevisions) that run at once in one k8s-service; the others wait, and a read of one page waits for none. One read of a 50 000-pod namespace asks 39 to 78 pages a second and holds up to about 110 MiB. A read waiting for its place holds where to go on, not the page it read; before 2026-11-08 each waiting read held its page, 16 MiB for 256 pods of 64 KiB (`TestAReadWaitingForItsNextPageHoldsNoPageItAlreadyRead`).
- `multicluster.wsWatchStartConcurrency` (16): watches of one cluster waiting for the API server's first answer at once, the Helm pages' stream's too, since client-go does not rate limit watches; the others wait their turn. A start the API server has not answered in 5 s gives its place to the next one and stays open, so a slow API server can have more than 16 starts unanswered at once: the limit spreads the starts, it does not cap them. A wait past 10 s tells the page its list is not following.
- `multicluster.wsWatchOpeningConcurrency` (8): watches from no version that may be receiving the objects they open with at once, for every cluster together. The API server sends every object there is as such a watch opens, and in the second W2 night 700 people's sockets coming back after a restart took k8s-service from 121 to 285 MiB of live heap in two seconds and past its limit 30 s later. Such a watch takes its place before it starts, so its objects are read as they come: an answered watch left unread fills the API server's buffer for it, which closes the watch past 100 ms (`cache_watcher.go`). A cluster takes the places up to its own limit, which starts at one, goes up by one for each start its API server answers within 5 s of the start going out and halves for each it does not (or answers with a 5xx), so a cluster that does not answer holds one place and a slow start among answered ones costs half of the limit for a moment (one start in three past 5 s, 60 openings: 22.0 s when one such start dropped the cluster to one place, `TestASlowStartAmongAnsweredOnesCostsHalfTheLimit`); half of the places while another cluster waits for one; and every free place up to its limit otherwise, lent with a clock of 1 s before the answer instead of 5 s, so a server with one cluster opens eight lists at once (64 openings of 0.2 s: 4.05 s when one cluster could take only half, `TestOneClusterOpensWithEveryPlace`). Beside two clusters that never answer, 50 lists of a third opened within 1 s (`TestAClusterThatDoesNotAnswerHoldsOneOpeningPlace`), where beside one such cluster they had waited 11.8 s when the places were taken without these rules. A start the API server has not answered in 5 s (1 s on a lent place, which does not lower the limit) gives its place back, and its objects, if they come, are read without one. The watch asks a watch list (`sendInitialEvents=true`, `resourceVersionMatch=NotOlderThan` from `resourceVersion=0`, which the API server serves from its watch cache as it does a watch from no version, ending the objects in a bookmark) and gives the place back at the first of: that bookmark or a change, a frame that would wait for the browser, the end of the watch, or 2 s after the API server answered. An API server that refuses watch lists (1.27–1.31 and 1.33 by default) answers 422, and one that takes them and sends no bookmark leaves three of them in a row at 2 s with no event in the last second (a list still coming in does not count); either way that cluster's watches open as a plain watch for 10 minutes, whose opening ends at a change or 50 ms without an object. A watch of changes, a watch that goes on from its version and the Helm pages' streams take no opening place. Eight node lists of 1 000 nodes opening at about 5.5 MiB each take 44 MiB, inside the 65 MiB between the memory share (0.80 of 461 MiB) and the 0.94 at which the 700 people ran out of memory.
- Connections to a cluster's API server: on 2026-11-18, with one k8s-service on a laptop kind cluster and 700 people on a KWOK cluster of 50 000 pods, k8s-service held 1 connection to that cluster's API server before the run, 21 in its middle, 19 at its end and 1 again after it.
- `multicluster.wsWatchStreamWindowKiB` (1024): the HTTP/2 window of each live list's stream, which costs both ways. A watch whose browser reads slowly gives its opening place back and waits with its socket's 256 frames and up to this much of its list unread, which only the memory share counts; and a stream reads at most this much a round trip, so a big list over a long one comes slowly, and the API server writing it may close the watch when changes pile up behind it. Measured on a laptop, the live heap 16 slow browsers opening 2 000 objects of 4 KB took and a 26 MB watch list over a 50 ms round trip: 256 KiB +4.7 MiB and 5.3 s, 512 KiB +10 MiB and 2.7 s, 1 MiB +18 MiB and 1.4 s, 2 MiB +33 MiB and 0.75 s, Go's 4 MiB +65 MiB and 0.69 s. Raise it for clusters far away (2048 for a round trip of 30–50 ms), lower it where browsers are many and slow.
- What is left outside these counts: the watches waiting for a slow browser are not counted; a cluster that has answered and stops answering holds the places lent to it for 1 s, its own half for 5 s, and then one place, so a cluster arriving then waits about 1 s once (4.50 s with 5 s on every place, `TestAClusterThatGoesDarkGivesItsLentPlacesBackSoon`); a start answered after 5 s reads its objects without a place; and an 80 ms pause in a plain watch's objects ends its opening early. A wait past 10 s for a place tells the page that the list waits for its turn to open (`limit_scope` `opening`, which the page does not read as memory running short) and reads its list again once the watch is on. In `TestWSMemoryPerUser` (go1.27.1 on a laptop, the collector's limit at 461 MiB, the memory share on, one cluster, a stand-in API server over TLS and HTTP/2 that sends a list's objects at once and changes nothing, browsers reading as fast as they can in a second process), 700 people opening W2's kept screens at once held at most 290–297 KiB more each, where without the opening places they held 634–635 KiB, none was refused, and every watch had its objects after 4.7 s; 500 people held 320–333 KiB more each, where they held 852–863 KiB, in 2.9–3.1 s. An earlier version measured the same way, which held one cluster to half of the places and read with a 256 KiB window, held 266–269 KiB in 5.5–5.8 s for 700 people and 278–280 KiB in 3.8 s for 500. A list that keeps changing or a slow browser is held to the rules above by the package's tests, not by that measurement.
- `multicluster.eventListConcurrency` (4): lists of one object's events, which every drawer's Events section needs, that one cluster gets at once; the others wait. The API server's Priority and Fairness counts such a list as up to 10 seats of its global-default level, about 49 by default; on 2026-11-08, with each drawer listing at once, 300 different people opening a ConfigMap drawer in a namespace of 76 000 events had the test cluster answer 430 of Kubeast's requests with 429. With these four places alone 44 of 216 such drawers then waited past 60 s, so an object's events are now read once for everyone asking at that moment, as `kubeast:cache`, by those whose identity may list events there (a SelfSubjectAccessReview, 60 s; across the cluster for a Node or another object of the cluster); a refusal of that check or of `kubeast:cache` lists them as the person.
- `multicluster.toolServerKubectlConcurrency` (3): kubectl processes in tool-server, about 40 MiB each in one container of 256 Mi; the others wait inside their call's 50 s, and the Go collector's limit is lowered by that memory. A `k8s_jq_query` program runs in a child process of tool-server that takes one of these places too, and one such child runs at a time (`jqRuns`): the others wait inside their call's 50 s, then their caller gets a 503 saying tool-server was busy and to ask again. The child ends itself past its memory budget (32 MiB and 8 bytes for each byte of the list, so 40 MiB at the 1 MiB output cap), is ended at 5 s, and, built as the image is (Linux, without cgo), cannot map more than 80 MiB past what it had mapped when it started (`RLIMIT_AS`, `jq_limit_linux.go`), so one step that asks for more at once, which the budget's look every 2 ms can miss, is refused when it asks. The 80 MiB are one 64 MiB heap arena, since Go starts the heap at a random place in its first arena, and room for the runtime's own maps: on 2026-11-09 in a Linux container (Go 1.27.3), 64 MiB failed 6 of 80 ordinary programs over a 908 KB list and 80 MiB none of 480, while a 200 MB string was refused every time. With nothing else stopping it, one child grew to about 124 MiB before the limit stopped it, more than its place's 40 MiB; ordinary programs stayed under 41 MiB, and one child at a time keeps that excess to one. macOS refuses the limit, and a build with cgo leaves it unset, since the stacks of the threads it starts count against it, so there the budget alone holds. On a laptop it adds about 20 ms to a call over a 1 MiB list (an ordinary program there ran within 16 MiB). An answer past 256 KiB is masked and written holding one of three places, and never without one: masking a 1 MiB kubectl list allocates about 7 MiB, and on 2026-11-08, with nothing bounding that step, twenty AI users at once took tool-server from 72 to 254 MiB in four seconds. It waits for its place past its call's 50 s, until 2 s before the server's 55 s write limit; with no place by then its caller gets a short error saying tool-server was busy and to ask again, and nothing at all once its caller has gone.
