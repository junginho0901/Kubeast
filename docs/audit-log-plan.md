# Audit log plan (audit-log-plan)

The document AGENTS.md and CLAUDE.md point to as authoritative. The code is the reference; this document is a summary drawn from the code (rewritten 2026-09-27 — the previous version lived outside the repository, so references to it were broken).

## 1. Purpose

Record who (actor) changed or sensitively opened what (target) in which cluster, when and how (action, result).
Viewing is through the admin screen (`admin.audit.read`) and CSV (`admin.audit.export`). Records are kept in two places: the application DB and the cluster log pipeline.

## 2. Principles

| # | Principle | Implementation |
|---|---|---|
| D1 | Every **write handler** (create/update/delete/rollback/restart/scale/apply/…) and **sensitive read** (Secret reveal, Node shell, Pod exec, Pod logs, kubeconfig read, audit log view and export) is recorded. Plain list/get, health and public endpoints are excluded | The handler builds a record with `audit.FromHTTPRequest(r)` and calls `auditStore.Write` |
| D2 | Both success and failure are recorded. A failure has `Result = failure` and the reason in `Error` | Helpers such as `recordHelmAudit` fill them from whether there is an err |
| D3 | Secrets are masked so they do not get into `Before`/`After` | `audit.MaskSensitive` (password/secret/token/apikey keys), AI tool results through `pkg/redact` |
| D4 | **The DB row is a precondition for sensitive actions** (fail-closed); only the stdout mirror is best-effort. While the audit DB cannot take a record, writes and sensitive reads get 503 `audit unavailable`, and lists and reads go on. A failed write after a change already ran is counted and logged at ERROR, and the response stands. If the DB is not there at boot, the service waits (`AUDIT_DB_WAIT_SEC` 90 s) and then exits — there is no log-only fallback (the same direction as NIST AU-5(4) restricted mode, Vault audit devices and kube-apiserver `--audit-log-mode blocking`) | k8s-service: `audit.Guarded` (2 s ping cache, failure counter, `audit` block in `/health`) + `audit.RequireWritable` on mutation routes (except POST `/search`) + `auditReady`/`refuseUnaudited` in conditionally audited GET handlers. auth-service: the same `audit.Guarded` + `RequireWritable` on signed-in routes (except token refresh, changing one's own password and the cluster switch signal — sign-in, sign-out and API key exchange were outside it to begin with) + a readiness check before reading audit logs, access reviews, AI usage and directory groups (2026-10-21; only admin writes are refused). session-service: the same `audit.Guarded` + `RequireWritable` on renaming and deleting chat rooms. ai-service: `require_audit_ready()` before running or rejecting an approved write tool and before adding, changing or deleting an AI model config; chat tools and alert investigations call `audit_ready()` before running (if it fails, the tool result is `audit_unavailable` and the investigation fails). **Probe write after a write failure**: a ping (SELECT 1) alone misses the case where the DB is alive but only the audit table cannot take rows (disk, locks, triggers), so once an audit row write fails, the readiness check switches to a probe write that inserts a row and rolls it back, and refuses until writing works (`audit.WriteProber`, Python `_write_broken`). Switch `AUDIT_FAIL_CLOSED` (default true, chart `audit.failClosed`) |
| D5 | One audit event = one DB row + **one stdout JSON line**. The cluster log pipeline takes a copy that is independent of the app DB | `audit.StdoutTee` (Go), `audit_writer._emit_stdout` (Python). Line format in §4 |
| D6 | Action names are `<domain>.<object>.<verb>`. A new action is added to §5-2 of this document before the code | Domains = `user` `admin` `k8s` `helm` `ai` |

## 4. Storage

- **DB**: `auth_audit_logs` (shared by all services; auth-service manages the schema). Go's `audit.PostgresStore` and Python's `audit_writer.py` INSERT into the same columns.
- **stdout**: one line through the service logger (JSON).
  - Line format: `{"time":…,"level":"INFO","msg":"audit","event":"audit","audit":{id,service,action,result,error,actor_user_id,actor_email,target_type,target_id,target_email,cluster,namespace,path,request_ip,user_agent,request_id,before,after}}`
  - The top-level `event: "audit"` is the routing key for the log pipeline.
  - Turn it off with `AUDIT_STDOUT=false` (chart `audit.stdout`).
  - If the DB write fails, the line is still written, with `store_error` added.
- **When the DB cannot be written (D4)**: changes and sensitive reads get 503 `{"detail":"audit unavailable"}`.
  - The reason is in the service log (`audit: refusing unrecorded action`).
  - The `audit` block of k8s-service `/health` has `ready`, `write_failures` and `last_error`.
  - Switch: `AUDIT_FAIL_CLOSED` (default true, chart `audit.failClosed`). Boot wait: `AUDIT_DB_WAIT_SEC` (default 90).
- **Viewing and export**: `GET /api/v1/auth/admin/audit-logs` (filters, pages), `GET /api/v1/auth/admin/audit-logs/export` (same filters, CSV UTF-8 BOM, at most 50,000 rows). Both are audited (`admin.audit.read`, `admin.audit.export`).
- **Sinks (optional)**: the DB is the primary store, and sinks **copy** DB rows out.
  - One dispatcher in auth-service does this: of several replicas, the one that holds a Postgres advisory lock. For each sink, it reads the rows above its cursor (`audit_sink_cursors.last_id`), sends them in batches, and moves the cursor on success.
  - The writing services (Go, Python) still INSERT only into the DB.
  - To avoid missing small ids committed late, it reads only rows older than 5 seconds.
  - Types:
    - `s3`: S3-compatible (AWS, MinIO, GCS, R2). Time-partitioned NDJSON gzip, key `prefix/YYYY/MM/DD/HH/<first id>-<last id>.ndjson.gz`.
    - `webhook`: `json` generic, `slack`, `teams` (Workflows Adaptive Card), `discord`, `telegram`, `pagerduty` (Events v2).
    - `email`: SMTP.
    - `file`: NDJSON, size rotation.
  - Each sink has an action filter (the same wildcards as permission patterns, e.g. `k8s.*.delete`) and a result filter.
  - Delivery is **at least once**: if the dispatcher dies after sending but before moving the cursor, it sends again.
    The record's `id` is the deduplication key on the receiving side. S3 object keys are id ranges, so the same batch overwrites the same key.
  - It does not block the request path. When a sink fails, its cursor stops and it retries (exponential backoff, up to 5 minutes).
    This shows in the metrics `kubeast_audit_sink_pending`, `_failures_total` and `_last_success_timestamp_seconds`, and in the alert `KubeastAuditSinkStalled`.
  - Send results are not recorded as audit rows; that would be a loop of audits producing audits.
  - Exported record (snake_case): `id, time, service, action, result, error, actor_user_id, actor_email, target_type, target_id, target_email, cluster, namespace, path, request_ip, user_agent, request_id, before, after`.
    It is the DB row as is; masking was already done at recording time.
  - Settings: chart `audit.sinks[]`, with secrets by Secret name only.
  - Object Lock (WORM) is left to the bucket's default retention, and Kubeast uses only `s3:PutObject`.
- **Integrity (hash chain and anchors, `AUDIT_INTEGRITY_*`, chart `audit.integrity`)**:
  - **Sealing**: every `AUDIT_INTEGRITY_SEAL_SEC` (default 10 seconds), auth-service's sealer takes the rows not yet sealed, in id order. It fills `chain_seq` (seal sequence), `prev_hash` and `row_hash = sha256(prev_hash ‖ 0x1e ‖ canonical row)`.
  - The canonical expression is `internal/auditchain.CanonSQL`. Postgres builds the string, so it can be recomputed with one psql line.
  - The write path stays as is; the services only INSERT.
  - **Anchors**: given an s3 sink name in `AUDIT_INTEGRITY_ANCHOR_SINK`, every `AUDIT_INTEGRITY_ANCHOR_HOURS` (default 24) it writes the chain head as a digest JSON to that sink's bucket. It records the anchor in `audit_anchors`.
    - Digest: `{version, created_at, from_seq, to_seq, rows, head_hash, prev_anchor{object_key, hash}, access_reviews[{id, reviewed_at, hash}], hash_algorithm}`
    - Object key: `<prefix>digests/YYYY/MM/DD/<HHMMSS>Z-<from>-<to>.json`
    - It writes even when there are no new rows, with metadata `anchor-hash`.
  - **Verification**: admins (`admin.audit.read`) get the status with `GET /api/v1/auth/admin/audit/integrity`, and recompute a range with `POST …/integrity/verify {from_seq?, to_seq?, anchors?}`.
    - The default range starts from the last anchor. The limit is 200,000 rows; past it, 413.
    - Result: `{ok, first_bad_seq, reason: hash_mismatch|chain_break|gap|anchor_mismatch, anchors[{head_ok, object_ok, reviews_ok}]}`
  - `admin.audit.export` gets an immediate anchor with `POST …/integrity/anchor`.
  - **Limits**: rows deleted in the window before sealing (≤ SEAL_SEC) are not caught. The Object Lock of the anchor bucket is the basis of trust; the digest has no signature.

## 5. Catalog

### 5-1. Naming rules

`<domain>.<object>.<verb>`, lowercase and dot-separated.
Pick the verb from those in use now: `create`, `update`, `delete`, `read`, `reveal`, `exec`, `shell`, `drain`, `cordon`, `uncordon`, `apply`, `rollback`, `upgrade`, `uninstall`, `test`, `trigger`, `suspend`, `resume`, `set`, `unset`, `sync`, `send`, `call`, `approve`, `reject`, etc.

### 5-2. Initial catalog

Extracted from the code (2026-09-27). By service.

### 5-4. What is not recorded (and why)

- List and get GETs (except sensitive reads), silence list and preview, and log file list (`ls`).
- The k8s-service internal paths `/internal/clusters/*/invalidate|validate` — service token + user JWT, outside the gateway. That work (cluster registration and update) is recorded by auth-service as `admin.cluster.*`.
- Issuing the investigator token (auth-service `/internal/investigator-token`) — the investigation itself is `ai.investigation.run`.
- Audit sealing failures — that would be a loop of audits producing audits, so they go to metrics and logs (`/health` `audit` block).
- Creating chat rooms and saving messages, accepted alert webhooks — the reason is in the matching row of §5-2.
- Malformed requests (unreadable body, empty required value, address shape, FastAPI 422). These are input mistakes where nothing was attempted.
  - Values refused by policy (keys entered directly, addresses that are not allowed, exec commands that are not allowed in a kubeconfig, TLS verification turned off) and permission refusals are recorded as failure.
- The connection test before registration (`POST /api/v1/clusters/validate`) — it only connects with the kubeconfig it received and saves nothing. Registration is `admin.cluster.register`.

### 5-3. Adding a new action

1. Add a row to §5-2 (in the same PR).
2. Record both success and failure in the handler; mask `Before`/`After`.
3. For a feature that gets a new `docs/*-plan.md`, a table of the target actions and the permission mapping in its `## N. 감사 로그` section.

### 4-1 Session recording (optional)

- The **output shown** in Pod exec and node shell terminals (the screen the user saw) is recorded as asciicast v2.
  - Keystrokes are not recorded, so input that is not echoed, such as passwords, is not kept. This is the same as asciinema's recommendation.
  - At session start, the terminal prints one line: "This session is recorded".
- k8s-service writes to a local volume, and also uploads **parts every `chunkSeconds` (default 30 s) during the session**. If the k8s-service pod disappears, only up to the last part interval is lost.
  - Store: `s3` (S3-compatible), `database` (`session_recording_parts`, 1 MiB cap per session) or `file` (PVC).
  - The list and status are in `session_recordings`.
- A session cut off for reasons on the k8s-service side is `interrupted`: a normal shutdown or container restart uploads the remaining output too, and when the pod disappears only the parts uploaded before remain (reason in `last_error`).
- If recording cannot start (cannot write to the local volume), the session is refused when `required: true` (default).
- Upload failures (30 s limit per part) do not block the session. They are retried and show in the metrics and alerts.
- Past `maxBytes` per session (default 64 MiB), only the recording stops, leaving a marker and `truncated`.
- Kubeast does not delete objects in the remote store (bucket lifecycle, Object Lock). DB rows follow `retention.auditDays`.

## 6. Retention

- auth-service deletes DB rows every day, only those past `RETENTION_AUDIT_DAYS` (chart `retention.auditDays`, default 0 = forever). The admin screen only views and exports CSV.
  - If there is at least one sink, it deletes only **up to the rows every sink has sent**. With a stopped sink, rows stay past the period.
- Review sign-offs, including snapshots, are deleted by the same daily job once they pass `RETENTION_REVIEW_DAYS` (chart `retention.reviewDays`, default 1095 days).
  - These are the access review's `access_reviews` and cluster hygiene's `hygiene_reviews`.
  - The purge reports them in `after.access_reviews` and `hygiene_reviews` of `admin.retention.purge`.
- Keep long-term records through the S3 sink (+ the bucket's Object Lock default retention): keep the DB only for the period the console screens, CSV and fail-closed need (about 90 days recommended when S3 is on).
- With the hash chain on, purge deletes only **a prefix of the chain**: old rows sealed after the smallest `chain_seq` among the rows inside the retention period (rows committed late) stay until the chain reaches them. `audit_anchors` is not deleted (it is small, and it is evidence for past ranges).
- The stdout copy follows the cluster operator's log pipeline policy (collection, retention, locking).

## 7. How to verify

- Unit: `services/pkg/audit` tests (store, masking, stdout line format).
- e2e: after a write action, there is a row in `GET /api/v1/auth/admin/audit-logs?action=<name>`, and the pod logs have the same number of `"event":"audit"` lines.
- Integrity:
  - `internal/auditchain` tests: hash, seal order, detection of changes, deletions and insertions, anchor digest, independent ranges.
  - e2e `audit-integrity.spec.ts`: seal rows → a one-line psql recomputation matches → change a row in the DB → `hash_mismatch` at that sequence → restore → anchor → stand-in object, `object_ok`.
  - With psql, without Kubeast: `select chain_seq, encode(row_hash,'hex') = encode(sha256(prev_hash || '\x1e'::bytea || convert_to(<CanonSQL>, 'UTF8')), 'hex') from auth_audit_logs where chain_seq between a and b order by chain_seq;`
    Also check that the previous row's `row_hash` = this row's `prev_hash`, and that the last row = the digest's `head_hash`.
