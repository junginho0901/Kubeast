## 1. What are we working on?

### Data flow

```
 Browser or API client
   │  session cookie (SameSite=Strict) or Bearer token · WebSocket Origin
═══╪══════════════════════════════════════════════ TB1 outside → Kubeast's namespace
   ▼
 gateway (nginx)
   │                                        │
   │ everything else for k8s-service        │ terminals and followed logs
   │                                        │ (to k8s-service while streams.enabled is false)
═══╪════════════════════════════════════════╪═══ TB2 gateway → backends (NetworkPolicy)
   ▼                                        ▼
 k8s-service × N                          k8s-service-stream × 1
 SERVER_ROLE all | api                    SERVER_ROLE stream
 lists, details, writes, live lists,      pod exec, node shell,
 /internal/* for auth-service and         followed logs, recording writes
 tool-server
   │                                        │
   └──────────────────┬─────────────────────┘
                      │ both reach:
                      ├── auth-service :8004   JWKS, token version
══════════════════════╪═════════════════════════ TB3 backends → PostgreSQL
                      ├── PostgreSQL   audit rows, token_version, recordings, sessions;
                      │                W5: cluster versions, drain progress,
                      │                Claude Code slots
══════════════════════╪═════════════════════════ TB4 backends → Redis
                      ├── Redis / Valkey   cache today; W5: change notices,
                      │                    shared cache, limits (tool-server too)
══════════════════════╪═════════════════════════ TB5 Kubeast → managed clusters
                      ├── API servers of the managed clusters   registered credential,
                      │                                         as the signed-in user
                      └── recording store   S3 or the database
```

Trust boundaries:

- **TB1** browser or API client to the gateway: who the caller is comes from the token alone. The WebSocket handshake also checks Origin.
- **TB2** gateway to the backends: the backends take the client address from the gateway's `X-Real-IP` (`audit.RealIP`). Only the NetworkPolicy keeps other pods from calling them, and only on a CNI that enforces it.
- **TB3 and TB4** backends to PostgreSQL and Redis: a password each, and the NetworkPolicy. Redis has no TLS and one user today. W5 gives each service its own Redis user and turns the `default` user off (row 2.8).
- **TB5** Kubeast to the managed clusters: the cluster's own RBAC also decides, since requests go out as the signed-in user.
- Between replicas there is no trust boundary in memory: a replica holds only its own connections. What one replica writes and another reads goes through PostgreSQL or Redis. W5 keeps in PostgreSQL what must stay right (cluster versions, drain progress, Claude Code slots) and uses Redis for what may be lost (notices that only speed things up, the shared cache, limit counters).

### What changes

1. **A stream server.** One image, three roles (`SERVER_ROLE`, open draft PR #823 `internal/config/role.go`). `all`, the default, serves everything as before. With `streams.enabled: true` (open draft PR #825) the chart runs `k8s-service` as `api` and a second Deployment, `k8s-service-stream`, as `stream`. The gateway sends four paths to it: `…/pods/{name}/exec/ws`, `…/pods/{name}/logs/stream`, `…/pods/{name}/logfiles/stream` and `/api/v1/nodes/{name}/debug-shell/ws` (`internal/routes/streams.go`). When the server holding the terminals is replaced, it ends the followed logs at once (the browser reconnects and goes on after the last line), tells each terminal when it will close, waits `streams.drainSeconds` (60) and closes with 1001 (open draft PR #824 `internal/drain/drain.go`). A new unauthenticated route, `GET /ready`, answers 503 while it drains (open draft PR #824 `internal/handler/health.go`).
2. **Shared state** (W5 plan, decided on 2026-11-14; open draft PRs #857, #858, #859 and #866, M-4's Redis limit counters and shared Network Flow Monitor answers not in a pull request yet). M-2: each cluster has a version number in PostgreSQL, raised in the same transaction that changes the cluster's row; every server compares it on a timer and drops what it built from an older version, and a notice on a Redis channel only makes this faster. M-3 keeps node drain progress in PostgreSQL with its owner and a heartbeat, as open draft PR #851 does for recordings; before it, a small change puts every cache key under `kubeast:cache:` and limits the cache flush to those keys. M-4 counts the limits that protect a managed cluster in Redis, shares Network Flow Monitor answers through the Redis cache, and holds Claude Code runs to an install-wide number of slots in PostgreSQL. M-5 lets one replica write each cluster's health. M-6b gives tool-server the same change notice and keeps its kubeconfig memory to 10 s, and gives each Redis client its own user. Open draft PR #852 gives the audit anchor and the alert webhook one writer each.
3. **Several replicas and HPA** (W5 plan). The chart's refusal of `replicas.k8sService > 1` and `replicas.toolServer > 1` is removed (M-7). HPA can be turned on per service (off by default). Rolling updates, readiness and PDB change for no-downtime replacement (M-6). Drafted in #867 (replicas and `autoscaling`), #856 (a `preStop` wait before SIGTERM), the M-6 branch (`/livez`, `/readyz`, rollouts, PDB, long-lived connections ended on SIGTERM) and #868 (database session limits and a pool size per service).
4. **Role names and cluster groups** (open draft PR #865). A Kubeast role acts on a managed cluster as a Kubernetes group made from its name (`kubeast:role:<slug>`, or the built-in roles' groups). The draft makes the database refuse a role name that makes another role's group, renames on upgrade the roles stored before that and removes their cluster grants, tells a built-in role by its exact name, stops giving a role whose group another role also makes, and writes each character outside ASCII in a group as its code point.
### What is worth protecting here

- A terminal into a container or a node: the most powerful thing Kubeast hands out.
- What a followed log and a terminal show, and the session recording of it, which can hold Secret values printed in the terminal.
- The audit rows and the recordings list, which are evidence.
- The cached answers in Redis, and the access answers (in Redis in `main`, in each process's memory with open draft PR #842).
- The registered cluster credentials, held in each server's connection pool and, for 10 s at most with W5, in tool-server's kubeconfig memory.
- Cluster versions, node drain progress and Claude Code slots in PostgreSQL, and the limit counters in Redis (W5).
- Who is still signed in: the signed-out sign-ins open draft PR #849 keeps in PostgreSQL.
- The Kubernetes groups a Kubeast role gives on a managed cluster, which the cluster's RBAC bindings decide on (change 4).
- The PostgreSQL connections every pod shares, and the locks W5 holds on them (rows 2.13, 3.10).

### Change 2: state moving to PostgreSQL and Redis (W5, open draft PRs #857 to #859, #866 and #868)

Today Redis (Valkey, `images.redis: valkey/valkey:9.1-alpine` in `helm/kubeast/values.yaml`) is the k8s-service cache only:

- It has a password (`--requirepass`, generated at install into `kubeast-secrets`), no TLS, and one `default` user allowed every command.
- `/data` is an emptyDir (`helm/kubeast/templates/redis.yaml`).
- It has no memory ceiling.
- Its NetworkPolicy lets in pods labelled `app: k8s-service`; open draft PR #825 adds `k8s-service-stream`.
- Every backend Deployment gets `REDIS_PASSWORD` through `envFrom` of `kubeast-secrets`. Only the NetworkPolicy keeps the others off.

So whoever can write to Redis today is: a process in a pod with that label, or anyone who can read the Secret and reach the port. On a CNI that does not enforce NetworkPolicy, that is anyone in the cluster who has the password. Valkey's own security page says it is designed for trusted clients inside a trusted environment.

What W5 decided on 2026-11-14 follows one line: Redis holds only what can be lost or changed without changing a decision. Whether a cluster changed, who runs a drain, which Claude Code run holds a slot and who is signed in are read from PostgreSQL. With open draft PR #842, no permission is decided from a Redis value (S-6). A value in Redis can make a server read again from PostgreSQL or the cluster, and the server checks the permission again when it does.

### Change 4: role names and the cluster groups they give (open draft PR #865)

A Kubeast role acts on a managed cluster as a Kubernetes group: the built-in roles as their own groups, and any other role as `kubeast:role:<slug>`, the slug made from its name (`A`–`Z` lowered, other ASCII outside `[a-z0-9._-]` a `-`, any other character `~` and its code point; `services/pkg/auth/impersonation.go` `RoleGroupSlug`). The cluster's RBAC bindings decide what each group may do (TB5), so two roles that make one group get one set of bindings.

Not yet. This page is enough for v0.7.8 when:

- Every "left before release" cell is either merged with its check passing, or accepted on this page with who accepted it and why. OWASP's process asks for the name of whoever accepts a risk.
