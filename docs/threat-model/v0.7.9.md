## 1. What are we working on?

Trust boundaries this page adds to the v0.7.8 page's TB1 to TB5:

- **TB6** ai-service and the model provider: what ai-service sends (the system prompt, the person's messages, tool results) leaves the install; what comes back (text, tool calls) is not trusted. The model decides which tool to call; the server decides whether it runs.
- **Text read from the clusters is not trusted**, whoever wrote it: pod logs, events, annotations, ConfigMap values, describe output, an alert's labels, annotations and its rule's expression, and the alert's two addresses (`generatorURL`, `externalURL`), which the screens draw. Anyone who can write one of them, or holds a cluster's webhook token, can write text the model reads or the screens show.

### What is worth protecting here

- What the AI reads from a cluster: logs, describe output, metric and trace answers, and the personal data in them; Secret values, which are always left out.
- The cluster's state: write and action tools, which wait for the asker's approval.
- The model provider credentials and the Claude Code token, in `kubeast-secrets`.
- The install's own addresses (Prometheus, Alertmanager, the services in the cluster), which the model provider has no need of.
- What the person sees: AI-written text drawn on their screen, and the links in it.
- The investigation records (report, `result`, tool calls) and the audit rows, which say what the AI read and did.
- The stores and API servers the AI reads: one investigation's queries to Prometheus, Loki and Tempo.
- The ways into the console: passwords, single sign-on, and the chart's admin account, the password way in while the provider is down.

### Three properties per session

A session that has untrusted input, sensitive access and a way to change state or send data out turns one planted instruction into an incident ([Agents Rule of Two](https://ai.meta.com/blog/practical-ai-agent-security/)).

| Path | Untrusted input | Sensitive access | Change state or send out | How many |
| --- | --- | --- | --- | --- |
| Alert investigation | yes (the alert, logs, events) | yes (cluster reads as `kubeast:investigator`; Secret values left out) | no write: the read-only list only (row 2.1); outbound held only with `networkPolicy.aiEgress` on (row 5.1) | two |
| Chat, reads | yes | yes (as the asker) | no | two |
| Chat, write tools | yes | yes | yes | three: each write waits for the asker's approval (row 2.1) |

What must hold: no write tool reaches an investigation, and the approval card shows what will run.
