# Changelog

What changed in each Kubeast release, newest first, in the form of [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/). This file starts at 0.7.8. Earlier releases are described on the [GitHub releases page](https://github.com/junginho0901/Kubeast/releases), and each release's notes there list every change with its pull request.

## [Unreleased]

### Changed

- k8s-service builds a Pods page or Cluster View node map answer once for everyone who asks for it at one moment with the same access and the same query, and those who came while it was being built wait for the next one without taking one of the places that hold every pod row. Each person still has their own access checked and gets the bytes they would have got alone.

## [0.7.9] - 2026-11-27

Alert investigations and the AI chat can start from what changed, narrow a namespace down before reading its logs and metrics one by one, read who calls whom and what used a node's CPU, and say which tool call shows each cause and which of three outcomes they reached: a cause found, no fault found or cannot tell. Each of these is a switch, and every new switch is on with `true`, `1`, `on` or `yes` in any case. `features.anomalyRank.enabled` is on by default, which gives AI Chat, the floating chat and the MCP server the tool `anomaly_rank`. For alert investigations, which are off by default, `ai.ruleCards.investigations`, `features.alertInvestigation.rules`, `changesFirst`, `narrowFirst`, `ledger`, `evidenceCheck` and `verdict` are on by default. The others are off. With all of them off, the model is sent what 0.7.8 sent, except that an alert reaches it as its rule's expression, without its links, that a chat question which only names JSON, YAML or wide is offered every tool, that with a Gemini model each tool call goes back with its thought signature, that with provider `anthropic` a call after a tool loop keeps the loop's tools and calls none of them, that a chat answer's last model call calls no tool and is told to answer, that the request for the rest of a cut chat answer is in other words, that on a Claude subscription an alert investigation's closing call and second ask hold the tool results between markers, and that Claude Code receives every prompt as written. What the AI tools `get_pod_metrics`, `issues`, `logsearch`, `alerts_inbox`, `investigations` and `k8s_get_pod_logs` answer changed without a switch too. Beside them, a read of a cluster that gets no answer ends after 20 s, every Kubeast server is ready about a second after it listens, and the gateway behind an AWS Application Load Balancer that sends to pod IPs waits for the load balancer before it stops. An SSO account (one that single sign-on made, `auth_source` `oidc`) no longer signs in with a password. The cluster breakers, the live lists' waits, the node drains, the database pools, Claude Code's slots and the model requests have metrics, with two AI alerts. On Kubernetes older than 1.30 the chart now stops before it changes anything when a pod would get a `preStop` wait, and several Known limits of 0.7.8 are fixed.

### Upgrading from 0.7.8

Read [Upgrading from 0.7.8 to 0.7.9](docs/upgrade-0.7.9.md) first. Some installs have to act:

- On a cluster older than Kubernetes 1.30, the chart now stops at the render, before Helm changes anything, when a pod would get a `preStop` sleep: `podShutdown.preStopSeconds` above 0, the gateway's own wait `gateway.preStopSeconds` above 0, or `streams.enabled`, whose `k8s-service-stream` sleeps `streams.preStopSeconds` whatever `podShutdown.preStopSeconds` is. 0.7.8 applied the other objects and the API server refused those Deployments. Set `podShutdown.preStopSeconds: 0` and leave `streams.enabled` off there, as for 0.7.8, and leave `gateway.preStopSeconds` unset or at 0. Below 1.33 it also stops `streams.enabled` with `streams.preStopSeconds: 0`. `helm template` (also with `--show-only`, as `scripts/render-target-rbac.sh` runs it) checks `--kube-version`, else Helm's own default: on Helm 4.0.0 (v1.20.0) or Helm 3.14 and older (1.29 or older), pass your cluster's version.
- k8s-service and k8s-service-stream no longer take every key of `kubeast-secrets`, or of the Secret in `secrets.existingSecret`, as environment. They read `DATABASE_URL`, `INTERNAL_API_TOKEN`, `REDIS_PASSWORD` while the Redis users are off, and `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY` when the Secret holds them. With `secrets.existingSecret`, any other key you put there for k8s-service no longer reaches it, also one named as a key of `kubeast-config`, whose value it took the place of (the Secret came after it in `envFrom`; k8s-service now reads `kubeast-config`'s value), and a lower-case `http_proxy`, `https_proxy` or `no_proxy`. List the key names, not their values, with `kubectl -n <namespace> get secret <name> -o go-template='{{range $k, $v := .data}}{{$k}}{{"\n"}}{{end}}'` before you upgrade.
- With the chart's PrometheusRule on (`metrics.enabled` and `metrics.prometheusRule.enabled`), a default install has six alerts, not five: `KubeastAIModelUnreachable` renders whenever `ai.enabled` is on, which is the default. It fires when, for 10 minutes, the last 10 minutes held three or more model requests that failed and none that was answered. `KubeastAIInvestigationsFailing` renders only with `features.alertInvestigation.enabled`. Both are `severity: warning`. Route them in Alertmanager before you upgrade.
- Every Kubeast server gets readiness every 3 s with no initial delay and a startup probe every second (`podStartup.quickReady`, on by default), so the upgrade rolls all of their pods with the new probes. Set `podStartup.quickReady: false` to keep 0.7.8's probes.
- The built-in Read role gets the permission `ai.tool.anomaly_rank` at start-up (the tool is on by default), and Write already holds `ai.tool.*`. A custom role that lists the AI tools one by one gets the new tool only when `ai.tool.anomaly_rank` is added to it.
- Behind an AWS ALB that sends to pod IPs, the gateway pods now wait 25 s and the target group drains 20 s; to keep 0.7.8's, set `gateway.preStopSeconds: 5` and write `deregistration_delay.timeout_seconds=300` in `alb.ingress.kubernetes.io/target-group-attributes`. The first upgrade from 0.7.8 still stops the gateway pods with 0.7.8's 5 s wait, so behind such a load balancer it can have 502 and 504, unless 0.7.8 already ran with `podShutdown.preStopSeconds: 25` and a 20 s deregistration delay.
- `features.anomalyRank.enabled` is on by default: the AI tool `anomaly_rank` and its route answer on a default install, read as the caller. `ai.ruleCards.investigations`, `features.alertInvestigation.rules`, `changesFirst`, `narrowFirst`, `ledger`, `evidenceCheck` and `verdict` are on by default too and change only alert investigations, which stay off (`features.alertInvestigation.enabled`). Set a switch to `false` to keep 0.7.8's behaviour. Under Docker Compose they stay off, since it passes none of them.
- Changes to the AI with no switch: an image in AI-written text is drawn as a link, an alert reaches the model as its rule's expression, without its links, a chat question is held to one output form's tools only when it asks for that form, with a Gemini model each tool call goes back with its thought signature, with provider `anthropic` a call after a tool loop keeps the loop's tools and calls none of them, a chat answer's last model call calls no tool and answers, the request for the rest of a cut chat answer is in other words, on a Claude subscription the calls that close a chat answer or an alert investigation and an investigation's second ask hold the tool results between markers, Claude Code receives every prompt as written, and what the AI tools `get_pod_metrics`, `issues`, `logsearch`, `alerts_inbox`, `investigations` and `k8s_get_pod_logs` answer changed (see Changed and Fixed).
- A chat answer may make 20 model calls (`ai.chat.maxSteps`, 1 to 100), where it made 10, so one answer can use more tokens. The chat token budgets are checked when a turn starts, not between its calls. `ai.chat.maxSteps: 10` keeps 0.7.8's number.
- Every new switch but `podStartup.quickReady` and the AI switches above is off by default, `multicluster.maxStreamsPerServer` (443) and `ai.chat.maxSteps` (20) have no switch and are always read, and the other new values that are neither off nor empty (`features.alertInvestigation.window.*` 15, 5 and 4, `features.anomalyRank.maxQueries` 12, `features.anomalyRank.logMaxBytes` 10 GiB and the other limits of `features.anomalyRank.*`) are read only while their switch is on, the windows of alert investigations only while `features.alertInvestigation.enabled` is; `gateway.preStopSeconds` is empty by default. A values file from 0.7.8 needs no change other than those the other lines in this section name. A script that reads one of the API answers under Changed may have to change. Upgrade with `--reset-then-reuse-values`: `--reuse-values` stops with that hint, as in 0.7.8, and `podStartup.quickReady` is in the chart's upgrade check.
- A cluster reached through a proxy that drops the `Audit-ID` header: an error status without that header is now read as coming from in front of the API server, so the health check's `/version` answered so opens the breaker. A status below 400 still counts as an answer without it. Let the proxy pass `Audit-ID`.
- Behind PgBouncer, keep session pooling: the retention purge now holds a session advisory lock while it runs, beside the migrations', the audit sinks' and k8s-service's health status lock.
- The retention purge's lock holds a connection of its own outside auth-service's pool while a run goes, so the chart counts one more connection per rolling auth-service pod against `postgresql.maxConnections`: 156 for one pod of each service with the AI on (was 154), 290 for three of each (was 286), and 310 with `streams.enabled` (was 306). A `postgresql.maxConnections` set to 0.7.8's sum, or above it by less than the rolling auth-service pods, stops the render with the new sum; with an external database, the install notes print the new sum. A new `postgresql.maxConnections` replaces the bundled PostgreSQL pod during the upgrade, and writes and sensitive reads answer 503 `audit unavailable` until it is back.
- An SSO account no longer signs in with a password, also one an admin's reset gave it in 0.7.8 or earlier: whoever signed in that way signs in through the provider. Such an account's `POST /api/v1/auth/change-password` answers 400 as well, so a script that changed its password through the API stops there. The chart's admin account (the account stored under `admin.email` as written) still signs in with its password, whatever made it. A session such a password opened before the upgrade goes on until `auth.sessionAbsoluteHours` (8 by default), unless an admin ends that account's sessions sooner by setting its role (`role_id` in `PATCH /api/v1/auth/admin/users/{user_id}`), also to the role it has. [Upgrading from 0.7.8 to 0.7.9](docs/upgrade-0.7.9.md#17-single-sign-on-accounts-and-passwords) counts such accounts.
- Self sign-ups that a single sign-on sign-in reached while they waited for approval become SSO accounts at the upgrade, also once an admin approved them or gave them a password (see Changed): a password one holds no longer signs it in, and its sessions end, so that person signs in through the provider. [Upgrading from 0.7.8 to 0.7.9](docs/upgrade-0.7.9.md#17-single-sign-on-accounts-and-passwords) counts the accounts whose password stops signing them in.
- With `auth.passwordLogin: admin-only`, a password account whose address differs from `admin.email` only in letter case is refused after the upgrade (see Changed). An install that later wrote `admin.email` in other letters keeps its old admin account under the old letters, which is now refused: write `admin.email` in the letters that account is stored under. [Upgrading from 0.7.8 to 0.7.9](docs/upgrade-0.7.9.md#4-what-changes-by-itself) says so.

### Added

- A "what changed" view of the timeline (`ai.timelineChanges`): `GET /api/v1/timeline/changes` and `GET /api/v1/namespaces/{namespace}/timeline/changes` list what changed in a window (the last 4 h by default), newest first. They list rollouts with the image before and after and the names of the other fields that changed, ConfigMap and Secret writes read from their metadata only, Helm release revisions, HPA scale times, node creations and condition changes, Argo CD history and failed operations, and container restarts with their reason and exit code. A source the caller may not read is named as not read. The AI tool `timeline` takes `view: "changes"`. Off, both routes answer 404 unless alert investigations read the changes (`changesFirst`). Without `ai.timelineChangesMore` the view does not list a replica count set without a new revision (`kubectl scale`, a scale button), a deleted object or a change to another kind, and the tool's description and the chat's instructions say so.
- More of the "what changed" view (`ai.timelineChangesMore`, alpha, off by default; alone it opens nothing): in a named namespace the view also lists the Jobs made in the window with the CronJob, other controller or field manager that made each (the newest 15, at most four of one CronJob, all counted), NetworkPolicy writes, Service writes by a manager that sets its selector or ports, and replica counts set on a Deployment or by a write on a StatefulSet: when, by which field manager and which fields, never a value. A Deployment's scale carries the time its ReplicaSet's count was set, since the API server keeps none for the scale itself, and a note says so. Each kind is one list more, read as the person and as metadata only: four a call, five where the namespace may have a StatefulSet, none without a namespace. A kind the person may not list is named as not read.
- Time windows and rules for alert investigations (`features.alertInvestigation.rules`, `changesFirst`, `window.metricsMinutes`, `logsMinutes`, `changesHours`): an investigation reads metrics, logs and changes over windows set from the alert's start (15 minutes, 5 minutes and 4 h by default). With `rules` it writes its report under Summary, Scope, What I checked, Likely cause, Ruled out and Next steps, and with `changesFirst` it reads the changes before the model's first turn.
- The AI tool `anomaly_rank` and its route `GET /api/v1/namespaces/{namespace}/anomalies` (`features.anomalyRank`, beta, on by default): what in one namespace differs from the window just before, ranked, from its issues, crash reasons, restarts, memory near the limit, CPU throttling, the conditions of the nodes its pods run on (not how busy their CPU is) and, with a log or trace store set, error log shapes and counts and changes in trace requests, errors and latency. Each check is a finding, normal, or not run with the reason; a check that had nothing to read in the window is not run. A finding is called new only when the window before has data and none of it. Without that data its summary says `no earlier data`, and it comes after the new findings and those that are critical now. A check that ran on part of what it reads (a list it could not read beside its findings, a log or trace answer past the 100 series its reader keeps, or a service whose p90 has nothing before to be compared with) is also listed under `partial`, with what it did not read. Narrowed to one workload, it matches that workload's pods by the names its controller gives them, so `cart` leaves out the pods of `cart-api`. One answer reads the stores at most 12 times (`features.anomalyRank.maxQueries`), 5 s a check and 20 s in all, 4 at once, and is kept 60 s; a metric check is one query over both windows, from 12 up three queries are kept for the call order (`features.callGraph`), and every read of a log line counts as one; the log checks are not run when Loki estimates more than `features.anomalyRank.logMaxBytes` (10 GiB). When Loki's index counts no lines over the window they read one line and are listed as not run only when that read finds none too, since Loki's index statistics leave out lines its ingesters have not flushed. It needs `resource.objects.read`; a grant limited to namespaces gets no metric checks, and the log and trace checks follow the rules of the log and trace tools.
- A size limit for the AI tool `loki_query` (`features.logSearch.queryMaxBytes`, 0 = off): a query whose streams Loki estimates past it is answered 400 with the size and how to narrow it.
- The narrowing as an alert investigation's first step (`features.alertInvestigation.narrowFirst`, with `features.anomalyRank`): after the changes, `anomaly_rank` is called once for the alert's namespace over the metrics window, without spending a model step. With this or `changesFirst`, the first step's answers follow the first message as calls and their tool results, as the model's own calls do; on the Claude subscription, which has no place for a tool result before its first turn, they stay in the first message between markers.
- Calls between workloads (`features.callGraph`): the AI tool `resource_graph` takes `include: ["calls"]` and a window and answers who calls whom in a namespace, from the service graph metrics of Tempo, the OpenTelemetry Collector or Alloy in the cluster's Prometheus and from Hubble's traffic metrics, with the workloads most likely at fault and paths from cause to symptom. `anomaly_rank` then orders the findings of those workloads cause before symptom. Without the namespace on the service graph metrics it reads the busiest 500 edges: an edge outside the 500 with the most failed calls then has `errors` and `error_ratio` null, not 0, and a query that brings back 500 series marks the trace source `truncated`. [Cluster requirements](docs/cluster-requirements.md) has the settings the metrics need.
- One node's neighbours (`features.nodeNeighbors`, alpha, off by default): the AI tool `get_node_metrics` takes a `node` and a window (the last 30 minutes by default), and `GET /api/v1/nodes/{name}/neighbors` answers what used that node's CPU against the window of the same length before it: the containers of every namespace on the node by cores, with what each grew by, its request, limit and start, its throttling and the time it waited for a CPU, the node's CPUs one by one, and the containers to suspect, their likely victims (slowed, not throttled, while the node was busy) and those stopped by their own limit, a suspicion, not proof. Namespaces whose pods the person may not list are counted, not named. It reads the cluster's Prometheus and the metrics API, at most six reads an answer; without Prometheus it gives current values and no role, and a grant limited to namespaces is refused the tool. Off, the route answers 404 and the tool takes no node.
- Repeated reads refused (`ai.refuseRepeatedReads`): a read tool called again with the same arguments within one chat answer or one investigation, less than 60 s after the first call answered, is not run, and the model is pointed to the first result. Write and action tools are never refused. Such a call's `ai.tool.call` audit row has `status: repeated` and `repeat_of`.
- The chat's rules for why questions (`ai.causeQuestions`, alpha, off by default): for a question that asks why something is broken, the chat's instructions say what to check before the answer (whether the symptom was there, what changed as a candidate only, the caller's and the callee's logs, a crashing pod's configuration, the node and its other namespaces when unrelated workloads slow together and none is throttled, and what could not be read, which is not the same as normal) and ask for one of three outcomes: cause found with the call that showed the symptom, no fault found with what was checked, or cannot tell with what is missing. A name not found ends the search for that name, not the reading. Such an answer reads more and uses more tokens. AI Chat only, and best on together with `ai.toolResultDetails`.
- Causes checked against the calls (`features.alertInvestigation.evidenceCheck`): each tool result an investigation reads carries its call number, the report ends with a block of causes citing those numbers, and a cause its call does not show, or that also cites a call that did not answer, is asked about once more, then listed under the report as not confirmed by the server. A block that says it found no fault beside a cause is asked for once more too.
- The hypothesis ledger (`features.alertInvestigation.ledger`): the report's causes, path, ruled-out list and hypotheses are kept with the investigation and shown under the report in Admin → Investigations and the Alerts inbox, each hypothesis with the calls for and against it. The investigation API and the MCP `investigations` read return them as `result`. The result keeps at most 10 causes, 12 path steps, 20 ruled-out objects, 12 hypotheses and 20 call numbers per cause and per side of a hypothesis; a longer list keeps its first items and says how many were given and kept in `cut`, and the report window says under it "Showing the first M of N: the server did not keep the rest." With this switch or the evidence check on, an investigation's model calls answer with up to 4,096 tokens, and a run may take one more step.
- The outcome of an alert investigation (`features.alertInvestigation.verdict`, alpha, on by default; nothing with both `evidenceCheck` and `ledger` off): the block at the end of the report also says which of three outcomes the investigation reached (a cause found, no fault found or cannot tell) and which calls show the alert's symptom, and the prompt has the model find that symptom first and use the calls it has left before it answers cannot tell. The server holds the block to the run's calls: a report that names a cause needs a call that answered and names what the alert is about (for the lines of a pod's log, the pod it was read of), a cause found needs a cause the calls show, and no fault found needs a call that names that workload or object, or read its namespace. What does not hold is in the one second ask; of an answer that still does not hold the server keeps cannot tell, with the reasons under the report and the causes as the model gave them. The report window, the investigation API and the MCP `investigations` read (`result.verdict`) show the outcome with three lists the server makes from the run's calls alone: looked at, checked and normal, and not looked at.
- Tool result details (`ai.toolResultDetails`): a tool result says what was cut (such as "M of N series"), the window it read when none was given, and why an empty result may be empty; in the chat and in investigations a read result starts with links to the console pages of what it names. The kubectl read tools say it too, for events, a list of one kind, a pod log or a `grep` without a match, pod metrics and the endpoints of a Service. `k8s_find_resource` also looks among the namespaces' names and, when nothing matched, says not to repeat the search and to go on with what is known, where it said to stop searching. Nothing more is read for this but that one list.
- Rule cards (`ai.ruleCards.chat`, off; `ai.ruleCards.investigations`, on by default): 13 cards by kind of failure (crash, out of memory, image, config change, rollout, network policy, DNS, resource limit, quota, node, a dependency down, a dependency slow, storage), each with checks in order and the read-only tools that answer them. The server picks at most two from the alert or the question (the cards `error_rate`, `latency` and `resource_pressure` only with `ai.ruleCards.symptoms`); `ai.ruleCards.cards` adds or replaces cards and `ai.ruleCards.remove` drops default ones.
- Rule cards picked by a symptom (`ai.ruleCards.symptoms`, alpha, off by default; with `ai.ruleCards.chat` or `ai.ruleCards.investigations` on): a card is also picked by what is said to be wrong, in English or Korean: an alert name such as `HighErrorRate`, or a phrase such as "requests are slow", in the question or in an alert's name, labels, summary, description and message. One word alone picks nothing. It adds the cards `error_rate`, `latency` and `resource_pressure`, 16 in all. The alert's text picks the card and does not go into it.
- Numbered placeholders for personal data (`ai.redaction.numbered`, with `ai.redaction.pii`): emails, phone numbers, resident registration numbers and card numbers become `<EMAIL_n>`, `<PHONE_n>`, `<RRN_n>` and `<CARD_n>`, one number per value across a chat answer or an investigation, and a write holding one is refused. The person who asked sees the values in their own chat answer, while the model, the stored answer, logs and audit rows keep the placeholders; after a reload the placeholders show.
- Cluster text as JSON tool results (`ai.toolResultsJSON`): each tool answer reaches the model as one JSON object in the tool result's place, with logs, describe output, YAML and command output as a JSON string.
- Outbound connections of the AI services held to listed addresses (`networkPolicy.aiEgress.allowListOnly`, `clusterAPIs`, `stsEndpoints`): outside the cluster network, ai-service reaches only `networkPolicy.allowExternalEgressCIDRs` and tool-server only the listed API servers and STS endpoints. The render stops with the reason when a list it needs is empty, and [Cluster requirements](docs/cluster-requirements.md) §15 says what stops when a list is short.
- `gateway.servedByHeader` (alpha, off by default): every answer the gateway sends, its own 502, 503 and 504 included, carries `X-Kubeast-Gateway` with the name of the gateway pod that sent it, to tell in a rollout test which pod answered each request. With it on, clients see the gateway pod names; off, the gateway's nginx configuration has no such line. Docker Compose never sends it.
- Metrics on k8s-service's `/metrics`: the cluster breakers (`kubeast_k8s_cluster_breakers_open`, `kubeast_k8s_cluster_breaker_opens_total{by}`, `kubeast_k8s_cluster_breaker_refusals_total`), the live lists' waits for their places and for memory (`kubeast_ws_watch_place_wait_seconds{places}`, `kubeast_ws_watches_waiting_for_place{places}`, `kubeast_ws_watch_memory_waits_total`, with a log line), the node drains (`kubeast_k8s_node_drains_running`, `kubeast_k8s_node_drains_holding`, `kubeast_k8s_node_drains_ended_total{status}`) and the Redis commands refused for the service's user (`kubeast_redis_refusals_total{command}`, with a log line). They also cover the `kubeast:cache` client's rate wait (`kubeast_k8s_client_rate_wait_seconds{limiter="cache"}`) and the waits for read places (`kubeast_k8s_read_place_wait_seconds{places}`: `node_pods` and `event_list` for a cluster's places, `big_read` for k8s-service's big read places). None has a cluster, user or route label.
- A metric of the waits of the node list, node box and shared read answers past 256 KiB for k8s-service's 16 write places, `kubeast_shared_write_place_wait_seconds{places="big_write"}`. It counts each take of a place, before a body's first part and after each part slower than 100 ms, a take that ended at the body's second or when its caller left too, and a take that reached that second up to it, so no observation is above 1 s. It has no cluster, user or route label.
- A cap on the terminals (pod exec, node shell) and followed logs each k8s-service holds open for all accounts together (`multicluster.maxStreamsPerServer`, 443, 0 = no cap; k8s-service-stream with `streams.enabled`): one past it is refused before it opens, as at an account's cap, with a failed audit row and a line on the screen saying the server is full. Refusals are counted in `kubeast_stream_server_cap_refusals_total`.
- Database pool metrics of auth-service, k8s-service, session-service and ai-service: `kubeast_db_pool_connections{state}` and `kubeast_db_pool_max_connections`, and in the Go services the takes of a connection that found none idle (`kubeast_db_pool_empty_acquires_total`, `kubeast_db_pool_empty_acquire_wait_seconds_total`) or gave up (`kubeast_db_pool_canceled_acquires_total`).
- ai-service metrics: model requests by outcome (`kubeast_ai_model_requests_total{outcome}`), alert investigations' ends (`kubeast_ai_investigations_total{outcome}`) and the Claude subscription provider's places (`kubeast_claude_code_runs{lane}`, `kubeast_claude_code_waiting`, `kubeast_claude_code_slot_wait_seconds`, `kubeast_claude_code_busy_total`). None has a provider, model, cluster or user label.
- The alerts `KubeastAIModelUnreachable` (with the AI on: for 10 minutes, three or more model requests failed and none was answered) and `KubeastAIInvestigationsFailing` (with alert investigations on: over an hour, three or more failed and more than half of those that ended, for 15 minutes), in `metrics.prometheusRule`.
- The release attests an SBOM of each image's arm64 variant beside the amd64 one, on the manifest list, and runs a trivy gate on each variant's own digest: `gh attestation verify oci://<image>:<tag> --predicate-type https://spdx.dev/Document/v2.3` lists both, and [Supply chain](docs/supply-chain.md) picks one by `arch=`.
- `scripts/verify-release.sh vX.Y.Z [commit]` checks a published release from outside, read-only: each image's provenance, SBOM attestations and cosign signature as `docs/supply-chain.md` gives them and narrowed to the release, both platform variants, the chart's provenance and signature, four checks that must be refused, and the image references of the chart's default render.
- [Upgrading from 0.7.8 to 0.7.9](docs/upgrade-0.7.9.md) (en, ko), linked from the README and Getting started.
- A [threat model page](docs/threat-model/v0.7.9.md) for the v0.7.9 changes.
- Row 2.13 of the [v0.7.8 threat model page](docs/threat-model/v0.7.8.md) now says that pgx sends a cancel request on a separate connection before it closes the connection.
- [Cluster requirements](docs/cluster-requirements.md) §14 (en, ko) says that the trace store and the alert store are one each for the install, shared by every registered cluster, unlike the log store: a cluster whose spans or alerts go to another store gets no AI trace or alert reads.

### Upgrading from 0.7.7

Read [Upgrading from 0.7.7 to 0.7.8](docs/upgrade-0.7.8.md) first. Some installs have to act:

- The cluster Kubeast runs in needs Kubernetes 1.30 or later for the pod shutdown wait. On an older one, set `podShutdown.preStopSeconds: 0`.
- `pdb.minAvailable` is no longer read. An upgrade that still sets it stops and says to set `pdb.maxUnavailable`.
- With auth-service, session-service and ai-service at 4 pods each, the database connections add up to 319, past the chart PostgreSQL's 300, and the upgrade stops at the render check. Raise `postgresql.maxConnections` or lower `postgresql.pool.<service>.maxConns` before you upgrade.
- A custom role whose name makes another role's group (`a-b` beside `a b`, `ADMIN` beside the built-in `Admin`) is renamed and loses its cluster grants. Role names outside ASCII get new groups (`운영팀` acts as `kubeast:role:~c6b4~c601~d300`, it was `kubeast:role:---`), so RBAC bound to the old group on registered clusters has to be bound to the new one. Back up the database first: a rollback does not undo the renames.
- Finish node drains in progress before you upgrade.
- The default model is `gpt-6-luna`. Saved model settings, an `ai.model` in your values and a Compose `.env` keep their model; change those that name `gpt-4o-mini`, which OpenAI shuts down on 2027-01-14, before then.
- With `secrets.existingSecret`, Redis keeps one password until the per-service Redis users' passwords are in a Secret (`redis.acl.existingSecret`, or the main Secret with `redis.acl.existingSecretHasKeys: true`).
- On each registered cluster other than the one Kubeast runs in, apply the RBAC again ([Cluster requirements](docs/cluster-requirements.md) §1): the ClusterRole the docs give a registered cluster's credential now also gets the `kube-system` Namespace, whose UID refuses a second entry for a cluster and another cluster's kubeconfig in a registered cluster's place. Until it is applied, both checks are skipped for that cluster.
- One account may hold 20 terminals and 20 followed logs open on each k8s-service, and one past either is refused before it opens. Where one account needs more (a shared account, or a script with an API key, which counts with its owner), raise `multicluster.maxTerminalsPerAccount` or `multicluster.maxFollowedLogsPerAccount`; `0` turns a cap off.
- Upgrade with `--reset-then-reuse-values`. `--reuse-values` stops with that hint, as in 0.7.7.
- Requests can fail for a short while during this upgrade, and people using Kubeast then may have to sign in again: the 0.7.7 pods stop without a `preStop` wait, and the chart's PostgreSQL and Redis restart once. Upgrade when few people use Kubeast ([Upgrading from 0.7.7 to 0.7.8](docs/upgrade-0.7.8.md#2-upgrade)).

### Changed

- The default AI model is `gpt-6-luna`, in place of `gpt-4o-mini`. Docker Compose without `.env` runs it too, in place of `gpt-4`.
- Cluster requests go as the signed-in person: the server version and API discovery reads a screen opens now name the person in the target cluster's audit log, and a request whose context names no person is not sent unless it is Kubeast's own, which is only a `GET` of the server version or an API discovery path (`/version`, `/api`, `/apis`, `/api/v1`, `/apis/<group>/<version>`).

- Service Deployments roll one new pod at a time and stop an old one only once the new one is ready.
- The migration Job runs each try in a pod of its own and ends at 10 minutes.
- k8s-service's cluster breaker tries one request again after `multicluster.breakerOpenSec`, `multicluster.breakerConsecutiveFails: 0` turns it off, and only a request whose calls could not reach the API server counts as a failure. Its health check reads each cluster's `/version` behind none of the people's requests, and an answer below 500 closes the breaker.
- New live lists wait while k8s-service is short of memory, past 80 % of its Go memory limit, with a notice on the page.
- A grant limited to namespaces opens the Dashboard with fewer requests to the cluster, and an idle live-list socket holds 18 KiB instead of 47 KiB.
- Cluster View's node boxes are answered from the pod rows k8s-service keeps, once its informers run, instead of a list of the node's pods, and a pod's window opened from a box reads the pod before it shows its containers.
- Cache keys move under `kubeast:cache:`, and a cluster change deletes only those keys.
- Alert start times are kept in UTC, whatever offset the sender writes.
- Docker Compose gives the Kubeast services 35 s to stop and PostgreSQL and Redis 30 s (Docker's default is 10 s).
- API answers: a Deployment row carries `current_replicas`, event frames carry `involved_object.uid`, `/cluster/api-resources` lists resources in kubectl's order, `GET /auth/roles` adds `same_group_as`, and `GET /cluster/pods/on-node` answers a box row per pod: the full row's `name`, `namespace`, `node_name`, `pod_ip`, `status`, `phase`, `restart_count`, `created_at` and `labels`, with `health` and `health_reason`, and no containers; an audit log list or export whose `since` or `until` is not an RFC 3339 time answers 400, where it left that bound out; a token whose session cannot be read is answered 503 with `Retry-After` where 0.7.7 answered 401, a live socket or terminal left unchecked for 5 minutes closes with 1013 instead of 4401 `session_unverified`, a watch frame's `limit_scope` can be `opening` (a watch waiting its turn to open), and the Helm releases stream's event id names the cluster, its registration's `config_version`, a tag of the person and each watch's version (`helm-releases/<cluster>/<config_version>/<person>?<namespace>=<resourceVersion>&…`, where it was always `helm-releases`); a terminal socket past its account's cap closes with 4429 `terminal_limit`, and a followed log past it is answered 200 with the event `stream-limit` and ends.
- A read of a Prometheus, OpenCost, Hubble Relay or Calico Whisker Service through a cluster's API server follows a redirect only on that API server and under the Service's proxy path, and a flow source registered by address follows none; any other redirect is a 502 with the reason. A 401 or 403 that a Prometheus or OpenCost Service writes itself is a 502 with its words, so it no longer signs the person out; the API server's own refusal of the proxy stays a 403, and its 404 for a Prometheus Service that is not there is a 502.

### Security

- Signing out ends the sign-in on the server ([GHSA-58jr-j4jf-w6hr](https://github.com/junginho0901/Kubeast/security/advisories/GHSA-58jr-j4jf-w6hr)). Up to 0.7.7 it only cleared the session cookie: when another person signed in on the same tab without a reload, the tab's live lists kept following with the first person's identity, and the first person's terminals and followed logs in other tabs kept running for up to `auth.sessionAbsoluteHours` (8 by default) after that sign-in. This needed one browser shared by two people.
- Custom roles no longer share one cluster group ([GHSA-58jr-j4jf-w6hr](https://github.com/junginho0901/Kubeast/security/advisories/GHSA-58jr-j4jf-w6hr)). Up to 0.7.7, the group a role acts as on a cluster was its name lowercased, with spaces at either end dropped and each other character outside `a-z`, `0-9`, `.`, `_` and `-` written as `-`, so `Ops` and `ops`, `a b` and `a-b`, and `운영팀` and `개발팀` (both `kubeast:role:---`) each acted as one group and the members of each role got the cluster bindings made for the other. 0.7.6 refused new names like that, but roles stored before 0.7.6 kept the shared group. Bind the new groups of role names outside ASCII on your clusters, and check the roles the upgrade renamed, as Upgrading from 0.7.7 says.
- A redirect from a Service that Kubeast reads through a cluster's API server is followed only on that API server ([GHSA-2hh4-6h6c-6979](https://github.com/junginho0901/Kubeast/security/advisories/GHSA-2hh4-6h6c-6979)). Up to 0.7.7 such a redirect could carry the cluster's credential to another host: when a Prometheus, OpenCost, Hubble Relay or Calico Whisker Service answered a read with a redirect to another host, Kubeast followed it and sent that host the cluster's credential, when it is a token, and the headers that name the signed-in person. This needed someone who could change what answers behind such a Service, or create a Service and a pod where Kubeast looks for one: for Prometheus when Kubeast finds it itself, and for OpenCost in `opencost`, `kubecost`, `monitoring` or `cost`. Where that was possible, replace the token in that cluster's kubeconfig and revoke the old one; the advisory says which credentials need nothing.
- `go.opentelemetry.io/otel/trace` 1.47.0 in tool-server's kubectl module (GHSA-q7gw-24fr-5p69).
