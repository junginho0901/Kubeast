# Changelog

What changed in each Kubeast release, newest first, in the form of [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/). This file starts at 0.7.8. Earlier releases are described on the [GitHub releases page](https://github.com/junginho0901/Kubeast/releases), and each release's notes there list every change with its pull request.

## [0.7.8] - Unreleased

Kubeast can run more than one pod of a service. k8s-service and tool-server run several replicas with the chart's Redis, each of the seven services can have an HPA, and what one server kept in its memory (cluster changes, node drain progress, Claude Code runs, session recordings, the audit anchor) moves to PostgreSQL, so another server reads the same. Pods being replaced finish what they hold before they stop.

### Upgrading from 0.7.7

Read [Upgrading from 0.7.7 to 0.7.8](docs/upgrade-0.7.8.md) first. Some installs have to act:

- The cluster Kubeast runs in needs Kubernetes 1.30 or later for the pod shutdown wait. On an older one, set `podShutdown.preStopSeconds: 0`.
- `pdb.minAvailable` is no longer read. An upgrade that still sets it stops and says to set `pdb.maxUnavailable`.
- With auth-service, session-service and ai-service at 4 pods each, the database connections add up to 319, past the chart PostgreSQL's 300, and the upgrade stops at the render check. Raise `postgresql.maxConnections` or lower `postgresql.pool.<service>.maxConns` before you upgrade.
- A custom role whose name makes another role's group (`a-b` beside `a b`, `ADMIN` beside the built-in `Admin`) is renamed and loses its cluster grants. Role names outside ASCII get new groups (`운영팀` acts as `kubeast:role:~c6b4~c601~d300`, it was `kubeast:role:---`), so RBAC bound to the old group on registered clusters has to be bound to the new one. Back up the database first: a rollback does not undo the renames.
- Finish node drains in progress before you upgrade.
- The default model is `gpt-6-luna`. Saved model settings, an `ai.model` in your values and a Compose `.env` keep their model; change those that name `gpt-4o-mini`, which OpenAI shuts down on 2027-01-14, before then.
- With `secrets.existingSecret`, Redis keeps one password until the per-service Redis users' passwords are in a Secret (`redis.acl.existingSecret`, or the main Secret with `redis.acl.existingSecretHasKeys: true`).
- On each registered cluster other than the one Kubeast runs in, apply the RBAC again ([Cluster requirements](docs/cluster-requirements.md) §1): the ClusterRole the docs give a registered cluster's credential now also gets the `kube-system` Namespace, whose UID refuses a second entry for a cluster and another cluster's kubeconfig in a registered cluster's place. Until it is applied, both checks are skipped for that cluster.
- One account may hold 20 terminals and 20 followed logs open on each k8s-service, and one past either is refused before it opens. Where one account needs more (a shared account, or a script with an API key, which counts with its owner), raise `multicluster.maxTerminalsPerAccount` or `multicluster.maxFollowedLogsPerAccount`; `0` turns a cap off.
- Upgrade with `--reset-then-reuse-values`. `--reuse-values` stops with that hint, as in 0.7.7.

### Added

- More than one replica: `replicas.k8sService` and `replicas.toolServer` above 1 with `redis.enabled: true`; `autoscaling.<service>`, an HPA on CPU for each of the seven services, off by default; a PodDisruptionBudget for each Deployment that can be down to two pods or more (`pdb.enabled` is now `true`, `pdb.maxUnavailable` 1). See [Running more than one replica](docs/high-availability.md).
- A shutdown wait before SIGTERM for pods behind a Service (`podShutdown.preStopSeconds`, 5 s). `/livez` and `/readyz` on every Go service. When a pod stops, live lists and followed logs reconnect to a pod that stays, and a terminal ends with a line saying the server is restarting.
- A stream server of its own for terminals, node shells and followed logs (`streams.enabled`, off by default). Open terminals get `streams.drainSeconds` (60) when it is replaced.
- A cap on the terminals (pod exec, node shell) and followed logs one account holds open on each k8s-service (`multicluster.maxTerminalsPerAccount`, `multicluster.maxFollowedLogsPerAccount`, 20 each, 0 = no cap): one past it is refused before it opens, with a failed audit row and a count in `kubeast_stream_cap_refusals_total`, and the terminal or log window says why.
- One Redis user per service on the chart's Redis (`redis.acl.enabled`, on by default; passwords in the Secret `kubeast-redis-users`).
- Database session limits on every service's connections (`postgresql.sessionLimits`, on by default), a pool size per service (`postgresql.pool.<service>.maxConns`) and a render check of their sum against `postgresql.maxConnections` (300). Behind PgBouncer, use session pooling.
- Install-wide Claude Code slots in the database (`ai.providers.claudeCode.maxConcurrentTotal`, `queueWaitSeconds`, `memoryLimit`). A chat turn waits for a slot and says so.
- Node drain progress in the database: a drain cut short reads "Interrupted", with Start again.
- Live lists come back a few at a time after a restart (`multicluster.wsWatchOpeningConcurrency`, 8; one that waits more than 10 s for its turn says so on the page, apart from the memory notice) and are asked as watch lists; each list's HTTP/2 window is `multicluster.wsWatchStreamWindowKiB` (1 MiB).
- Allowed read checks of the screens served from Kubeast's shared cache can be asked once per group set instead of once per person (`sharedReadChecks.enabled` in the chart's `auth` settings, beside `customRoles`, off by default). Turn it on only where every authorizer of the cluster answers by groups as RBAC does; [Cluster requirements](docs/cluster-requirements.md) §1 has the commands that check it.
- Metrics on k8s-service's `/metrics`: `kubeast_k8s_client_rate_wait_seconds`, `kubeast_k8s_client_rate_waits_total`, `kubeast_k8s_access_reviews_total`, `kubeast_terminals_open` and `kubeast_followed_logs_open`. `gateway.accessLog.upstreamTimes` adds each request's upstream times to the gateway's access log.
- The alert `KubeastAuditAnchorStalled` (`metrics.prometheusRule`), with an audit anchor sink set: no anchor written for twice `audit.integrity.anchor.hours` (whole hours). When auth-service cannot read the last anchor at start it reads it again every minute, so the gauge behind the alert does not stay 0 until the next anchor.
- GPT-6 Sol and GPT-6 Luna (`gpt-6-sol`, `gpt-6-luna`) in the OpenAI model list, sent with `reasoning_effort: "none"` so their tool calls go through.
- Cluster View pages its node boxes, ten a page with up to twelve pod cards each, and opens a node's own view with all its pods. The node map can be used with a screen reader.
- The floating chat opens and closes with ⌘/ on a Mac and Ctrl+/ elsewhere.
- [Upgrading from 0.7.7 to 0.7.8](docs/upgrade-0.7.8.md) and a [threat model page](docs/threat-model/v0.7.8.md) for this release.
- For development: `scripts/upgrade-rehearsal.sh`, which upgrades the previous release to the checkout on a kind cluster of its own, and the opt-in e2e projects `fault`, `rollout` and `ai-layers`.

### Changed

- The default AI model is `gpt-6-luna`, in place of `gpt-4o-mini`. Docker Compose without `.env` runs it too, in place of `gpt-4`.
- Cluster requests go as the signed-in person: the server version and API discovery reads a screen opens now name the person in the target cluster's audit log, and a request whose context names no person is not sent unless it is Kubeast's own, which is only a `GET` of the server version or an API discovery path (`/version`, `/api`, `/apis`, `/api/v1`, `/apis/<group>/<version>`).
- Signing out ends the sign-in on the server: its tokens are refused and cannot be refreshed, and its open connections in other tabs close.
- No two roles share a group, and role names outside ASCII get distinct groups. A grant, an approval or an OIDC group sync of a role sharing another role's group is refused (400 `role_same_group`).
- The chart's PostgreSQL starts with `max_connections` from `postgresql.maxConnections` and restarts once on this upgrade. The chart's Redis has a memory cap (80 % of its memory limit, `volatile-lru`).
- Service Deployments roll one new pod at a time and stop an old one only once the new one is ready.
- The migration Job runs each try in a pod of its own and ends at 10 minutes.
- k8s-service's cluster breaker tries one request again after `multicluster.breakerOpenSec`, `multicluster.breakerConsecutiveFails: 0` turns it off, and only a request whose calls could not reach the API server counts as a failure. Its health check reads each cluster's `/version` behind none of the people's requests, and an answer below 500 closes the breaker.
- New live lists wait while k8s-service is short of memory, past 80 % of its Go memory limit, with a notice on the page.
- A grant limited to namespaces opens the Dashboard with fewer requests to the cluster, and an idle live-list socket holds 18 KiB instead of 47 KiB.
- Cluster View's node boxes are answered from the pod rows k8s-service keeps, once its informers run, instead of a list of the node's pods, and a pod's window opened from a box reads the pod before it shows its containers.
- Cache keys move under `kubeast:cache:`, and a cluster change deletes only those keys.
- Alert start times are kept in UTC, whatever offset the sender writes.
- Docker Compose gives the Kubeast services 35 s to stop and PostgreSQL and Redis 30 s (Docker's default is 10 s).
- API answers: a Deployment row carries `current_replicas`, event frames carry `involved_object.uid`, `/cluster/api-resources` lists resources in kubectl's order, `GET /auth/roles` adds `same_group_as`, and `GET /cluster/pods/on-node` answers a box row per pod: the full row's `name`, `namespace`, `node_name`, `pod_ip`, `status`, `phase`, `restart_count`, `created_at` and `labels`, with `health` and `health_reason`, and no containers; an audit log list or export whose `since` or `until` is not an RFC 3339 time answers 400, where it left that bound out; a token whose session cannot be read is answered 503 with `Retry-After` where 0.7.7 answered 401, a live socket or terminal left unchecked for 5 minutes closes with 1013 instead of 4401 `session_unverified`, a watch frame's `limit_scope` can be `opening` (a watch waiting its turn to open), and the Helm releases stream's event id names the cluster, its registration's `config_version`, a tag of the person and each watch's version (`helm-releases/<cluster>/<config_version>/<person>?<namespace>=<resourceVersion>&…`, where it was always `helm-releases`).

### Deprecated

- `gpt-4o` and `gpt-4o-mini` are marked deprecated in the OpenAI model list.

### Removed

- `pdb.minAvailable`. Set `pdb.maxUnavailable` instead.
- `o4-mini`, `gpt-5` and `gpt-5-mini` from the OpenAI model list. A saved setting naming one still opens, as a custom model name.

### Fixed

- In the light color mode the notice bands (a refused read, a stopped live list, a past sign-off or snapshot, the hygiene collectors and a cut list, kinds the graph could not read), the pending access requests count, log search highlights and the PriorityClass conflict chip keep their text readable, and the sign-in pages keep the default mode's colors; they had shown pale text on a pale ground since 0.7.6.
- No list, window or drawer draws one read's rows as another's after a switch of filter, tab, namespace, object or cluster.
- Panels that closed only on a click outside, Advanced Search's Select Resources and Settings, also close on Escape and give the focus back to their button; with the Refetch interval list open, the first Escape closes only the list.
- A list on Fit holds the rows that end inside its table, each measured at its own height, where 0.7.7 took the first row's height for every row: a list whose rows wrap holds another number of rows a page, and on the page it is counted on, no last row sticks out past the table's bottom.
- A live socket that connects again reads its lists again, so rows deleted while it was closed go; frames that come while a list is read are applied to its answer; the Helm releases stream goes on from the last version it saw, also when the browser opens it again after a cut or on another k8s-service, instead of sending every release again with a read of the list.
- A list's Refresh reads the list once, where each press read it a second time right after, and a change that comes while it reads stays on the list.
- Session-end audit rows are written even when the browser has already closed the connection.
- A database restart no longer signs people out. While a token's session cannot be read, auth-service, k8s-service, session-service and ai-service's REST routes refuse it with 503 and `Retry-After`, and tool-server's tool calls with 503, instead of 401, which the console reads as signed out (ai-service's MCP endpoint still answers 401). These 503s count in the `KubeastHighErrorRate` alert, which 0.7.7's 401 did not. The other services first take the version they read in the last 5 minutes, as when auth-service is down, and meanwhile ask auth-service again for a user at most every 2 s. The console keeps its page and asks again, the live lists connect again by themselves, a terminal offers Reconnect and a followed log says to open it again. A Helm releases stream the browser does not open again (its answer was a 503 or a 502) is opened again by the page once a GET of it answers, and reads its list again, since the browser's last event id is not sent with it; a stream refused (403) stops and says so, and a 401 goes the way of a live connection whose session ended. `/auth/me` answers 503 when any read of the person's access fails, where it answered 200 with less access. A version that moved on, a signed-out sign-in and a user or API key that is gone stay 401; an API key exchange whose key or owner cannot be read answers 503 and leaves its audit row. Going from 0.7.7, the 0.7.7 pods not yet replaced still answer 401 while the database restarts, so people using Kubeast then may have to sign in again ([Upgrading from 0.7.7 to 0.7.8](docs/upgrade-0.7.8.md#2-upgrade)); a 0.7.8 pod that asks a 0.7.7 auth-service answers 503, since auth-service now marks the 404 of a user or key that is gone (`"code": "subject_gone"`) and 0.7.7 answered a read that failed with the same 404 unmarked.
- The floating chat is told what a screen says for a read that was refused, failed or is not installed, instead of zero.
- While the chart's Redis does not answer, the screens k8s-service keeps in its cache (Helm releases, YAML, Timeline, the Resource Graph) read the cluster at once, where each read could wait 30 s or more: a cache command gives up within 0.5 s, and the cache then leaves Redis out for 3 s. A change's removal of cached entries that Redis did not take is made up for by flushing the cache in Redis before k8s-service reads it again.
- The chart's Redis, and Docker Compose's, keep no snapshot on disk: a Redis container started again in the same pod loaded the snapshot, with entries deleted after it.
- The floating chat button no longer sits over the Next button of a list's footer at the bottom of the screen: the page buttons of a footer that ends a page (a list page, Cluster View's node boxes and a node's pods) end clear of it, and a section's footer (the GPU screens' cards and panels) keeps them at its edge.
- The pod of a node shell whose k8s-service was killed (out of memory, a node lost) is deleted by another k8s-service, or by the same pod's restarted container, one to two minutes later, as the person who opened the shell, where it ran until `nodeShell.timeoutSeconds` (3600 s). A shell whose server is alive and reaches the database is never deleted by another; a server that cannot write its node shells' heartbeat to the database for 45 s closes them itself first. A row whose pod cannot be deleted is dropped once the deadline has passed. With node shell off (the default) nothing of this runs.
- The floating chat button no longer sits over the last words of AI Usage's note under its list, Advanced Search's page buttons under its results, or the Update button of the last AI model's edit form at the end of the AI Models page: the note ends where a list footer's page buttons end, Advanced Search's page buttons keep the same room, and the AI Models page leaves room under its last row.
- Monitoring's Nodes and Pods tabs no longer ask every 5 s on a cluster without metrics-server, and show a refused metrics read in the cluster's words.
- Monitoring's Pods tab on All namespaces, for an account limited to namespaces, says that no pod in those namespaces has metrics, where it said metrics-server is missing or not answering.
- Screen text follows the language rules in more places: Korean names Pod, Node, Namespace, Service and ServiceAccount in English and Role Management by its menu name; AI model notes, the Ollama and Custom provider names, the AI Models form's own messages and the text a window writes when a failure carries no reason are in the screen's language; empty fields of the dashboard windows and the Cluster View pod show `-`; the PriorityClasses list and the PriorityClass, Node and EndpointSlice drawers say their booleans as Yes or No text, not badges; a Secret with no data says None.
- A read the cluster refused is not tried again a second later, and a read on a timer (the Dashboard's overview, node list and problem pods, the Prometheus sections, the GPU screens, the Pods list, Cluster View, the admin lists, the Alerts inbox) stops once refused, until the screen is opened again, another cluster is chosen or the account's access changes; a refused read also asks once more when the browser tab is shown again a minute or more after the refusal, so access changed in the cluster itself shows on the same screen.
- A cluster switch asks each read of the new cluster once, with none of the parameters of the cluster left: the Dashboard asked for its top resources twice, once leaving out what the cluster left had refused. After signing in, a screen waits until a cluster is chosen, where it read the server's default cluster first, and a cluster list that could not be read (a 503 while the database restarts, asked again as it says) keeps the cluster chosen before, where it cleared it.
- Prometheus sections say when the cluster's Prometheus does not answer, and that no longer marks the whole cluster unreachable.
- Hundreds of people opening the Timeline of every namespace on a cluster of 100 000 events no longer take k8s-service past its 512 Mi. The Timeline and the events API read a namespace's or the cluster's events once for everyone asking the same at that moment whose identity may list them all, as `kubeast:cache`, and each answer counts its own window from that read, as its own read would; a read of more than one page of events, as the person or for everyone, takes one of `multicluster.bigReadConcurrency`'s places. In 0.7.6 and 0.7.7 each person read every event, all at once.
- The Timeline of every namespace, opened by hundreds of people at once, answers within the gateway's 60 s again: its rollouts read a namespace's or the cluster's Deployments, ReplicaSets and ControllerRevisions once for everyone asking at that moment whose identity may list that kind there, as `kubeast:cache`, and each answer keeps the rollouts of its own window, as its own read would. With 500 people, the Timeline's rollouts read about 24 000 pages of ReplicaSets, 8 000 of ControllerRevisions and 11 000 of Deployments as those people in 16 minutes, and 214 of 718 Timelines waited past 60 s.
- The ClusterRole the docs give a registered cluster's credential lets it get the `kube-system` Namespace, whose UID refuses a second entry for a cluster and a registered cluster's kubeconfig replaced by another cluster's. With the credential the docs gave as enough, the UID could not be read and both checks were skipped. Apply the RBAC again on each registered cluster ([Cluster requirements](docs/cluster-requirements.md) §1).
- A time with an offset (such as `+09:00`) now means the moment it names in an audit log search, its CSV export, an AI Usage period and the chat list API's `before_updated_at`. Before, its clock time was read as UTC, so the results were off by the offset. The console sends UTC and was not affected.
- The AI tools read `until_time` the same way, and refuse one of the right form that is no real time (such as `2026-02-30T00:00:00Z`) with the reason. An audit log search or export with a `since` or `until` that is not an RFC 3339 time now answers 400, where that bound was left out and every row on its side matched.
- Secret files stay readable with `podSecurity.enabled: false`.
- The chart refuses `sessionRecording.storage: file` with more than one k8s-service pod (`replicas.k8sService` above 1, or `autoscaling.k8sService` with `maxReplicas` above 1), as it does with `streams.enabled`: every pod mounted the one file volume. Use `s3` or `database`.
- Teams says under the name field why Add did not add a team with no name, where it only moved the focus to the field, and the field has a label.
- A values file copied from 0.7.6 or earlier stops on its release image tag instead of keeping that release's images.
- A request through the gateway whose connect to a service gets no answer, as for a moment after that service's only pod is deleted, ends as 504 after 3 s instead of waiting nginx's default 60 s: every route now has the 3 s connect timeout only the AI routes had.
- A chat answer whose stream was cut is saved once, under its question.
- A chat in which the AI asked for approval of a write (an approval card) can be deleted, where AI Chat said "Not deleted: internal server error" and kept it: session-service deletes the chat's approval requests (`tool_approvals`) with it, in one transaction. Approve and Reject write their audit rows (`ai.tool.execute`, `k8s.pod.exec`, `ai.tool.reject`) before the chat message, so they are written also when the chat was deleted while the write ran.
- Deleting a chat, and the chat retention purge (`retention.chatDays`), name in their audit row each write approval they delete while it is still approved (`after.open_approvals` of `ai.session.delete` and `admin.retention.purge`: its id, tool, cluster and approval time), where the audit log kept its `ai.tool.approve` with no row saying the call's outcome was never written, as when the ai-service running it stopped.
- AI Chat says under its title why it could not read the AI model, such as no model set up yet, where it showed only "Start a new chat": at once, in two lines at most with the whole reason on hover.
- An approved AI write whose ai-service stopped before writing the outcome (out of memory, a lost node, or a shutdown that cut a run going past 20 s) no longer says "running" on its approval card for good with its arguments unmasked in the approval row: 10 minutes after the approval, the first ai-service to look (a new approval card, the card opened, a pod's first database use) ends it failed as interrupted, with the arguments masked and an `ai.tool.interrupt` audit row in the same transaction. Approvals an earlier release left so end the same way after the upgrade. Whether the write changed the cluster is not known, and the card's result says to check the cluster before asking again. Approve with a model setting that cannot be used answers 503 and leaves the card waiting, to approve once the setting is fixed.
- After an audit row ai-service could not write on PostgreSQL, its approvals, MCP tool calls, alert investigations and AI model changes go on once the audit table takes rows again. Since 0.7.0, with `AUDIT_FAIL_CLOSED` on (the default), they stayed refused (503 `audit unavailable`, a tool's `audit_unavailable`) until a row written without that check, such as a chat message's, was stored on that pod, or the pod restarted: the readiness check that tries an insert after a failed write stopped on its own transaction each time, before the insert.
- Advanced Search's examples "Pods whose first container restarted more than 5 times" (`status.containerStatuses[0].restartCount > 5`) and "ConfigMaps that carry data" (`data != null`) find what they say, where `status.containerStatuses?.some(c => c.restartCount > 5)` and `!!data` matched nothing, and "Completed jobs (not suspended)" reads `status.completionTime != null`, where `status.succeeded > 0` also took a running Job with one pod done; an expression the search cannot read or compute says so with the reason in place of the results ("The expression could not be read: Unexpected operator"), also when the read listed no objects, and tells the floating chat the same with the types the read failed or cut, where it showed 0 results.
- For development: tests that failed now and then on a busy runner, or read one pod where a service can run two, wait on what they check, and the guard's build to compare with (`scripts/before-stack.sh up <tag>`) takes the probes of that tag's chart.
